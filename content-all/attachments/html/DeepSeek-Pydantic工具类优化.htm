1. field_validator 和 model_validator 示例

`field_validator` 和 `model_validator` 是 Pydantic 提供的两种内置校验机制，它们分工明确，构成了一个层层递进的校验体系-7。

  • `Field` 是最基础的约束：它通过参数如 `min_length`、`ge`（大于等于）、`pattern`（正则匹配）等，直接对字段进行声明式校验-7-4。

  • `@field_validator` 处理单字段复杂逻辑：当 `Field` 的约束不够用时，用它来为一个或多个特定字段添加自定义校验逻辑。校验失败则抛出 `ValueError`-7-4。

  • `@model_validator` 处理跨字段联合校验：当校验需要比较多个字段的值（例如密码确认、日期范围）时，使用它。它能访问到整个模型的实例，进行字段间的联动检查-7-10。

from pydantic import BaseModel, Field, field_validator, model_validator

class RegisterVo(BaseModel):
    username: str = Field(..., min_length=2, max_length=20, description="用户名")
    password: str = Field(..., min_length=6, max_length=20, description="密码")
    confirm_password: str = Field(..., description="确认密码")

    # 1. @field_validator: 对 username 字段进行额外清洗和校验
    @field_validator("username")
    @classmethod
    def username_must_valid(cls, v: str) -> str:
        # 去掉前后空格
        cleaned = v.strip()
        # 自定义业务规则：英文名至少3字符，中文名至少2字符
        if cleaned.isascii():
            if len(cleaned) < 3:
                raise ValueError("英文用户名至少需要 3 个字符")
        else:
            if len(cleaned) < 2:
                raise ValueError("中文用户名至少需要 2 个字符")
        return cleaned

    # 2. @model_validator: 校验 password 和 confirm_password 是否一致
    @model_validator(mode="after")
    def check_passwords_match(self) -> 'RegisterVo':
        if self.password != self.confirm_password:
            raise ValueError("两次输入的密码不一致")
        return self

关键语法点：

  • `@field_validator("username")` 指定了它校验的字段名-7。

  • 修饰器函数必须声明为 `@classmethod`，其第二个参数 `v` 是待校验的字段值-7。

  • 返回值会替换原值（如上面的 `return cleaned` 实现了去除首尾空格的效果）-7-4。

  • `@model_validator(mode="after")` 表示在模型实例创建之后执行，此时可以安全地通过 `self` 访问所有字段的值-10-7。

1. `@field_validator` 与 `@classmethod` 的顺序关系

顺序有关系，且必须是 `@field_validator` 在上，`@classmethod` 在下。

python
复制
下载
# ✅ 正确
@field_validator("username")
@classmethod
def username_must_valid(cls, v: str) -> str:

# ❌ 错误 - 会报错

@field_validator("username")

原因：装饰器是从下往上执行的。当 `@classmethod` 在下面时，它先被执行，将函数变成类方法。然后 `@field_validator` 收到的是一个类方法对象，而不是普通函数，导致 Pydantic 无法正确识别和注册这个校验器。

2. `model_validator(mode="after")` 的 before 和 after 时机

模式执行时机能访问的数据常见用途

`mode="after"`在所有字段校验之后执行能访问已校验的完整模型实例 (`self`)跨字段依赖校验（如密码确认）、计算派生字段

    age: int

        """在校验后：检查年龄合理性"""
        if self.age < 0:

⏹️ 实现防止死循环的早停策略

防止 Agent 陷入死循环，通常需要组合使用多层策略，从“硬限制”到“智能检测”逐层递进。

第一层：设置最大迭代次数 (`max_iterations`)

这是最基础也最直接的防护，为 Agent 的执行步数设定一个硬上限。当达到这个阈值时，Agent 会强制终止。

  • 实现方式：在使用 `AgentExecutor` 时，直接设置 `max_iterations` 参数。不同 Agent 类型的默认值有所不同（如 `ReActAgent` 默认为 6，`StructuredChatAgent` 默认为 12），建议根据任务复杂度显式设置，简单任务 5-8 步，复杂任务 10-15 步，然后根据日志调优-4。

  • 示例代码：

    python
    复制
    下载
    from langchain.agents import AgentExecutor

agent_executor = AgentExecutor(
    agent=agent,
    tools=tools,
    max_iterations=10,  # 设置最大循环次数
    handle_parsing_errors=True,
)

第二层：设置递归限制 (`recursion_limit`)

这是 LangGraph 底层引擎的安全限制，控制图中可以执行的步骤总数。`create_agent` 返回的 Agent 基于 LangGraph，因此受此限制。

  • 实现方式：在调用 `agent.invoke()` 时，通过 `config` 参数传入`[citation:3][citation:6]`。

  • 示例代码：

    python
    复制
    下载
    agent = create_agent(model, tools)
# 在调用时设置递归限制
result = agent.invoke(
    {"messages": [{"role": "user", "content": "..."}]},
    config={"recursion_limit": 100}  # 默认是 25
)

第三层：使用中间件 (Middleware) 进行智能检测

这是 `create_agent` 提供的更高级、更智能的方式。中间件可以在 Agent 的每一步执行前后插入逻辑，用于检测重复模式并主动干预。

  • `ModelCallLimitMiddleware` (调用次数限制)：可以直接限制模型被调用的次数，达到阈值后抛出错误终止流程-7。

  • `LoopDetectionMiddleware` (循环检测)：可以跟踪 Agent 的行为，例如检测同一文件是否被反复编辑且毫无进展，一旦发现这种“微循环”，就向 Agent 注入提示词（nudge），引导它改变策略-1。

  • 实现方式：将中间件实例传给 `create_agent` 的 `middleware` 参数。

  • 示例代码：

    python
    复制
    下载
    from langchain.agents import create_agent
from langchain.agents.middleware import ModelCallLimitMiddleware

limit_middleware = ModelCallLimitMiddleware(
    run_limit=3,  # 最多调用模型 3 次
    exit_behavior="error",
)

agent = create_agent(
    model=llm,
    tools=[...],
    middleware=[limit_middleware],  # 应用中间件
)

这三层策略通常结合使用：用 `max_iterations` 和 `recursion_limit` 兜底，用中间件进行更智能的检测和干预。

🔑 `create_agent` 的模型配置 (base_url & api_key)

关于你问的 `create_agent` 指定模型时是否需要传递 `base_url` 和 `api_key`，答案是：`create_agent` 本身不直接配置这些，而是通过它接收的 `model` 参数（即你创建的 LLM 实例）来配置的。

因此，你需要先构造一个已配置好 `base_url` 和 `api_key` 的模型实例，再传给 `create_agent`。这样做的好处是可以支持多种服务提供商-2-5-8。
