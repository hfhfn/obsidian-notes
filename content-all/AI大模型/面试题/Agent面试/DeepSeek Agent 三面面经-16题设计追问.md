## 一、架构与安全

### Q1：AI 私人助理的整体架构怎么设计？

面试官给了四个层的名字，但真正在问的是：**你为什么这么切，边界在哪。**

| 层 | 要解决的事 | 关键设计 |
|---|---|---|
| **交互层** | 多端接入（App / 小程序 / 语音）、会话状态保持（session vs conversation）、**意图前置判定** | 一句话进来先判断：闲聊 / 查询 / 执行动作。判定做不好，调度层会收到大量无意义请求 |
| **调度层** | 规划（拆步骤）、分发（选工具 / 子 Agent）、状态管理、终止判定 | 核心是 Agent Runtime；核心矛盾是「灵活性与可控性」——纯 ReAct 灵活但容易跑飞，纯固定流程可控但覆盖不了长尾 |
| **工具层** | 所有外部能力的统一封装 | **统一工具契约**：输入 schema、输出 schema、错误码、超时、幂等语义、权限标签。工具不是「能调就行」，而是「调失败了系统知道怎么退」 |
| **记忆层** | 被动记忆（存下来，需要时召回）+ 主动记忆（常驻用户画像） | **读写分离**：写走异步、读走缓存，否则每次对话都要等一次数据库往返 |

> [!important] 四层调用关系
> **严格单向 + 事件回调**：交互层不直接调工具层，调度层不直接操作数据库。
> 理由很实际——一旦允许跨层直连，后面想加 trace、加权限、加限流，就得改 N 个地方。

> [!quote] 面试官想听的
> 分层不是为了画图好看，是为了让「加一个能力」和「加一个约束」都只改一个地方。

### Q4：AI 生成代码的安全性怎么解决？

关键认知：**「禁用 exec/eval」只是第一层，真正的边界在内核。** 四层防御，从外到内：

| 层 | 做法 | 要点 |
|---|---|---|
| ① **隔离层** | microVM（Firecracker）或用户态内核（gVisor），再退一步至少 nsjail / bubblewrap | 容器共享宿主机内核，逃逸面比 microVM 大得多 |
| ② **网络层** | 默认**完全禁网**，不是「限制域名」 | 限制域名要靠 DNS 和代理，而代码可以直接连 IP；要联网就走白名单代理 + 出站流量审计 |
| ③ **系统调用层** | seccomp-bpf 做 syscall 白名单；Landlock 限制文件访问路径 | 只放行运行时必需的（读文件、内存分配、时钟）；`execve`、`fork` 直接不给 |
| ④ **资源层** | cgroups v2 限 CPU / 内存 / 进程数 + wall-clock 超时 | 内存和进程数一定要限，否则一个 fork bomb 就能把宿主机打挂 |

> [!warning] 语言层面的禁用是辅助，不是边界
> Python 里禁 `exec` / `eval` / `__import__`、禁 `os.system`、禁 `subprocess`——这一层容易被绕过（`getattr(builtins, 'ev'+'al')`）。

**两个常被忽略的点：**

- **依赖供应链**：用户代码 `pip install` 一个恶意包，前面四层全白做。沙箱要无外网 + 预置镜像。
- **产物审计**：生成的文件（脚本、二进制）出沙箱前要扫描，不能直接落到用户真实目录。

> [!quote] 面试官想听的
> 「禁 exec/eval 不够，边界必须在内核和网络。」

### Q5：定制了哪些能力？

四件「看起来简单、做起来全是坑」的事：

| 能力 | 做法 |
|---|---|
| **任务调度** | 持久化执行引擎（Temporal / Restate 思路）：每一步是一个 activity，状态落库，进程挂了能从断点续跑；不能「一个 for 循环跑到底」 |
| **状态回退** | 三件事：**幂等**（重放不重复下单）、**补偿**（Saga 模式，已发出的请求怎么撤回）、**状态快照**（回退到哪一版）。做法：每步写 checkpoint，回退 = 恢复 checkpoint + 重放后续步骤 |
| **Checkpoint** | 存**最小可恢复状态**：任务目标、已完成步骤、每步关键产出、当前待决策点。存全量上下文会让 checkpoint 越来越大、恢复越来越慢 |
| **Trace 回放** | 记的不是最终答案，而是：每次模型调用的完整输入输出 + 每次工具调用的参数和返回 + 每步耗时。**不能复现的问题，基本等于修不了** |

> [!quote] 面试官想听的
> 「Agent 的可靠性靠 durable execution，可调试性靠 trace。」

## 二、幻觉控制

### Q2：高准确性场景怎么控制幻觉？

按「介入阶段」分四类：

| 阶段 | 手段 | 作用边界 |
|---|---|---|
| **生成期** | **约束解码**：grammar-constrained decoding 强制符合 JSON Schema（Outlines / XGrammar / llguidance / vLLM guided decoding） | **只保证格式合法，不保证内容正确**。能保证时间是合法 ISO 时间，保证不了是用户说的那个时间——把它当防幻觉手段是概念混淆 |
| **生成前** | **检索增强**：把「凭记忆答」变成「照着材料答」 | 关键不在有没有 RAG，而在**检索结果是否强制进上下文**。事实类查询检索为空，就直接走「我不知道」分支 |
| **生成后** | **引用溯源**：每条事实性陈述挂到来源（span-level attribution） | 输出结构带 `citations` 字段 + 生成后引用校验。**性价比最高**：把「难以度量的质量问题」变成「可以跑批的校验任务」 |
| **生成后** | **自我反思**：让模型自查 | 对「知识性幻觉」几乎无效——模型不知道自己不知道。有效的是「逻辑一致性」：前后矛盾、漏约束、算错数 |

> [!important] 四种手段不是并列的
> 约束解码管**格式**、检索管**事实来源**、引用校验管**可追溯**、反思管**一致性**。
> 只说「我用了 RAG + 反思所以幻觉低」，等于没答。

### Q3：幻觉率、引用错误率多少？业务能不能接受？

这是陷阱题——面试官要的不是数字，是**你怎么定义这个数字**。

**先拆指标：**

| 指标 | 定义 | 可测性 |
|---|---|---|
| **事实错误率** | 答案里出现与事实不符的陈述 | 人工标注口径 |
| **引用错误率** | 引用存在但不支持该结论，或引用片段根本不存在 | 可自动测 |
| **越界率** | 检索不到却仍然作答的比例 | 最好测，日志直接统计 |

**再说口径：** 分母是「所有回答」，还是「所有包含事实性陈述的回答」？两者能差好几倍，混着讲就是耍花招。

**然后按场景分级：**

| 场景 | 策略 |
|---|---|
| **日程 / 转账 / 发消息这类写操作** | **零容忍**。不是「降低错误率」，而是改成**确认式交互**：AI 只生成草稿，落库前必须用户确认。把模型准确率问题转化成产品交互问题，是唯一可靠的解法 |
| **信息汇总 / 摘要** | 可容错，但必须**带引用**，让用户能自己核 |
| **闲聊 / 建议** | 基本不设阈值，错了代价很小 |

**最后加一层熔断：** 某类意图的越界率连续超阈值，自动降级到「只检索不生成」或「转人工」。

> [!quote] 面试官想听的
> 先给定义和分母，再给分级阈值，最后给熔断。顺序错了就显得没做过。

## 三、记忆系统

### Q6：长中长期记忆怎么分层存储？

按「访问频率 + 生命周期」分四层，而不是按技术栈分：

| 层 | 存储 | 内容 | 要点 |
|---|---|---|---|
| ① **工作记忆** | 上下文窗口 | 当前会话最近若干轮 + 当前任务中间状态 | 不落库，就是 prompt 里的内容 |
| ② **短期记忆** | Redis | 跨轮但不跨天的：会话状态、临时槽位、限流计数 | 带 TTL，过期自动清 |
| ③ **长期语义记忆** | 向量库 | 历史对话片段、文档、笔记 | 解决「找得到相关的东西」，不解决「这个东西是否权威」 |
| ④ **长期结构化记忆** | MySQL / PG | 用户画像、偏好、事实性槽位（「用户住上海」「不吃辣」「周三下午固定开会」） | **权威源** |

> [!important] 向量库不是记忆，它只是索引
> 很多人把「把所有对话塞进向量库」当记忆系统，结果：同一事实五个版本、时间上互相矛盾、检索出来不确定哪个对。
> **正确做法：事实进结构化表，原文进向量库。** 结构化表每条事实带 `source_span`（对应哪段原文）、`confidence`、`updated_at`；冲突时按时间和置信度裁决，而不是看谁被检索出来。

**读取路径也要分层：** 先读结构化（快、准），检索不到再走向量（慢、广）。反过来会很贵。

> [!quote] 面试官想听的
> 「权威源和索引要分开」——这是记忆系统和「一个大号向量库」的分水岭。

### Q7：记忆滚动更新、摘要压缩、结构化压缩分别怎么做？

三种压缩的**失真特性完全不同**：

| 方式 | 做法 | 关键细节 / 代价 |
|---|---|---|
| **① 滚动更新（rolling summary）** | 滑动窗口：保留最近 N 轮原文，更早的压成摘要，摘要随新内容滚动更新 | 摘要要带**锚点**：不能只写「用户讨论了项目排期」，要写「用户说项目排期定在 11 月中（第 12 轮）」。**摘要有损且不可逆**，原始对话必须冷存兜底 |
| **② 摘要压缩（hierarchical summary）** | 每 10 轮一个小结，每 10 个小结一个中结，以此类推 | 检索可先命中「中结」再下钻「小结」。代价：层级越高粒度越粗，越容易丢关键约束。高层摘要要维护**「不可丢弃字段」**：硬性约束、已承诺的事、明确拒绝的事 |
| **③ 结构化压缩（slot extraction）** | 把自然语言抽成 schema：`{偏好, 约束, 事实, 待办}` | **唯一无损可校验**的——抽取完可反查原文。但只覆盖「能被 schema 表达」的部分，情绪、语气、氛围全丢 |

> [!success] 工程组合
> **结构化管硬事实，摘要管软上下文，原文兜底。** 三者并存，不是三选一。

> [!quote] 面试官想听的
> 「压缩必然有损，所以要留原文、留锚点、留不可丢弃字段。」

## 四、多 Agent 与工程范式

### Q8：Multi-Agent 怎么协作？ReAct 与 Plan-and-Act 什么区别？

**三种协作拓扑：**

| 拓扑 | 特点 | 适用 |
|---|---|---|
| **主从（Orchestrator-Worker）** | 一个调度者拆任务，分给专家 Agent | 可控性最好，适合业务流程明确的场景 |
| **流水线（Pipeline）** | 固定顺序传递，如「检索 → 分析 → 写作 → 校对」 | 最简单，也最容易被误当成 Multi-Agent |
| **对等协商（Debate / Peer）** | 多个 Agent 各自出方案再投票或辩论 | 质量上限最高、成本也最高，一般只用在关键决策点 |

实际用最多的是**主从 + 局部对等**：主流程主从，只在「需要判断的节点」开两三个 Agent 交叉验证。

**ReAct vs Plan-and-Act 不是新旧关系，是两种控制流：**

| | ReAct | Plan-and-Act |
|---|---|---|
| 机制 | Think → Act → Observe 循环，每步基于上一步观察决定下一步 | 先一次性生成完整计划，再逐步执行 |
| 优点 | 能根据反馈动态调整 | 可控、可预估成本、可人工审核计划 |
| 缺点 | 没有全局视野，容易局部绕圈，步数不可预测 | 计划一错后面全错，中途环境变化无法自适应 |

> [!tip] 实际系统通常是分层混合
> 外层用 Plan 生成粗粒度计划（3–6 步），每一步内部用 ReAct 执行。既有全局约束，又保留局部灵活性。

### Q9：Loop Engineering 是什么？和 Graph Engineering 有什么区别？

两个词不是标准术语，但精准描述了两种工程取向：

| | Loop Engineering | Graph Engineering |
|---|---|---|
| 组织方式 | 围绕一个循环：think → act → observe，直到满足终止条件 | 把流程显式画成图：节点是步骤/Agent，边是转移条件 |
| 核心工程问题 | **怎么保证循环能停下来**：最大步数、重复动作检测、无进展检测（连续 N 步无新增有效信息就退出）、成本熔断 | **状态怎么在节点间传递、在哪落盘**：checkpoint、条件边 |
| 适合 | 开放域、路径不确定的任务（如「调研一个行业」） | 流程相对确定、但分支多的任务（客服工单、审批流、内容生产流水线） |
| 优势 | 灵活 | 可视化、可测试、可回滚、可插入人工节点 |

> **一句话区分：Loop 是「用模型决定下一步去哪」，Graph 是「用人决定有哪些步，让模型决定走哪条边」。**

**演化路径：** 先 Loop 快速验证 → 跑出稳定高频路径 → 把这条路径固化成 Graph → 只在不确定的节点上保留 Loop。

> [!quote] 面试官想听的
> 「Loop 的问题是收不住，Graph 的问题是改不动，所以成熟的系统是 Graph 骨架 + Loop 节点。」

### Q10：MCP 与 Skill 分别怎么注册和使用？

两者**不在一个层面**：

| | MCP（Model Context Protocol） | Skill |
|---|---|---|
| 层次 | **协议层** | **能力包 / 方法论层** |
| 定义 | 模型怎么和外部能力通信：JSON-RPC 2.0、三类原语（tools / resources / prompts）、传输（stdio / SSE / streamable HTTP） | 「提示词 + 脚本 + 流程知识」的封装；注册「什么场景下、按什么步骤、用什么工具」 |
| 注册 / 调用 | Server 声明 tool（名字、描述、inputSchema）→ 客户端 `tools/list` 注入模型上下文 → 模型输出 `tool_use` → 客户端转发 `tools/call` → 结果回填 | 描述触发场景与执行步骤，按流程调用已有工具 |
| 价值 | **解耦**：工具作者不关心模型和宿主，写一次所有支持 MCP 的客户端都能用 | 固化内部流程与最佳实践 |
| 一句话 | 解决「**能不能调**」 | 解决「**该怎么用**」 |

**典型组合：** 数据库 MCP Server 提供 `query` 工具（协议层）；Skill 里写「先看表结构 → 再生成 SQL → 执行前 explain → 结果超过 100 行要聚合」（方法论层）。

**选型：** 跨应用复用 → MCP；内部流程固化 → Skill。反过来用会很别扭——把流程知识塞进 MCP Server，会让工具又胖又难维护。

> [!quote] 面试官想听的
> 「MCP 是接口标准，Skill 是使用范式，两者是正交的。」

## 五、数据闭环

### Q11：Badcase 怎么定义？review 拒绝、用户不采纳、高质量样本怎么处理？

**先给三分类，这是整题的地基：**

| 类型 | 例子 | 可信度 |
|---|---|---|
| **① 显式负反馈** | 点踩、点「重新生成」、明确说「不对」 | 较高 |
| **② 隐式负反馈** | 不采纳、不复制、追问同一件事、会话中途断掉、改完才用 | **差别极大，最容易被误用** |
| **③ 自动检出** | schema 校验失败、引用校验失败、工具调用报错、超时、循环超限 | 高 |

> [!warning] 「用户不采纳」是最容易被误用的信号
> 用户没采纳，可能是模型错了，也可能是用户改主意、想换说法、只想看看别的方案。不做归因就打标，训出来的模型会学到「少给建议」「少主动」。

**必须加一层归因分类：** 事实错 / 格式不合 / 风格不合 / 需求变了。只有「事实错 / 格式不合」才进训练集，「需求变了」要丢弃。

**Review 拒绝同理：** 要区分「答错了」和「答对了但不合规」（如泄露不该说的信息）。后者不是能力问题，是策略问题，不该进 SFT。

**高质量样本三条件同时满足：** 用户明确接受（或复制/采纳）+ 人工 review 通过 + **可验证**（有引用、有工具返回、有标准答案）。第三条最重要——没有可验证依据的「好评样本」，训进去等于把模型的运气固化下来。

### Q12：Badcase 回流 SFT 的完整链路？

九步流水线，每步一个坑：

| # | 步骤 | 坑 / 要点 |
|---|---|---|
| ① **采集** | 从 trace 拉全链路记录，不是只拉最终问答 | 没有 trace 就没有回流，这是前置条件 |
| ② **归因打标** | 人工 + 规则；打三类标签：错在哪（事实/格式/推理/工具）、错的原因（知识缺失/检索失败/指令理解/策略）、该怎么改 | 归因不清，后面全白做 |
| ③ **去重与聚类** | 同一问题可能 200 条相似 badcase | 全量训会过拟合这一个点；聚类后按簇采样 |
| ④ **脱敏** | 用户隐私、内部 ID、密钥 | 必须在构造训练数据**之前**做 |
| ⑤ **构造样本** | SFT pair / DPO pair / 过程监督 | **不能直接把用户期望当答案**，要重写正确答案并带引用；过程监督训「中间该调哪个工具、怎么规划」，对 Agent 特别有效 |
| ⑥ **配比** | 新数据占比 **5%–20%**，混入等量同分布正常样本防遗忘 | 最容易翻车：badcase 通常只有几百条，直接混会被通用数据淹没，或反过来过拟合 |
| ⑦ **训练** | LoRA 起步，全参只在大版本动；学习率比常规略低 | 防少量数据过拟合 |
| ⑧ **离线评测** | 必须跑三套：回归集、badcase 集、留出盲测集 | 盲测集防在 badcase 集上过拟合 |
| ⑨ **灰度与监控** | 小流量上线，盯四个指标：同类 badcase 复现率、整体采纳率、平均步数、时延 | 采纳率涨但时延涨太多，不能全量 |

> [!quote] 面试官想听的
> 「回流不是训一遍就完，关键是配比和回归集——修新问题的同时别弄坏老能力。」

## 六、评测与 RAG

### Q13：评测体系怎么搭？四层怎么分工？

| 层 | 指标 | 失败表现 |
|---|---|---|
| **① 检索层** | Recall@k、MRR、nDCG、**引用命中率** | 「材料没找到」，模型再强也救不了 |
| **② 生成层** | 忠实度（faithfulness / groundedness）、答案正确率、格式合规率、引用正确率 | 要能区分「答错了」和「答得对但没依据」——后者更危险，因为看起来可信 |
| **③ 链路层** | 任务成功率、工具调用成功率、平均步数、P95 时延、异常退出率 | 很多问题出在链路，不在模型 |
| **④ 线上层** | 采纳率、重试率、追问率、投诉率、次日留存 | 唯一真实的指标，但延迟高、信噪比低 |

> [!important] 关键在层与层之间的归因
> 线上采纳率跌了 → 线上 badcase 反向打回链路层 → 看哪一步失败 → 再打回生成层/检索层 → 看是模型问题还是材料问题。
> **没有这条归因链，四层评测就只是四张报表。**

**离线涨、线上不涨，八成是这三个原因：** 评测集与真实分布不一致、指标定义与用户感知不一致（nDCG 涨了但用户只看第一条）、链路层有时延/失败率拖累。

### Q14：知识助手 RAG 的难点？PDF / 表格 / 条款怎么解析切分？

难点不在「接一个向量库」，在**文档进入向量库之前那一段**。这段决定上限，后面怎么调都补不回来。

| 文档类型 | 坑 | 做法 |
|---|---|---|
| **PDF** | 双栏被读成交错、页眉页脚混进正文、扫描件无文字层、公式图注被打散 | 先做**版面分析**（DocLayout-YOLO / LayoutLMv3），拿到区块（标题/正文/表格/图/页眉页脚）再按阅读顺序拼接，不要直接 `pdfplumber` 抽全文 |
| **表格** | 跨页、合并单元格、无边框，纯文本抽取破坏行列关系 | 转成 Markdown 或 HTML 保留结构；表格前补一行「表头说明」（这张表在讲什么、行列是什么含义）——检索靠语义，光有数字召不回 |
| **条款** | 法律/制度靠层级编号表达逻辑（第 X 条 → 第 X 款 → 第 X 项） | 切分必须保留**父级路径**，否则孤立的「（三）应当在 5 个工作日内……」召回来没人知道属于哪条 |

**切分的核心矛盾：** 块小 → 检索准但上下文不全；块大 → 上下文全但检索不准。

> [!success] 工程解法
> **小块检索、大块喂入（small-to-big / parent-child chunk）**：用 200–400 字的子块建索引，命中后回溯到父块（整节或整条）喂给模型。
> 每个 chunk 都要带「属于哪份文档、哪一章、哪一节」的元数据；检索时先按元数据过滤，再走向量——**元数据预过滤的收益，通常比换一个更好的 embedding 模型更大**。

> [!quote] 面试官想听的
> 「RAG 的上限在解析，不在检索；切分要做小块检索、大块喂入。」

### Q15：检索怎么优化？query rewrite / BM25 / 向量 / RRF / rerank 怎么配合？

这五个组件不是并列的「优化点」，是一条链上的不同环节：

| # | 组件 | 解决什么 | 要点 |
|---|---|---|---|
| ① | **Query rewrite** | 「问得不像文档」 | 指代消解 + 补全、多查询扩展（3–4 个角度）、多跳拆解。**收益通常最大**，因为很多「检索不到」本质是 query 信息不足 |
| ② | **双路召回** | 单一召回的盲区 | BM25（稀疏）擅长精确匹配：型号、编号、专有名词、条款号；向量（稠密）擅长语义相似：同义、跨语言、模糊描述。**两路必须都有** |
| ③ | **RRF 融合** | 两路分数不可比 | BM25 分数无界、余弦相似度在 [−1,1]，直接加权没有意义。RRF 只用排名：`score(d)=Σ1/(k+rank_i(d))`，k 通常取 60。**RRF 是融合手段，不是提分手段** |
| ④ | **Rerank** | 召回准但排序糙 | 召回用双塔（快、精度有限），rerank 用 cross-encoder（query+doc 拼一起，精度高但慢），只对 Top 20–50 做 |
| ⑤ | **上下文组装** | 召回了怎么放进 prompt | 最相关的放开头和结尾（中间位置容易被忽略，即 lost-in-the-middle）；每个片段带来源标识，为引用溯源服务 |

**实践漏斗：** 召回宽（每路 50–100）→ RRF 合并 → rerank 取 Top 5。这个漏斗形状比参数调优重要。

> [!quote] 面试官想听的
> 「rewrite 提召回率，双路补盲区，RRF 只做融合，rerank 才是提精度的关键。」

## 七、手撕：最长公共子串

> [!warning] 先区分「子串」和「子序列」
> - **最长公共子串（Longest Common Substring）**：必须**连续**。递推 `dp[i][j] = dp[i-1][j-1] + 1`（相等时），不相等归零。
> - **最长公共子序列（LCS）**：可以**不连续**。不相等时取 `max(dp[i-1][j], dp[i][j-1])`。
> 题目里如果是子串，就按子串实现；面试时如果面试官说 LCS，**主动确认是子串还是子序列**——这个确认本身就是加分项。

```python
def longest_common_substring(s: str, t: str) -> str:
    m, n = len(s), len(t)
    # dp[i][j]: 以 s[i-1]、t[j-1] 结尾的最长公共子串长度
    dp = [[0] * (n + 1) for _ in range(m + 1)]
    best, end = 0, 0          # best 记录最大长度，end 记录在 s 中的结束位置

    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if s[i - 1] == t[j - 1]:
                dp[i][j] = dp[i - 1][j - 1] + 1
                if dp[i][j] > best:
                    best = dp[i][j]
                    end = i
    return s[end - best:end]
```

**三个容易错的点：**

- `dp` 要多开一行一列，表示「空前缀」，否则 `i-1` 越界。
- `best` 和 `end` 要在更新的同时记录，不能最后再扫一遍——扫一遍能找到长度，但找不到对应子串。
- `end` 取 `i` 而不是 `j`，因为结果要从 `s` 里切；两边长度一致取哪个都行，但要在注释里说清。

### 一维滚动（空间 O(n)）

```python
def longest_common_substring_1d(s: str, t: str) -> str:
    m, n = len(s), len(t)
    dp = [0] * (n + 1)
    best, end = 0, 0

    for i in range(1, m + 1):
        # 关键：内层必须倒序，否则 dp[j-1] 已被本行更新，会串行累加
        for j in range(n, 0, -1):
            if s[i - 1] == t[j - 1]:
                dp[j] = dp[j - 1] + 1
                if dp[j] > best:
                    best = dp[j]
                    end = i
            else:
                dp[j] = 0        # 必须清零，否则残留上一行的值
    return s[end - best:end]
```

> [!important] 倒序是唯一的陷阱
> 正序时 `dp[j-1]` 已是本行（第 i 行）的值，等于把「本行上一列」当成「上一行上一列」，结果会算出连续重复的错误长度。

**复杂度：** 时间 O(m·n)，空间二维 O(m·n)、一维 O(min(m, n))。

**可能的追问：**

- **返回所有最长公共子串？** 不改 DP，更新 `best` 时收集位置；出现更长时清空重收。
- **数据量到百万级？** DP 不可行（O(m·n) 在百万规模是 10¹² 量级）。改用**后缀自动机**或**后缀数组 + LCP**，可做到 O(n) 级别。
- **多字符串的公共子串？** 后缀自动机同样适用（在 SAM 上跑所有串，取每个状态的最小匹配长度）。

> [!quote] 面试官想听的
> 主动区分「子串」和「子序列」，以及一维滚动里为什么要倒序。

## 八、复盘：把每个模块问三遍

这场面试最大的感受：它不考你知道什么，考你能不能为自己的设计负责。

每一条追问都指向 **失败模式**：

1. 它在什么情况下会失效？
2. 失效了系统怎么知道？
3. 知道了之后能退回哪一步？

> [!success] 准备这类面试的方法
> 与其背方案，不如把每个模块都问自己三遍。这三个问题答得出来，设计才算你的。
