## 一、本质：本体是什么 / 什么才算本体

### 精准定义：区分标准本体与企业落地

> [!abstract] 本体是什么
> **本体（Ontology）是对某一领域中概念、关系、属性及公理的显式、形式化规格说明**，用于统一含义，并规定哪些结论可以从已有知识中推出。在采用本体建模的知识图谱中，它通常承担 **Schema / 语义层**的作用；知识图谱中的实体和事实则构成实例层。

标准语义网路线常用 **OWL** 表达本体，用 **Turtle** 等语法序列化本体和事实，再由支持相应语义的推理器推导隐含知识。**OWL 是建模语言，Turtle 是序列化语法，推理器是执行组件**；本体不必限定为 OWL，也不必以 Turtle 存储。

在 Palantir 等企业运行系统的语境下，可以进一步把本体理解为 **「一份可以运行的业务契约」**：将业务对象、状态、规则、动作和权限连接起来，让人和 Agent 的操作可执行、可验证、可追责。后文的企业落地标准主要讨论这一扩展语境；**动作、权限和写回不是所有标准本体都必须具备的定义条件**。

### RDF、OWL、Turtle 与推理引擎的分工

| 组件 | 是什么 | 负责什么 | 能力边界 |
|---|---|---|---|
| **RDF** | 图数据模型 | 用「主语—谓语—宾语」三元组表示资源与事实 | 复杂领域语义通常由 RDFS / OWL 等词汇表达 |
| **RDFS** | RDF Schema 词汇与语义 | 定义类、子类、子属性、属性定义域与值域等 | 可做基础类型与层级推理，表达能力比 OWL 有限 |
| **OWL** | Web Ontology Language，本体语言 | 表达等价类、不相交类、属性特征、基数限制等公理 | **OWL 2 DL** 采用描述逻辑式语义；具体推理能力取决于语言片段和引擎支持 |
| **Turtle** | Terse RDF Triple Language，RDF 的文本序列化语法，常用扩展名 `.ttl` | 把 RDF 三元组，以及映射成 RDF 的 OWL 本体写成可读文本 | 负责表示；自身不执行推理，也不是通用规则语言 |
| **推理引擎** | 执行形式化语义或规则的程序 | 从公理与事实推导新事实，检查逻辑一致性等 | 必须选择支持目标语义的实现；并非所有引擎都支持完整 OWL DL |
| **SHACL** | RDF 图的约束验证语言 | 检查必填、数量、类型、取值等数据要求 | 负责数据是否符合指定形状，与 OWL 逻辑蕴含的目标不同 |

同一份 RDF 图可以用 Turtle、RDF/XML、JSON-LD 等语法表示。只要解析出的图相同，并使用相同的推理语义，**换一种序列化格式不会改变逻辑结论**。

### Turtle 是什么，为什么看起来能用它推理

Turtle 用紧凑的文本写出 RDF 图：`@prefix` 声明命名空间，`.` 结束一组语句，`;` 复用主语，`a` 是 `rdf:type` 的简写。下面把本体公理和实例事实写在同一段 Turtle 中：

```turtle
@prefix :     <https://example.org/company#> .
@prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .

# 本体公理：员工是人的子类；汇报关系具有传递性。
:Person a owl:Class .
:Employee a owl:Class ;
    rdfs:subClassOf :Person .
:reportsTo a owl:ObjectProperty, owl:TransitiveProperty .

# 实例事实：Alice 是员工，向 Bob 汇报；Bob 向 Carol 汇报。
:Alice a :Employee ;
    :reportsTo :Bob .
:Bob :reportsTo :Carol .
```

解析器把文本还原为 RDF 图后，支持相应语义的推理器可推出：

```turtle
# RDFS 子类推理：员工属于人的子类，因此 Alice 也是人。
:Alice rdf:type :Person .

# OWL 传递属性推理：两段汇报关系推出一段间接汇报关系。
:Alice :reportsTo :Carol .
```

实际分工是 **Turtle 文本 → 解析为 RDF 图 → 按 RDFS / OWL 语义或已配置规则推理 → 得到隐含事实**。只解析文件不会自动产生这些结论；只启用 RDFS 推理也不会获得上述 OWL 传递属性结论。

> [!warning] 公理写错，结论也会错
> 示例中的 `reportsTo` 表示包含间接汇报的关系，因此可以声明为传递属性。如果业务含义是「直接汇报给」，就不能这样建模；否则会把 Alice 的间接上级 Carol 错当作直接上级。逻辑推理是否可靠，首先取决于关系含义与公理是否匹配。

### 推理机制与可靠性边界

**演绎推理**是在既定语义下寻找逻辑蕴含：若某个结论在满足公理和事实的所有解释中都成立，就称它被这些知识所蕴含。OWL 2 DL 推理器可进行类层级分类、实例归类、一致性检查等；其他实现也可能采用规则前向链、后向链等算法。**并非所有推理引擎都基于描述逻辑，OWL 公理也不等同于任意业务规则。**

- **Apache Jena** 是 RDF 处理框架，包含 RDFS 推理、通用规则引擎及覆盖部分 OWL 语义的内置推理器；其内置 OWL 推理器并不完整覆盖 OWL DL。
- **Pellet / Openllet、HermiT** 等属于 OWL DL 推理器路线。选型时应核对目标 OWL 版本、语言片段与实现支持，而不是只看「能读取 `.ttl`」。
- **自定义业务规则**需要额外的规则语言或执行机制。Turtle 可序列化映射为 RDF 的公理或规则描述，但不能自动执行任意规则；例如 Jena 通用规则通常使用其专用规则语法。

> [!note] 如何准确表达「确定性、可解释、不会幻觉」
> 对于固定且一致的知识、固定的语义与受支持的推理范围，逻辑蕴含由形式规则决定，**推理阶段不依赖大模型的概率生成**。这使结论有可核查的依据，但推导证明或解释仍需引擎支持并配置记录。
>
> 这不等于「结论一定符合现实」：错误事实、错误公理会推出错误业务结论；不一致知识库应先诊断冲突，推理器支持不足或超时也可能导致漏推。更准确的说法是 **「形式推理避免生成式模型式的自由编造，但不保证输入知识真实，也不保证所有实现都能完整推理」**。

OWL 通常采用**开放世界假设**：没记录某条事实，不等于它不存在。`domain` / `range` 主要支持类型推导，并不直接等同于表单校验；例如「订单必须显式填写供应商」应通过 SHACL 或应用校验落实，不能仅靠 OWL 的存在性公理检查缺失字段。

### 本体、知识图谱与向量库：互补，但不在同一抽象层

| 对象 | 核心作用 | 擅长什么 | 需要补充什么 |
|---|---|---|---|
| **向量库** | 存储向量并支持相似度检索 | 找语义相近的文本、图片或候选实体 | 相似度检索本身不提供显式关系路径和逻辑蕴含；多步 / 多跳能力需配合检索编排、图或规则 |
| **知识图谱** | 组织实体、属性与关系事实 | 精确关系查询、路径遍历、多跳检索，支持溯源 | 语义约束和演绎推理依赖其 Schema、本体及执行组件；图遍历本身不等于逻辑推理 |
| **本体** | 定义共享概念、关系含义及公理 | 统一语义，支持分类、逻辑蕴含与一致性检查 | 需要实例数据与推理器配合；业务完整性检查、动作执行还需验证器和应用机制 |

知识图谱可以采用本体，也可以只采用较轻的 Schema；**不能笼统说它「缺乏语义约束」**。向量库也可以参与多步检索系统；**不能把检索原语的局限等同于整个系统「无法多跳」**。采用本体的知识图谱中，本体可比作语义骨架，事实是填入骨架的数据，向量索引则补充模糊语义召回。

> [!tip] 三层口述版
> **定义**：本体是领域概念、关系、属性及公理的形式化规格说明，常作为知识图谱的语义层；企业运行系统可进一步将它扩展为对象、规则、动作和权限组成的业务契约。
>
> **机制**：用 OWL 等语言表达公理，用 Turtle 等语法序列化本体与事实，再由支持相应语义的引擎执行演绎推理；推理能力来自公理、语义和引擎，不来自 Turtle 文件格式。
>
> **对比**：向量库负责语义相似召回，知识图谱负责显式事实和关系查询，本体负责共享语义及逻辑公理。三者可以协作，推理结论的可靠性取决于输入知识与引擎能力。

### 两个极端判断（都过于省事）

| 极端 | 说法 | 问题 |
|---|---|---|
| 太宽松 | 「画了对象和关系、加了层 schema 就算完成企业本体落地」 | 未明确共享语义与公理，也未形成可执行的业务机制 |
| 太严苛 | 「没 OWL、没标准推理机就开除本体籍」 | 忽略了自研类型系统/规则引擎也能承担本体作用 |

### 真正的判断标准：语义能否成为机器契约

判断企业本体是否形成可运行的语义底座，不能只看文件后缀 / 格式 / 是否用了 OWL，还要看四件事能否稳定成立：
1. **明确含义** —— 同一业务对象在不同系统里是不是同一个意思
2. **稳定执行** —— 机器能稳定地依据它执行
3. **发现矛盾** —— 数据和规则冲突时，系统能发现并说明原因
4. **解释结论** —— 结论能解释依据、留下可追溯的证据

### 底层必须是「四层协作的语义底座」

| 层级 | 职责 | 回答的问题 |
|---|---|---|
| **形式语义** | 业务世界里什么是可能的 | 概念、关系、约束的定义 |
| **数据约束** | 眼前这份数据是否合格 | 字段必填、质量、范围 |
| **业务规则** | 当前场景下应该怎样处理 | 决策逻辑 |
| **权限与流程** | 谁能让行动真正发生 | 谁能批准/谁不能绕过 |

> 提醒：**用了 OWL 也不自动「毕业」**。OWL 是开放世界假设（没看到≠不存在），真实业务常要求「封闭世界 + 必填校验」，所以形式语义还需要配合 SHACL 数据约束、业务规则、权限与流程门禁。

## 二、本体的组成与落地三层架构

本体的核心建模要素是**类、关系、属性与公理**。在 OWL 中，关系通常用对象属性（Object Property）表示，字面值属性用数据属性（Datatype Property）表示；公理（Axiom）用于表达逻辑语义，与 SHACL 的数据验证约束应区分。

以 Oxygen 案例为参照，可将企业级落地拆成下列三层。TBox / ABox 是逻辑知识的划分，数据总线是工程组件；三者不是本体标准规定的必备架构。

| 层 | 角色 | 类比 | 存什么 | 具体作用 |
|---|---|---|---|---|
| **TBox**（术语盒 Terminology Box） | 语义定义 | 一部全平台统一的「商品规范手册」 | 类层级与类定义等术语公理；此处也将属性公理统称在内（严格区分时可称 RBox） | 为推理器提供语义依据；入站数据校验需配合 SHACL / 业务校验 |
| **ABox**（断言盒 Assertion Box） | 实例记忆 | 照着手册填进去的真实数据 | SKU、品牌、供应商、订单等**业务实例** | 存实体、记事实；多跳检索读它 |
| **ItemTunnel / 数据总线**（调度脊椎） | 调度分发 | 大脑指令靠它分发到全身，记忆更新靠它协调节奏 | 数据流转/版本/时效 | 分级调度、版本管控、统一收口全业务 |

> 类比总结：**TBox 是大脑，ABox 是记忆库，总线是脊椎**。没有脊椎，大脑和身体是断开的。
> 这套「TBox 定语义 + ABox 存实例 + 数据总线管调度分发」的三层范式，**Palantir 与京东同源同构**。

### 落地案例：京东 OxygenAICC（百亿级）

- 三层架构：TBox（人机协同持续演进：零售专家自顶向下定框架 + 算法自底向上挖新概念，三段式「发现→融合→验证」）+ ABox（属性维度已建成、关系维度是下一步）+ ItemTunnel（分级时效调度：离线/近线/实时三档；按「商品+属性」粒度锁版本，旧结果永不覆盖新结果；统一收口搜索/发品/推荐/治理）。
- 核心技术 **S²D（语义搜索-判别）**：先 TBox 定范围做语义检索召回 Top-K 候选，再判别模型在候选内精确匹配 → 精确率从传统自由生成的 <80% 压到 92%+，抑制大模型幻觉。
- 落地成效：搜索流量覆盖率 80%+、商品信息质量问题下降 37%、发品核心属性自动填充率 >80%、整体吞吐提升 10 倍。
- 理论源自京东技术论文（arXiv:2606.28070）。

> [!tip] Agent 前提下的本体
> Agent 准备下单时，系统能不能在**动作发生前**识别冲突？能不能说清**是哪条业务规则**阻止了这次操作？能不能找到**谁有权解除冻结、谁不能绕过**？这才是本体从一张关系图走向企业运行系统的关键一步。

### 另一条落地路径：数据中台 + 语义层 / 工具层 / 记忆层

不推翻现有 ODS / DWD / DWS / ADS，而是在其上补三层能力：

| 层 | 作用 | 关键设计 |
|---|---|---|
| **语义层** | 让 AI「看懂」 | 7+1 规范：实体 / 关系 / 事件 / 规则 / 指标 / 词表 / 模型 + 治理引擎；NL→DSL→SQL 准确率可达 98%+ |
| **工具层** | 让 AI「动手」 | 用 MCP 把指标查询、事件查询、知识检索封装成受权限控制的工具 |
| **记忆层** | 让 AI「越用越准」 | 业务规则 + 领域知识图谱 + 历史纠正；本体就是 Agent 的长期记忆 |
| **Harness** | 运行时框架 | Agent Loop + 权限控制 + 上下文管理 + Hooks；Agent = Model + Harness |

> **语义层是静态知识（什么是什么），工具层是动态能力（能做什么），记忆层是进化能力（学到了什么）。**
> 展开见 [[AI大模型/本体与知识图谱/本体论落地实践-从数据中台到智能中台|本体论落地实践：从数据中台到智能中台]]。

## 三、构建方法论：5 种方法（LLM 驱动的新范式）

传统建法（数据工程师与领域专家开无数个会、白板画图、手动映射扁平宽表为 Object/Link）按月计周期、业务一变牵一发动全身、面对非结构化数据无能为力。LLM 带来三大压倒性优势：

1. **非结构化数据的降维打击** —— 100 页 PDF 合同，一段 Prompt 直接提取结构化三元组，无需 500 个标注样本训 NER。
2. **零样本语义理解** —— 说明要提取的实体/关系类型即可，能理解「毛利率下滑」与「供应链中断」的潜在语义关联。
3. **隐性知识补全** —— LLM 基于预训练知识补全常识性关联（如「供应商在东南亚」→ 自动推断「有地缘政治风险」）。

### 两种幻觉 & 四种治理方案

**幻觉类型**：①无中生有（编造原文不存在的实体/关系）；②类型爆炸（同一实体不同批次叫不同名字，Schema 变浆糊）。

| 治理方案 | 做法 |
|---|---|
| **Schema-Guided Prompting** | 预定义 JSON 列表限定 Object/Link Type，严禁发明新类型 |
| **HTRO 降维拆解** | 不一次画整张图；先提实体，再两两配对喂 LLM 做二元判断，幻觉率降一个数量级 |
| **RAG + 证据溯源** | 每个关系必须附原文引用，点 Link 高亮原文，无出处直接丢弃 |
| **Human-in-the-Loop** | 人工终审；涉及真实触发动作的 Action 永远不让 LLM 单独定义 |

### 五种构建方法选型速查

| 方法 | 范式 | 核心思路 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|---|---|
| 纯人工专家驱动 | 自上而下 | 专家手工定义，OWL 格式（Protege） | 精准、逻辑严密 | 贵慢、难维护 | 航空/核电/医疗 |
| OntoKG | 自上而下 | Schema First，LLM 填空 | 精准无幻觉 | 无法发现未知 | 金融/合规/法律 |
| 聚类发现 | 自下而上 | Data First，HDBSCAN 聚类 | 冷启动神器 | 边界模糊噪音大 | 竞争情报/创新药 |
| LLM4Onto | 混合 | 实体涌现 + 亲和传播聚类 + HTRO | 自动推导高质量 Schema | — | 数字化初期/供应链重构 |
| 混合流水线 | 组合 | Phase1 人工定核心 → Phase2 LLM 提取 → Phase3 聚类补盲 → 持续迭代 | 生产级、知识飞轮 | 复杂 | 企业级落地 |

> 生产级原则：**LLM 做 80% 脏活，人做 20% 灵魂**。每次项目交付后新知识反哺回本体，飞轮持续转。

> [!tip] 动手前先过一遍清单
> 具体到「边界怎么定、实体怎么抽、层级方向怎么判、关系依据在哪、怎么验证」，见 [[AI大模型/本体与知识图谱/本体建模自检清单|本体建模自检清单]]；工程上怎么补语义层 / 工具层 / 记忆层，见 [[AI大模型/本体与知识图谱/本体论落地实践-从数据中台到智能中台|本体论落地实践：从数据中台到智能中台]]。

## 四、企业落地范本：Palantir（一套可学的顺序）

### 架构心智：不是记产品名，而是记落地顺序

```
1. 从具体业务决定出发 → 只连接需要的数据（垂直切片，非全域治理）
2. Ontology 定义对象、规则、动作、权限（四维集成：Data · Logic · Action · Security）
3. K-LLM 范式 → 同时用多个模型、随时可替换
4. Agent 调用受控工具，结果写回 ERP/MES 等业务系统
5. 补齐评测、监控、发布和回滚（Apollo）
```

### 两个常见误解

| 误解 | 正解 |
|---|---|
| Ontology = 知识图谱 | Ontology = 可以运行的业务契约（含动作、权限、写回） |
| Apollo = 算力/模型调度 | Apollo = 软件持续交付（发布、升级、监控、回滚、零停机，**不管 GPU**） |

### 关键机制

- **Ontology 决策内核**：四维集成 **Data · Logic · Action · Security**；三层 Language/Engine/Toolchain；**Kinetic（动能）**——动作是本体的一部分而非外挂，库存调拨/二次审批/替代物判断/下游联动都挂在对象上。**只统一名词、不定义状态变化、权限和写回 → 得到的是更漂亮的标签，不是 Ontology。**
- **K-LLM**：不把智能全压在大模型上，一个决定可同时调用业务规则、预测模型、优化器、LLM Function（`能用 K 模型的时候，不要只用一个`）。架构必须假设**随时能换模型**，所以把业务规则/动作边界放在模型外面。
- **Read-Write Loops**：人和 Agent 走同一套接口进 Ontology，收同一套权限；Action 旁必须有**幂等键、回执、补偿、审计、人工接管**；闭环不是把聊天记录塞回向量库，而是把决定和结果放回业务对象的历史。
- **Apollo（软件交付）/ Rubix（底座）**：Apollo 管版本发布/灰度/回滚；Rubix 是硬化的高可用 K8s 底座。对应国内谈「私有化/等保/信创/边缘」的对照物。
- **alpha vs beta**：成功的部署是企业在**追 alpha**——围绕自己差异化建设、把自身特殊性注入 Ontology，而不是买一个一刀切的 SaaS 基础方案（beta）。Offering 是可以自己造的。

### 中国企业的两轮九十天落地法

- **前九十天**：选一个高价值决定 → 接通最小数据点 → 定义对象/关系/状态 → 做出一个有人审批、能写回、结果可追踪的 **Action 闭环**。验收不看模型多聪明，只看业务有没有真的改变。
- **后九十天**：再加 Agent，按 K-LLM 假设介入至少两种可替换的模型。

> [!question] 自测：这套企业 AI 是否真正属于你？
> **如果明天更换大模型，业务对象、规则、动作、权限和历史还能不能留下？** 如果不能，可能只是一个更贵的 Demo。
> 配套两问：① 模型明天换掉，对象/规则/动作/权限/历史还在不在？（查 Ontology + K-LLM）② 能不能进我的隔离环境、升级失败能不能回滚？（查 Apollo + Rubix）

> [!tip] 想看产品内部机制
> Object Type 四步建模、Action Type 五步配置、OAG vs RAG、Workshop / Chatbot、前 FDE 的三个大实话 → [[AI大模型/本体与知识图谱/Palantir企业AI架构深度拆解|Palantir 企业 AI 架构深度拆解（Foundry · Ontology · AIP）]]。

## 五、速查表

| 术语 | 含义 | 类比 |
|---|---|---|
| TBox | Terminology Box，类/属性/关系/约束的规则模板 | 语义大脑 / 规则手册 |
| ABox | Assertion Box，填入真实业务数据的实例库 | 业务记忆 / 实体库 |
| ItemTunnel | 商品总线，分级调度 + 版本管控 + 统一服务收口 | 架构脊椎 / 数据总线 |
| S²D | 语义搜索-判别架构，先检索候选再判别筛选 | 抑制大模型幻觉 |
| RDF | 用主语—谓语—宾语三元组表达图数据的模型 | 事实表达底座 |
| RDFS | 类、属性及层级等基础 Schema 词汇与语义 | 基础类型 / 层级推理 |
| OWL | W3C Web 本体语言，定义逻辑公理与形式语义 | 语义建模标准路线之一 |
| Turtle | RDF 的可读文本序列化语法；可表示 RDF 化的 OWL 本体与事实 | 写数据的格式，不执行推理 |
| 推理引擎 | 按受支持的 RDFS / OWL 语义或规则推出隐含知识 | 公理 + 事实 → 逻辑结论 |
| SHACL | RDF 图的形状与数据约束验证语言 | 必填 / 数量 / 类型 / 取值校验 |
| Object/Link/Action Type | Palantir 本体的三大核心组件（实体/关系/写操作） | 数字孪生 |
| Kinetic | 本体的动能——动作内嵌为本体一部分 | 可执行的契约 |
| K-LLM | 一个决定同时调用多个模型、随时可替换 | 模型无关 |
