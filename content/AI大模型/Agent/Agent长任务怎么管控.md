# Agent 长任务管控方法论

> **定位：** 针对 Agent 在多步任务（如十几步行业调研）中「忘记目标」「跑偏方向」「重复调用工具」等失控问题，从架构层面给出的生产级管控方案。核心结论：长任务管理靠的是**三层能力 + 五道关卡**的架构机制，而非 prompt 优化。

---

## 一、失控根因：只有执行能力，缺乏管控能力

多数团队在做 AI 助手时只堆工具和提示词，缺少基本的工作记忆机制，导致十几步任务跑到一半就跑偏。一个完整的长任务体系必须包含以下三层能力：

| 层级 | 作用 | 缺失后果 |
|------|------|----------|
| **① 任务规划层** | 将大目标拆解为具有先后顺序、带有明确交付成果的具体步骤 | 任由模型想到哪儿做到哪儿，无结构化流程 |
| **② 状态记忆层** | 把每一步输入/输出、当前进度、中间结果全部结构化存储，形成可追溯的工作记忆 | 做到第七步就忘了第一步 |
| **③ 目标锚点层** | 每次推进新步骤前先回溯原始目标，确保方向不偏差 | 任务偏离，「自行加需求」 |

> **典型错误回答：** 只在 prompt 里多次调用目标工具、设置最大重复次数上限（最多三次），但不清楚中途模型「自己加戏」时的应对方案。

---

## 二、任务拆解：避免中途崩溃的三板斧

任务拆解不能依赖大模型自由发挥，工程实践中的成熟方案有三步：

### ① 分层拆解 — 逐层锁死边界

每个步骤的**交付成果必须清晰写死**，明确写清输入是什么、输出是什么、怎样才算完成，避免模糊描述（如仅拆成「查资料」）。
```text
示例（新能源行业研报任务）：
├─ Step1: 逐层检索行业数据
│    ├─ 输入：行业名称
│    └─ 输出：结构化数据集
├─ Step2: 交叉核验数据一致性
│    ├─ 输入：Step1 输出
│    └─ 输出：一致数据集
└─ Step3: 汇总生成研报
     ├─ 输入：Step1 + Step2 输出
     └─ 输出：正式报告文档

# 伪代码校验逻辑
def validate_step(step):
    assert step['out'] is not None, '交付物缺失'
```

### ② 依赖校验

步骤间的先后关系必须理清：有前置依赖的步骤不得提前执行。例如：数据未加载前，不得开始写报告（这类低级错误 Agent 确实会犯）。

### ③ 动态重规划

拆分并非一成不变：遇到**工具调用失败**或**信息不足**时，应允许 Agent 调整后续步骤的顺序或内容，而非一劳永逸地写死全流程。

### ⭐ 杀手锏：任务回滚机制
```bash
agent-ctl inspect --task-id 108
[FAIL] 步骤2 数据置信度低于阈值（62%）
```

某一步执行失败或结果不达标时，能**退回到上一个稳定的状态节点重试**，而不是从头来过。

## 三、执行监控：四项组合拳防跑偏

不会每轮都重复一次目标（浪费上下文窗口且易被中间对话稀释），需要同步推进四项工作：

### ① 目标锚定

将原始目标**永久留存**（不因上下文增长而被冲掉），每次执行新步骤前做一次目标对齐校验，评估是否与总目标相关；若不相关即刻叫停。

### ② 步骤合规检查

每完成一步自检三件事：

| 检查项 | 说明 |
|--------|------|
| 是否重复执行已做步骤？ | 检测冗余循环 |
| 是否超出任务边界做无关事项？ | 守住范围 |
| 是否擅自给自己加需求？ | 防止过度发挥 |

### ③ 关键节点自省

不是每轮自省（成本太高），而是在以下触发点自动反思：
- 子任务完成时
- 工具调用失败时
- 结果异常时

必要时调整后续路径。

### ④ 熔断保险丝（三道硬上限）

| 熔断维度 | 示例阈值 | 触发行为 |
|---------|---------|---------|
| 最大步骤数 | 30 步 | 强制终止 |
| 最大工具调用次数 | 50 次 | 强制终止 |
| 最大执行时长 | 300 秒 | 强制终止 |
```python
# 伪代码示意
if steps >= MAX_STEPS or calls >= MAX_CALLS or elapsed >= MAX_DURATION:
    abort(task_id)
```

## 四、工具调用治理：解决反复交叉与重复查询

这是长任务中最常见的翻车点。很多人只知道限制调用次数，没抓住本质——**工具管控和结果记忆缺失**。工程上做好三件事：

### ① 提前定义工具的注册表与参数校验

入参格式、取值范围、调用限制须显式声明，非法参数直接拦截。
```text
示例错误复现：
[T00L1] query_data(code='A01') → 成功
[T00L2] query_data(code='A01') → 重复查询！触发上限 max_calls=3 强制中断
```

### ② 做好调用结果沉淀（去重复用）

已检索的资料、已返回的工具结果必须全部**结构化存入工作记忆**，后续遇到相同需求**直接复用已有结果**，严格禁止重复调用。

### ③ 搭建失败降级链路

| 场景 | 处理策略 |
|------|---------|
| 工具调用失败 | 先重试 → 再换替代工具 → 简化参数后重新尝试 |
| 非核心步骤失败 | 直接跳过 |
| 注意 | 不能一报错就全盘终止 |

> **血泪教训：** 绝不能放任 Agent 自行判断何时使用哪个工具。必须把工具的**具体使用场景写成明确规则**，否则它会为了凑步骤数而反复调用同一工具，根本拦不住。

## 五、验收闭环：跑完 ≠ 完成

只做最终结果检查是不够的，需要进行**闭环验证**，通过三道把关：

### 第一道：目标把关
```python
def audit_long_task(trace, original_goal):
    # 1. 目标把关
    check_goal_alignment(trace.intent, original_goal)
    # 校验是否存在目标偏离
```

- 目标是否与原始需求一致？
- 过程中是否有偏离导致部分要求未完成？

### 第二道：过程合规把关
```python
# 2. 过程合规把关
assert not trace.has_redundant_steps()        # 无冗余步骤
assert not trace.has_unauthorized_ops()       # 无越权操作
return True
```

- 执行过程中没有冗余步骤、重复调用或越权操作。

### 第三道：结果质量把关

- 输出内容是否符合格式要求？
- 数据能否溯源？
- 结论是否有依据支撑？

### 补充：任务复盘机制（闭环关键）
```bash
agent-ctl review --dump-failed ./cases
agent-ctl optimize --rule=all
```

将所有**偏离、失败或超时**的任务统一沉淀为案例库，反过来优化：
- 任务规划规则
- 工具调用策略
- 自省触发机制

最终打造出同时具备**可观测性、可度量性与可迭代能力**的 Agent 系统。

## 六、速查表：面试官考察的三个维度

| 考察维度 | 内涵 | 反例（没做过的人） |
|---------|------|-----------------|
| **① 工程化思维** | 长任务管理靠的是**架构与机制**，不是 prompt 炼丹 | 「写好 system prompt 就能一劳永逸」 |
| **② 采坑经验** | 清楚知道任务会跑偏、工具会出问题，能说出具体的漏洞和解决方法 | 只关心如何让 Agent 跑完，不懂如何避免错误、防止跑偏、节省资源 |
| **③ 闭环意识** | 从规划→执行→校验→复盘全链路覆盖，做完更要确保结果正确并持续优化过程 | 做完就结束，没有复盘与反馈迭代 |

---

## 核心金句

> 没做过的人只关心怎么让 Agent 把任务跑完；真正做过项目的人才懂如何**避免错误、防止跑偏、节省资源**。
