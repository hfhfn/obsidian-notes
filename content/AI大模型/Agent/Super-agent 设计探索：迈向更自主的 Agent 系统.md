# Super-agent 设计探索：迈向更自主的 Agent 系统

## 一句话定位

当单任务 Agent 证明"模型会用工具"之后，**瓶颈从模型能力转移到人的注意力**：一个人同时只能跟进 3–5 个活跃 Session。本文提出 **Super-agent** ——把 Agent 从"单次手动会话"里解绑，变成跨会话保持上下文、并发推进多任务、持续在线的连续实体；并用五个模块（双层架构 / 事件驱动 / 面向人的交互 / 计算状态环境分离 / Watchdog）拼出它的系统架构。核心方法论不是新理论，而是**把计算机系统的经典工程思想（Fast/Slow Path、Cache、投机执行、存算分离、Control Loop）搬到 Agent 系统上**。

> 定位说明：这是一篇面向工程实践的**架构思路探讨**，不是 DeepSeek Harness 现有产品功能说明。部分设计已在 `dsh-superagent-prototype` 原型插件中实现，非正式产品。

## 1. 问题：为什么单 Session 撑不住

| 现状 | 后果 |
|---|---|
| Agent 以**单一 Session** 为基本单位，Session 之间彼此独立 | 并行多任务必须手动切换 + 自己记住各 Session 上下文 |
| 人的并发能力有限（实测约 3–5 个活跃 Session） | **单任务上限取决于模型能力，多任务上限取决于人的注意力** |
| 在本地单会话 Agent 上叠加 CLI / MCP / 连接器 | 仍受制于单会话同步阻塞、多任务上下文混乱、本地设备离线即停 |
| Session 同时承载"技术上的上下文管理"和"面向用户的项目管理" | 产品形态被底层实现绑架；让用户管 Session 是**从 LLM API 继承下来的设计惯性** |

## 2. 四个基础特征

| 特征 | 含义 | 对应架构模块 |
|---|---|---|
| **连续** | 在 IM、GitHub 评论等熟悉界面交互，感觉始终只有一个 Agent；不必想"Session X 里有没有 Y 信息" | 双层架构 + 全局 Router 记忆 |
| **高效** | 响应快，且能并行高质量完成多个复杂任务；不用等上一条完成才接下一条 | 双层架构 + 异步（全双工）ReAct Loop |
| **主动** | 不等逐条指令，持续观察环境事件并主动推进；不需要介入时保持安静 | 事件驱动（Trigger + 过滤 + 订阅直通 + 投机执行） |
| **持久** | 始终在线、接入真实工作环境、长期运行遇到异常能自愈 | 计算/状态/环境分离 + Watchdog |

关键判断：**单个 ReAct Loop 无法同时支持这四点**，底层必须有一套架构。相似的设计约束会导出相似的架构选择。

## 3. 双层架构：Router 层 + Worker 层

### 3.1 要解决的权衡

- **全部事件交给同一个 Session**：上下文最连续，但受单个 ReAct Loop 串行速度上限限制，耗时长、吞吐低，多任务细节混杂影响完成质量。
- **每条事件新开独立 Session**：并发吞吐最高，但任务间不独立时缺全局上下文、结果割裂，且多个 Session 各自回复用户造成混乱。

解法：把「维护全局连续性」与「高并发执行」拆到两层——常驻 **Router 层**统一承接人类交互与全局协调，上下文隔离的 **Worker 层**并发执行具体任务。

<div align="center">

![双层架构](Super-agent 设计探索：迈向更自主的 Agent 系统_图文/img_04.jpg)

</div>

> "双层"是**逻辑职责划分**，每一层内部都不必局限于单个 Session。

### 3.2 Router 层（常驻全局路由）

- 承接所有入口的人类交互，是全局的**序点（Sequence Point）、协调点和记忆**。
- 为不成为性能瓶颈，**不直接执行具体任务**、只做交互与分派，**甚至可以不配 Bash 工具**。
- 与常见 Agent Team 的区别：Agent Team 的 Team Lead 要深入理解任务细节、高频协调，推理负载重；Router 只处理**任务之间**的高层关联与分派，不介入单任务内部拆解 → **用较轻量的模型就够**。

**为什么单个常驻 Router Session 没有成为瓶颈：批处理（Batching）**

- 上一轮推理期间到达的 Trigger 会积压，在下一轮 LLM 调用中**一并注入**。
- Router 每步是**长输入、短输出**；多条 Trigger 合并进一次调用后在 Prefill 阶段并行计算，单次请求耗时增长**远慢于** batch 大小。
- 因此一定范围内：**积压越多，单个决定分摊的推理时间越低**。上限取决于上下文长度和模型单轮能准确处理多少条 Trigger。
- 规模再大时，Router 层内部可做多层过滤结构或水平切分（Sharding）——但**这就是又一轮连续性 vs 吞吐量的权衡**，切得越细吞吐越高、记忆连续性越低。在全局记忆问题解决之前，这个权衡始终存在。

### 3.3 Worker 层（隔离并发执行）

- 彼此上下文隔离，挂载**完整执行工具**，在独立上下文中专注单一任务；通常配**能力最强的模型**（直接决定任务结果与代码质量）。
- **不直接与人类交互**：推理过程与工具调用不输出到外部信道，只向 Router 汇报状态，由 Router 统一回复。
- 同层 Worker 通常不直接通信；冲突多发生在共享工作环境（如同一个 PR），靠"都订阅了该 Thread → 收到相同事件通知"来各自发现并解决，少数跨任务协同由 Router 中转。
- Worker 内部仍可再建 Subagent 或本身就是一个 Agent Team，对 Router 透明。

场景对照：

| 场景 | Router 层 | Worker 层 |
|---|---|---|
| 研发协作 | 分派 + 跨任务协调 | 同时推进问题复现 / PR 评审 / 特性开发，互不阻塞 |
| 个人助手 | 维持单一聊天页的交互连续性 | 对话框里每个话题各派一个 Worker 并行推进、起草回复 |

## 4. 事件驱动：一条 Trigger 的生命周期

驱动 Agent 的主要输入不再是人类逐条键入的提示词，而是环境中的**半结构化事件（Trigger）**：群聊消息、邮件与日程提醒、代码审查评论、CI 运行结果。四个递进问题对应四个机制：

### 4.1 事件过滤（3.1）——Fast Path / Slow Path

真实群聊与代码平台的事件流是典型的「**高噪音、低触发率**」，逐条调模型判断延迟与成本都不可接受。

| 层 | 角色 | 做什么 |
|---|---|---|
| 程序层策略 | **Fast Path**（低成本、低延迟、确定性） | 按事件来源、群组范围、用户/机器人白名单等确定性条件准入；对不同来源设"仅响应明确请求 / 作为候选 / 直接忽略" |
| 语义层策略 | **Slow Path**（高成本、灵活） | 对通过程序层准入的候选事件，由 LLM 按提示词策略 + 上下文判断是否需要行动；**同时是面向人类的自然语言扩展点** |

### 4.2 事件路由（3.2）——订阅与直通

如果每个后续事件都经 Router 转发，这个全局节点依然承受大量负载。定义 **Thread** = 同一个 GitHub PR、同一个 IM 话题或同一封邮件串下的连续事件流。

<div align="center">

![Thread 示例](Super-agent 设计探索：迈向更自主的 Agent 系统_图文/img_06.jpg)

</div>

| 路径 | 条件 | 处理 |
|---|---|---|
| **Fast Path（已订阅）** | Worker 创建后直接订阅该 Thread | 同一 Thread 的后续事件由程序**直通** Worker，不经 Router；超出任务范围时 Worker 可取消订阅或交回 Router 重派 |
| **Slow Path（未订阅）** | 尚未被订阅的新事件 | Router 仍可观测所有事件掌握全局，但只负责判断与分派 |

<div align="center">

![订阅与直通](Super-agent 设计探索：迈向更自主的 Agent 系统_图文/img_07.jpg)

</div>

- Thread ↔ Worker 订阅是**多对多**：一个 Worker 订多个 Thread，一个 Thread 可被多个 Worker 订阅 → 交集处的新事件同时直通给所有订阅者，**无需点对点通信**也能感知彼此操作、自行解冲突。
- 输出侧仍由 Worker 把关键结论汇报 Router，Router 统一回复用户并同步全局记忆。

### 4.3 上下文组织（3.3）——Inline & Spill + 链式召回

**"浪费上下文窗口，就是浪费模型的智能。"** 把有限的上下文窗口当作 **Cache** 管理：

| 操作 | 定义 | 场景 |
|---|---|---|
| **Inline** | 把近期很可能用到的信息直接内联进窗口，省去工具调用往返 | 附上紧密关联对象的 ID、内容前 50 字、IM 消息的前后相邻消息与所回复的消息、代码评论所在评审讨论的相邻评论 |
| **Spill** | 超出预算或低频使用的完整信息留在窗口外，只留引用或摘要，按需读取 | 长内容设较小长度上限，截断并保留**续读入口**，需要时再调工具读全文 |

优化顺序（借用局部性 Locality 思想）：

1. **从最少信息开始**：只给当前对象 ID 和内容摘要；
2. **利用局部性逐步 Inline**：先紧密关联对象 ID，再时空相邻内容；
3. **超上限则 Spill**：截断 + 保留续读入口。

**链式召回（Chain of Recall）**：系统给 Trigger、Thread、Worker Session 等对象唯一 ID，注入时内联下一跳关联对象的 ID，底层构成一张**引用图**；每次工具召回的结果本身也遵循 Inline & Spill，返回时又带上再下一跳的摘要与 ID，模型便能从当前事件顺引用关系**逐跳按需展开**上下文。例：当前消息 → 所在 Thread → 相关 Worker Session → 该 Worker 关联的另一个代码评审 Thread。这缓解了 Router 层在长程中丢失先前信息的问题。

### 4.4 提前行动（3.4）——投机执行

借鉴 **Speculative Execution**：在结果是否被采用还不确定时，先根据环境信号在后台尝试，用额外算力换人类的等待与介入成本。**有价值就交付，没价值就丢弃。**

- 个人助手：收到会议邀约/待办 → 后台核对日程冲突、搜集背景、备好回复草稿 → 用户过目即可确认。
- 研发协作：内部用户群配了"**静默复现并修复**"策略——有人反馈问题或讨论改动方案时，Agent 先在后台复现并找修复方案，**只有确认问题且找到简单方案才交付**，否则全程安静。

## 5. 面向人的交互

### 5.1 全双工交互（4.1）——异步 ReAct Loop

经典 ReAct Loop 中 `run()` 是同步阻塞的，工具执行期间会话无法响应任何新输入（半双工）。

改造：把耗时命令/子任务改为异步 `start()` / `stop()`：

1. 模型调 `start()` → 立即收到 **Started** 返回，循环不再等待；
2. 后台执行完成后，结果作为**一条新的事件消息**投递回会话；
3. 模型可用 `stop()` 主动终止跑太久的后台命令。

由此前台对话与后台执行解耦：新输入在**当前推理步结束后**即被处理，不必等后台工具完成。（该机制已在 DeepSeek Harness 实现，**尚未默认开启**。）

### 5.2 多信道交互（4.2）——输出要匹配信道带宽

把终端的交互方式原样搬进群聊（冗长推理 + 密集工具调用）在多人协作中必然信息过载。双层架构已把冗长过程隔离在 Worker 内部，再对每个信道用提示词定制规范：

| 信道 | 侧重 | 具体做法 |
|---|---|---|
| IM 等即时通讯 | 低打扰的轻量沟通 | 像人类同事一样只在需要决策或验收时通知；只问直接问题、给简短结论。**实测有效硬规定：单次回复不超过 100 词** |
| GitHub / 邮件 / 文档等异步信道 | 结构化、高信息密度的异步交付 | 按项目规范写完整的问题背景、改动说明与验证结果；个人助手场景直接起草结构化邮件与文档摘要 |

## 6. 计算、状态与环境的分离（存算分离）

本地 Agent 默认把「推进 Agent Loop 的计算」「需持久保存的会话状态」「代码仓库与本地工具链等执行环境」绑在一台设备上 → 休眠即停、访问不到其他设备的环境。分两步解耦：

**第一层：计算 ↔ 状态分离（5.1）**
Agent Loop 放进**云端无状态弹性容器**（可水平扩展、重启、替换），Session 等持久化状态存入**数据库**；连续性由持久化存储保障 → 摆脱单机生命周期，实现云端持久在线。

**第二层：Agent Loop ↔ 执行环境分离（5.2）**
模型所需上下文的很大一部分要通过工具调用从代码仓库、本地文件、依赖服务获取——**广义上下文包含执行环境本身**。

| 常见思路 | 为什么不行 |
|---|---|
| 云端起沙箱、拉代码、重建环境 | 真实环境含未提交修改、私有凭据、内网服务依赖、特定硬件/工具链，同步成本高且易遗漏 |
| 要求用户搬到云端工作 | 迁移成本过高 |

既然是环境本身难以复制，**就别让环境跟着 Agent Loop 上云**：Agent Loop 在云端，重状态执行环境留在原地，只在端侧部署一个**不保存会话状态的轻量 daemon**，只负责执行命令并返回结果。

- 与 Anthropic「**脑手分离**（Decoupling the brain from the hands）」思路一致（harness 无状态、会话日志存在 harness 之外、统一接口按需接入执行环境）。
- 差异在**场景**：那篇讲托管服务（按需沙箱、客户 VPC 内资源）；这里首先要接入的是**用户日常使用、可能间歇在线的个人机器**（有未提交修改和本地凭据）。
- 因此支持 **BYOM（Bring Your Own Machine）**，也支持接入云端托管机器或按需创建的计算环境；甚至能支持间歇在线设备——某台个人设备重新上线后，云端 Agent 再自动触发完成需要在该设备执行的任务。

## 7. Watchdog：主系统之外的外部控制回路

长期运行的分布式系统很难只靠主系统内部逻辑保证可靠，需要主系统之外的独立 **Control Loop**。

- 实现：主系统外配一个**独立的 Watchdog Session**，用定时消息驱动，构成外部 Control Loop。
- 职责一（基础设施）：接口报错、状态恢复失败等；
- 职责二（任务本身）：仅靠进程存活探测不够——很多异常不是崩溃，而是**模型陷入无效循环或偏离目标**。所以由模型判断各 Worker 是否有实质进展、方向是否偏离整体目标；发现异常及时介入，外部偶发故障持续复查直至恢复。
- Watchdog 本身也是具备完整工具能力的 Agent Session：维护者可以**用自然语言问它故障原因**，也可以让它**在线修正主系统行为**（增删提示词、调整触发规则）。

## 8. 初步实验

实验基于合成负载与简化环境，作者自称"部分设置还可以更严谨，结果仅作初步参考"。

### 8.1 消融实验（7.1）

设置：群聊 + GitHub CI 消息流同时驱动四种方案；单次实验约 **300 条消息**，其中约 **20 条是工作请求**，其余为闲聊、跟进、叫停和 CI 消息；编码工作用一个只消耗时间的工具代替（衡量**调度与协作能力**，而非单任务执行能力）；每种方案跑 5 次；消息间隔与工作时长按 1/4 缩放，模型调用耗时为真实值。

<div align="center">

![累计到达曲线与四种方案的累计完成曲线](Super-agent 设计探索：迈向更自主的 Agent 系统_图文/img_12.png)

![消融实验数据](Super-agent 设计探索：迈向更自主的 Agent 系统_图文/img_13.png)

</div>

| 方案 | 任务完成时间 P50 / P95（分钟） | 单次实验读缓存 Token（全部 Session） |
|---|---|---|
| **Super-Agent** | **12.4 / 15.7** | 2323 万 |
| Super-Agent，去掉直通 | 12.6 / 15.5 | 3177 万 |
| 单 Session + Subagent 工具，中性提示 | 20.4 / 29.5 | 605 万 |
| 单 Session + Subagent 工具，提示优先委派 | 13.8 / 29.0 | 1082 万 |

关键结论：

1. **带 Subagent 的单 Session 受提示词影响极大**：中性提示下模型 5 次运行**一次都没调用 Subagent**，全在主 Session 干、不断被新消息打断（P95 29.5）；改"优先委派"后 5 次中 4 次委派，但仍慢于 Super-agent，剩下 1 次判断工作"很小"而自己执行 → 形成长尾。**双层架构在系统层面缓解了"依赖提示词工程与模型临场判断分不分工"的问题**（Router 不直接干活、Worker 只收所订阅 Thread 的消息）。
2. **开销换稳定性**：Super-agent 维护多个独立会话，读缓存 token 高于单 Session（2323 万 vs 605/1082 万），是**用更多 token 换更短且更稳定的完成时间**。
3. **直通机制不改善质量，但省 Router 开销**：去掉直通后完成时间基本不变（12.6 / 15.5），但 Router 需做的决定**增加约 30%**，总读缓存 token 从 2323 万 → 3177 万（**+37%**）。

### 8.2 Router 层批处理压测（7.2）

设置：Router 调真实模型、Worker 用 Mock 模型；需要决定的 Trigger 到达速率从约 **1 条/分钟** 提到约 **40 条/分钟**。

| 指标 | 低负载（≈1 条/分） | 高负载（≈40 条/分） |
|---|---|---|
| 平均 batch 大小 | 1.0 | 2.8 |
| 单次请求耗时 | 2.5 s | 3.9 s（增长慢于 batch） |
| **单个决定分摊的推理时间** | **6.4 s** | **1.6 s** |

含义：事件突发拥堵时，Router 层靠**自动合并积压事件**提高有效吞吐；这也解释了 7.1 中即使去掉直通让 Router 峰值负载上升，仍未触及单 Router 的吞吐瓶颈 → **当前团队规模下无需过早水平切分而牺牲全局上下文连续性**。

## 9. 开放问题

| 编号 | 问题 | 具体张力 |
|---|---|---|
| 8.1 | **如何扩展双层架构** | 超出单 Router Session 承载时，何时水平切分、粒度如何、同层 Worker 何时需直接通信、用什么协作拓扑，均无定论；`Router 事件判别 / 分批派 / 上下文召回`的**模型与系统协同设计（Co-design）**值得专项训练。长程记忆是跨月运行的主要瓶颈 |
| 8.2 | **脱离 Session 后如何协作** | 底层会话不再对应用户界面会话后，如何向用户呈现任务与项目管理成为新问题；"以聊天窗口为中心"是路径依赖——交互可能更多发生在**领域特化界面**（如直接在 GitHub Issue/PR 里工作）；界面上保留的"一个会话"底层未必只有一个 Session。另外，模型能力过渡期内许多任务仍需人类**中途介入、接管、实时协同** |
| 8.3 | **上下文边界与 A2A** | 组织配备 Super-agent 本质是在**划分上下文共享/隔离边界**：需共享的共用同一实例，需隔离的各配一套。多个隔离实例之间（个人助手 ↔ 团队 Super-agent）的跨边界协同是 A2A 问题（不特指某协议） |
| 8.4 | **安全与隐私** | 事件驱动扩大了不可信输入面；云端 Agent Loop + 端侧 daemon 默认建立在"云与端互信"前提上，**一旦云端被入侵或提示词注入攻破，所连接的端侧设备都面临被控制风险**；即使云端未破，凭据一旦进入模型上下文就可能泄露 → 需要让 Agent **完全不接触凭据本身**也能使用凭据的机制 |

## 速查表：五个模块 ↔ 四个特征

| 模块 | 解决的问题 | 支撑的特征 |
|---|---|---|
| 双层架构（Router + Worker） | 连续交互 vs 高并发吞吐的权衡；Session 成为实现细节 | 连续、高效 |
| 事件驱动（Trigger / 过滤 / 订阅直通 / Inline-Spill / 投机执行） | 从"人给指令"到"环境给事件" | 主动 |
| 面向人的交互（异步 ReAct Loop / 多信道规范） | 后台耗时操作阻塞前台；输出不匹配信道带宽 | 连续、高效 |
| 计算-状态-环境分离（存算分离 + 端侧 daemon） | 单机生命周期限制、跨设备接入真实环境 | 持久 |
| Watchdog（外部 Control Loop） | 长期运行的基础设施故障与"模型跑偏" | 持久 |

术语对照：

| 术语 | 含义 |
|---|---|
| **Super-agent** | 跨会话保持上下文、并发多任务、持续在线的连续 Agent 形态及其系统架构 |
| **Trigger** | 环境产生的半结构化事件（群消息、PR 评论、CI 结果…） |
| **Thread** | 同一 PR / IM 话题 / 邮件串下的连续事件流 |
| **Fast / Slow Path** | 确定性代码快速准入 vs LLM 语义判断 |
| **订阅直通** | Thread 与 Worker 多对多订阅，后续事件由程序直达 Worker，不经 Router |
| **Inline / Spill** | 高概率要用的内联进窗口；低频或超预算的留在窗口外只留引用 |
| **Chain of Recall** | 对象间内联下一跳 ID 构成引用图，逐跳按需展开上下文 |
| **投机执行** | 后台提前尝试，有价值就交付、无价值就丢弃 |
| **全双工** | 异步 `start()`/`stop()`，后台运行期间仍可响应新输入 |
| **BYOM** | Bring Your Own Machine，把自己的开发机接入云端 Agent |
| **Watchdog** | 主系统之外的独立 Control Loop，兼查基础设施与任务进展 |

## 核心金句

> 单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

> Session 应当是系统的实现细节，而不应是用户的认知负担。

> 浪费上下文窗口，就是浪费模型的智能。

> 我们在当前阶段做出了一系列工程和场景简化——这套系统能以较低复杂度运作，很大程度上正是因为这些简化。

> 我们并没有提出全新的理论，而是将计算机系统中经典的工程思想应用到了 Agent 系统的构建中。

> Agent 不再只是一个被动等待指令的对话窗口，而是演进为数字环境中持续在线的自主协作者。
