# LangChain Loop Engineering 四层架构笔记

## 摘要

视频解读 LangChain 官方博客提出的 Loop Engineering 概念：让 Agent 从"偶尔能做事"走向"长期可靠地做事"，关键在于模型外围的 Harness 系统。作者将这套工程栈拆解为四层可堆叠循环——从最底层的工具调用，到验证、事件驱动，再到自改进的爬坡循环。

---

## 时间轴 · 画面与讲解

### [00:00–01:10] 核心命题：好模型只是起点

- **讲解**：Agent 可以查资料、改文档、跑测试、提交变更、写回业务系统。但让它偶尔做成一次不难，**长期可靠地做有价值的事**才难。
- LangChain 官方博客强调：一个 Agent 能否进生产环境，取决于模型外面有没有一套为任务设计的 **Harness**（工作系统）。
- Harness 负责：给上下文、接工具、定边界、检查结果、处理失败、必要时把人叫回来。
- 画面：手绘风格办公桌面，机器人操作电脑；中央流程图含四个模块（上下文 → 工具 → 结果 → 人工审阅），以箭头连接。

---

### [01:10–02:31] 第一层：Agent Loop（工具循环）

- **讲解**：最小的循环。系统把任务和上下文交给模型 → 模型决定是否调用工具 → 工具返回结果 → 模型继续思考/调用 → 直到判断任务完成。
- 以 LangChain 文档 Agent 为例：读取需求 → 规划修改 → 克隆代码仓库 → 打开文件改文档 → 创建 Pull Request。
- **关键**：模型被放进一个可以行动的环境，真的去读写文件、提交变更，而不只是"告诉你怎么改"。
- 这一层是后面三层的基础，没有它 Agent 只是一轮问答。
- 画面：循环流程图，标号 1–5：需求 → 工具调用 → 返回结果 → 继续决策 → 任务完成，形成闭环。

---

### [02:31–04:27] 第二层：Verification Loop（验证循环）

- **讲解**：在 Agent 完成一次任务后加一个**校验器（Grader）**。
  - 校验器可以是确定性脚本，也可以是另一个模型扮演的评审。
  - 拿着明确标准检查输出：链接能否打开、CI 是否通过、Diff 范围是否合理、文档是否覆盖该解释的内容。
  - 不通过时，系统把失败原因带回给 Agent，让它再修一轮。
- **Grader 的角色**：不负责写主要答案，只负责根据规则判断结果够不够格。
- **两个前提**：① 标准要清楚；② 错误反馈要能指导下一轮修改。若标准只是"看起来不错"，模型裁判容易给出漂亮但无用的评价。
- **代价**：增加单次运行的延迟和成本（token 和时间都上去），随手试验可能不值得，但在生产场景通常值得。
- 画面：四步循环图——标准 → 检查（CI/链接/Diff）→ 反馈（失败原因+建议）→ 重试，箭头闭合。右侧堆叠三本书分别标注"规范""测试""指南"。

---

### [04:27–06:26] 第三层：Event-Driven Loop（事件驱动循环）

- **讲解**：前两层解决"一次任务怎么跑、结果怎么验"；这一层解决"**谁来启动它**"。
- 很多 Agent Demo 停在手动触发（打开界面输入任务），适合演示和个人工具，但离业务系统还差一步。
- 生产环境里，任务往往来自外部事件：
  - 新文档请求进来
  - Webhook 被触发
  - 计划任务到时间
  - Slack 频道有人发消息
- LangChain 文档 Agent 的例子：监听一个专门收文档请求的 **Slack 频道**，有人在频道里发请求，频道就触发 Agent 执行；Cron 和 Webhook 也能承担类似触发。
- Agent 从一个"被临时调用的脚本"变成系统里**长期运行的组件**。
- 事件发生后，系统启动前面的 Agent Loop + Verification Loop；完成后把结果写回业务系统或交给人审批。
- 画面：流程图分三区——左侧"事件来源"（Slack / Webhook / Cron / 业务系统）→ 中间"Agent 工作流"（理解事件 → 分析决策 → 工具执行 → 生成结果）→ 右侧"文档/知识系统 + 审批队列"。底部标注"监控·日志·重试·告警"。

---

### [06:26–07:50] 第四层：Hill Climbing Loop（爬坡循环）

- **讲解**：前三层让 Agent 自动工作；第四层让系统**根据运行记录改进自己的工作方式**。这是原文最重要也最容易被讲浅的一层。
- **Trace（轨迹日志）**：一次 Agent 运行留下的完整记录，包括模型看到的上下文、调用过哪些工具、工具返回了什么、校验器给了什么反馈、哪一轮失败/通过。单看是调试记录；把很多 Trace 放在一起，就成为系统改进的信号。
- 做法：让一个**分析 Agent** 去看这些 Trace：
  - 看这一次为什么失败
  - 寻找重复出现的**系统性问题**（如：总是漏掉某类 API 参数说明、总在同类 CI 检查里失败）
- 发现模式后，系统可以创建 Issue，要求修改：
  - 基础 Prompt
  - 工具配置
  - 验证规则
  - 对开源权重模型，运行结果还可成为**强化学习微调**的信号
- 记忆和检索到的 Skills 也可以用类似方式优化。
- **本质**：把"复盘制度"产品化——过去团队每周看一次失败案例，现在由系统在循环中持续自动完成。
- 画面：复杂流程图展示完整爬坡循环：收集 Trace → 聚合分析找出失败模式（缺少参数说明 42%、幻觉引用 28%、遗漏边界 18%、格式不规范 12%）→ 改 Prompt / 改规则 / 升级 Grader → 回到内层循环重新运行 → 评分提升 → 持续迭代。图中还展示具体数字：通过率 42%→68%，平均得分 0.46→0.71，幻觉率 28%→12%，时延 9.3s→6.1s。

## 四层架构总览

| 层级 | 名称 | 核心问题 | 关键机制 |
|------|------|----------|----------|
| 1 | Agent Loop | Agent 怎么行动？ | 模型 ↔ 工具循环，直到任务完成 |
| 2 | Verification Loop | 结果怎么验？ | Grader 按标准校验，失败反馈让 Agent 重试 |
| 3 | Event-Driven Loop | 谁启动 Agent？ | 接入 Slack/Webhook/Cron 等真实事件入口 |
| 4 | Hill Climbing Loop | 怎么持续变好？ | 收集 Trace → 分析失败模式 → 改进 Prompt/工具/规则，自动迭代 |

## 08:05–08:50｜复盘信号与四层循环的体系定位

**讲解**

总结为什么 agents 又改错了文档？Hill climbing loop 希望把这个复盘变成持续发生的系统动作——每一次运行都留痕，很多次运行形成信号，信号推动 harness 改动。

把这几期内容放在系列坐标里看：
- **Agent Harness 那期**：大框架，解释模型之外还有 prompt、tools、memory、hooks、evaluation 和运行编排。
- **Coding tools 那期**：spec 和验收标准，回答"验证循环的标准从哪里来"。
- **Codexmaxxing 那期**：长期工作系统和事件驱动循环关系很近。
- **Harness 那期**：从代码评分和失败记录反过来改 harness，和第四层爬坡循环最接近。

Line Chain 这篇文章的价值是把分散主题压成了一个更易落地的**四层顺序**：先让 agent 能调用工具做事，再让结果能被验证，再让系统能被事件唤醒，最后让运行轨迹推动系统自动优化。它和前面这些内容的关系更像是系列坐标的补充。

**画面**

手绘风格信息图/地图：中心岛屿标注"Loop Engineering"，四周分布四个编号模块（Agent Harness / SPEC 验收 / Codexmaxxing / Meta Harness），各模块内含流程图与图标，周围点缀指南针、机器人、木船、宝箱、书本、咖啡杯等元素。屏内文字包括"系列坐标""通过循环工程，把不确定变成可控，把一次性成功变成持续的系统能力""迭代与进化"等。

## 09:02–09:50｜人机协作：人留在关键点

**讲解**

给 agent 工程画了一张执行地图后，再说人类介入。Loop engineering 容易让人联想到全自动系统，但 LangChain 原文的态度很明确：**自动化需要把人放在最需要判断的位置**。

在 agent loop 里，以下几类敏感工具调用应该要求人确认：
- 数据库写操作
- 资金交易
- 权限变更

在 verification loop 里：
- 链接是否能打开，可以交给脚本
- 面向客户的叙事是否合适，很多时候仍然需要人判断

在事件驱动循环里：
- agent 生成的结果可以先进入审批队列，再同步到业务系统

在 hill climbing loop 里：
- 系统建议改 prompt、改工具、改验证规则，也应该经过人审再上线

**机器适合做高频、标准化、可重复检查的工作；人适合做价值判断、风险判断和语境判断。**

**画面**

办公场景流程示意图：左侧机器人坐桌前使用电脑，中间人物依次在"敏感操作""客户表达""上线审批""规则改动"等环节（均标"审批通过"），下方"自动跑通（持续验证与反馈）"子流程含检索信息、生成内容、校验检查、评估打分、反思改进等步骤。屏内核心标语："人要留在关键点，自动跑通全流程""人把关关键处，稳得住才能跑得快""人机协作，持续进化！"

## 10:04–11:20｜Loop Engineering：从标签到工程习惯

**讲解**

Loop engineering 听起来新，但它真正有用的地方在**工程拆解**。

很多团队做 agent 时，模型偶尔能把任务做出来，但系统没有回答清楚几个后续问题：
- 做完之后怎么知道对不对？
- 失败之后怎么重试？
- 任务怎么自动进入系统？
- 长期问题怎么被发现并修掉？

Line Chain 这篇博客给出的**四层循环**正好把这四个问题摊开了：

| 层级 | 核心能力 | 工程意义 |
|------|----------|----------|
| 第一层 | 让 agent 能行动 | 解决"怎样做" |
| 第二层 | 让行动结果被检查 | 解决"怎样验" |
| 第三层 | 让 agent 进入真实业务环境 | 解决"怎样触发" |
| 第四层 | 让运行记录变成改进信号 | 解决"怎样改进" |

只看第一层，agent 很容易停在 demo；加上第二层，开始接近可靠工具；加上第三层，才像一个可以放进组织流程的服务；到了第四层，团队开始真正管理 agent 的长期质量，减少每天手工修同一种错误的消耗。

比起记住"四层架构"这个标签，更值得记住的是一个**工程习惯**：
- 少一点追问模型下一句该怎么答
- 多一点设计系统：怎样做、怎样验、怎样被触发、怎样从失败记录里改进

AI 工程师接下来要写的，可能越来越少是单个 prompt，越来越多是围绕**任务、标准、事件和日志**搭起来的循环。

**画面**

工程仪表板界面：显示"工程习惯 / 最终清单"，当前循环状态"运行中 Step3/6"，指标看板（耗时 2m34s、成功率 92%），运行日志节选（任务生成→工具调用 search_docs→结果不完整重试→验证通过→进入下一步），任务看板（待办/进行中/已完成），改进记录与下一步计划。屏内核心标语："把每一次循环，变成可控、可验证、可改进的系统能力""好习惯，让 Agent 越跑越稳！"
