# L3-18-06 沙箱隔离：让 Agent 的危险操作套上防护罩

> [!abstract] 摘要
> 本章解析 AI Agent 执行代码、操作文件、访问网络时的**三大安全风险**，对比**容器隔离 / WebAssembly / 进程隔离**三种主流沙箱技术的原理与取舍，并给出基于**目录挂载、网络白名单、资源上限**的最小权限设计方案，助力 Agent 项目从实验态平稳过渡到生产级。

---

## 一、为什么需要沙箱隔离？

> [!warning] 核心比喻
> 没有沙箱保护的 Agent，等同于**「没有安全培训的实习生拿到了全公司系统的最高管理员权限」**——出事故只是时间问题。

沙箱是系统兜底的**安全网**：即使 Agent 在执行环境内部失控，破坏力也被严格限制在局部，绝不波及宿主机与外部网络。

### Agent 三大高风险操作与威胁

| 风险维度 | 典型威胁表现 | 风险等级 |
|---|---|---|
| **代码执行** | 恶意逻辑（如 `rm -rf /`）、无限循环耗尽 CPU/内存、读取并窃取敏感数据 | 极高 |
| **文件操作** | 误删重要系统/业务文件、覆盖篡改配置、越权读取机密数据 | 高 |
| **网络访问** | 内网探测、未授权伪造身份调用敏感 API、被利用当跳板发起 DDoS | 高 |

---

## 二、三种主流沙箱技术对比

| 技术 | 原理与机制 | 优势 | 短板 | 适用场景 |
|---|---|---|---|---|
| **容器隔离**（Docker/K8s） | 独立文件系统、网络与进程空间，无法直接访问宿主机 | 隔离性强、生态成熟、最标准的生产级方案 | 启动慢（秒级）、资源开销较大 | 企业级 Agent 系统、需完整环境隔离 |
| **WebAssembly**（WASM） | 模块在隔离环境中运行，线性内存、无直接 I/O，天然安全沙箱模型 | 启动极快（毫秒级）、内存占用小、零额外开销、代码默认无法触碰宿主机 | 支持语言有限、隔离粒度较粗 | 高并发/海量请求、模型侧推理、对启动速度敏感 |
| **进程隔离**（seccomp/AppArmor） | OS 级轻量隔离，共享内核，通过受限系统调用限制文件/网络访问 | 几乎无额外开销、性能敏感 | 共享内核、隔离力度相对较粗 | 性能极致敏感、轻量级快速迭代 |

### 典型配置示例
```text
# 容器隔离示例
image: python:3.11-slim
cpu: 0.5 | memory: 512Mi
network: none

# WASM 编译执行示例
WebAssembly.compile(code)
instantiate(module, env)

# 进程隔离示例（seccomp / AppArmor）
seccomp --filter "read,write,open,close"
AppArmor profile
read_only_root: true
```

### 实战趋势

- 多数企业因业务推进效率，仍以**容器隔离**为默认首选。
- **WASM** 正迅速崛起，在 YC 等创新团队与模型侧广泛应用。
- **进程隔离**适合极轻量、强性能诉求。

## 三、文件系统沙箱设计（最小权限）

**核心原则**：Agent 只能看到必须看到的内容，只能修改必须修改的内容。

**关键机制**：目录挂载（按需暴露）+ 权限精细控制 + 无痕清理。

### 挂载策略示例

| 宿主机路径 | 沙箱内路径 | 权限 | 说明 |
|---|---|---|---|
| `/projects/workspace/agent-workspace` | `/workspace` | `rw` | 工作区，可读写 |
| `/shared/datasets` | `/data` | `ro` | 数据集，只读防篡改 |
| `/tmp/agent-output` | `/output` | `rw` | 临时输出 |
| `/etc`, `/home` | — | 不可见 | 系统核心目录完全隐藏 |

### 无痕清理（临时文件系统）
```bash
mount -t tmpfs -o size=100M tmpfs /sandbox/tmp
```

将 Agent 临时操作映射到内存文件系统，沙箱销毁后自动清理，**零残留**。

## 四、网络隔离：三种模式

| 模式 | 安全等级 | 说明 | 适用 |
|---|---|---|---|
| **完全隔离** | 最高 | 彻底切断所有网络访问 | 纯计算/推理任务 |
| **白名单模式** | 中 | 仅允许访问指定域名/IP | 需调用已知 API 或公司内网，**最实用的默认配置** |
| **代理模式** | 中高 | 所有请求强制经代理转发，统一审计、过滤、留痕 | 需全量访问可追溯 |

---

## 五、资源限制

- **核心指标**：CPU 核心数、内存上限、磁盘配额、执行超时时间、进程数量、文件句柄数——均需**严格封顶**。
- **落地原则**：最小权限——只给 Agent 完成任务所需的最小资源与权限，不多不少。
- 一个没有资源限制的 Agent，对底层基础设施而言**无异于随时引爆的定时炸弹**（如内存被打满、CPU 挂掉）。

---

## 六、落地核心要点（5 条）

1. **代码执行必须进沙箱** — 即使信任的 Agent 也可能产出有 bug 或危险的代码；沙箱是抵御风险的最后一道防火墙。
2. **首选容器隔离技术** — 在云端独立环境跑 Agent、隔离宿主，简单、标准、生产级。
3. **网络访问默认拒绝** — 遵循默认拒绝原则，仅当确有需要（如 Web Search / Web Fetch）才放开并可控。
4. **严格设定资源上限** — 对 CPU/内存/磁盘/执行时间设硬性限制，实时监控且可控。
5. **全量记录审计日志** — 记录沙箱内一切操作，是安全审计与问题排查的「眼睛」。

> [!note] 一句话理解
> 沙箱就是 Agent 的**「安全手术室 / 银行的保险柜」**：你可以在里面自由处理，但物品种类受限、时间全程监控、绝不波及外部世界。
> 进阶方向：**工具执行链**（多次工具调用管理、工具注册、参数校验、结果解析）。
