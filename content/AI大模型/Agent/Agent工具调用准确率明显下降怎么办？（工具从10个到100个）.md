# 面试官：Agent调用准确率明显下降怎么办？（工具从10个到100个）

> [!abstract] 摘要
> 工具从 10 个膨胀到 100 个时，调用准确率下滑的根因是**上下文信噪比骤降与决策空间超限**；解法是「向量检索预筛 + 工具描述治理 + 按场景动态挂载」，并用结构化评测闭环验证效果。

## 主题定位
当 Agent 工具从十几个膨胀到上百个时，调用准确率下滑的本质是**上下文信噪比骤降与决策空间超限**。破局点不在堆砌提示词，而在重构流程：通过向量检索预筛收窄候选集、通过工具描述治理划定互斥边界、结合场景化动态挂载保障组内协同。

---

## 一、问题根因诊断

### 现象对比：10 工具 vs 100 工具

| 维度 | 10 工具阶段 | 100 工具阶段 |
|------|-------------|--------------|
| 描述总长度 | 几百 token | 数千 token |
| 模型处理状态 | 可快速扫完，区分度高 | 注意力被稀释，极易混淆 |
| 相似工具差异 | 字面差异明显 | 如「查订单状态」与「获取订单详情」相似度高达 **0.91~0.92** |
| 决策难度 | 轻松 | 从 10 个选项里挑很容易，从 100 个里挑会看花眼 |

### 本质归因
信号强度不变，噪声随选项数线性放大。这是**决策空间过大的通病**，而非模型变笨。

问题出在流程设计：将「理解用户意图」与「从百个工具中挑选」两件事硬塞进同一个 Prompt 让模型串行执行，超出了其有效处理能力。

---

## 二、核心解法框架

提升准确率的关键不是加长提示词，而是改变挂载策略：**从全量并列挂入，改为先检索、再动态挂载相关工具**。

采用三层叠加方案：
```
100个工具 → [向量检索] → Top-K(5~10) → [工具治理 + 场景分组] → 最终选择 1 个
```

---

## 三、方案一：向量检索预筛选（Tool Retrieval）

### 实现路径
参考 RAG 架构：
1. 将所有工具描述进行 Embedding 并向量化入库
2. 用户提问时，先用 Query 检索向量库
3. 召回 **Top-K（通常 5~10 个）** 最相关工具
4. 交由模型在精简集合中完成最终选择

### 关键细节：工具描述的双重视角
工具描述不能只写给 LLM 阅读，**必须同时适配检索器的召回逻辑**。需显式写明：
- 该工具能解决什么问题
- 什么业务场景下使用（when-to-use）

仅写功能字面会导致检索召回失准。

### 边界缺陷：无法消灭相似混淆
若两个相似工具与 Query 的语义相似度均极高，检索步骤会将它们**一同召回**。候选集缩小后，模型依然面临二者二选一的困境。此缺陷需依靠工具治理层补齐。

---

## 四、方案二：工具治理（合并与互斥边界）

### 重叠工具处理
能合并的直接合并，通过参数分化用法。

### 并存工具的互斥条件写法
将「何时触发 / 返回什么」写成**互斥条件**，强制模型依据明确边界做区分。

> *示例*：
> - 「查订单状态」明确限定：`仅需知晓订单所处环节 → 仅返回状态枚举`
> - 「获取订单详情」明确限定：`需完整收货人/金额/商品清单 → 返回全量子段`

**总结**：检索解决「找得全」，治理解决「分得清」，两者必须配套使用。

---

## 五、方案三：按场景动态挂载（分组策略）

### 背景
部分工具天然归属同一业务流，跨组工具混杂会引入无关干扰。

### 实现方式
预先按业务域分层分组：
- 电商场景拆分为：订单组、售后组、用户组
- 开发场景拆分为：代码组、部署组、日志组

### 执行流程```
轻量意图分类器（粗粒度场景判定）→ 挂载对应场景的子集工具 → 模型在子集内选型
```

### 收益
同时满足「控制单次输入规模」与「保障组内协同」，杜绝无关工具（如退款流程中莫名插入「发微博」工具）污染上下文。

### 意图分类的风险与兜底机制

**单点故障隐患**：分类器一旦判错，正确工具将彻底缺席候选列表，模型无解。这比"选错"更严重；跨场景复合需求同样会被卡死。

**双重兜底设计**：
1. **向量检索兜底**：无论分类结果如何，始终保留全量工具检索通道，防止漏召
2. **置信度兜底**：当分类置信度低于阈值时，自动并行挂载相邻场景组的工具，为错误留出回旋空间

---

## 六、认知纠偏：MCP 不是选型问题的解药

### MCP 的真实定位
Model Context Protocol 是工具**接入层**协议，通过 MCP Server 将数据库、内部系统、第三方 API 统一暴露为标准接口，解决的是"如何连接"的工程问题。

### 规模反噬
MCP 极大降低了接入门槛，导致工具数量呈指数级增长，反而放大了上层的选型难度。

### 核心结论
接入归接入，选择归选择。MCP 与工具路由策略属于不同抽象层级，需协同设计，不可互相替代。

---

## 七、效果验证：建立结构化评测闭环

### 测试集准备
沉淀数十条带标注的真实问题（明确记录标准调用工具）。

### A/B 对比实验
| 组别 | 方案 |
|------|------|
| 对照组 | 全量挂载所有工具 |
| 实验组 | 检索 + 动态挂载 |

### 双指标监控
1. **端到端工具选择准确率**：模型输出与标注答案的一致性
2. **逐题回归（Regression）**：重点排查原全量方案答对的样本，在新方案下是否出现准确率倒退

### 检索层独立评估
单独计算**召回率**（Ground Truth 是否落入 Top-K）。

- 若召回偏低：优先优化工具描述的 Embedding 质量，或适当调大 K 值（如 5→10）
- **延迟权衡**：K 值上调可改善召回与准确率，但同步推高首 token 延迟，需按线上 SLA 综合权衡

---

## 八、架构取舍与演进建议

- **非银弹属性**：工具总量仅在个位数（如 5~6 个）时，全量挂载是最优解；强行叠加检索链路只会徒增推理延迟与故障节点
- **规模阈值**：工具检索化与动态挂载是为**数十至上百个工具**的规模化阶段准备的防御架构
- **工程原则**：尽早建立包含端到端准确率与回归指标在内的评测闭环，以数据驱动迭代
