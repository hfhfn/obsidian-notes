# Anthropic Agent 产品设计新范式

> **来源**：抖音图文 · 发布时间 2026-09-05 · 阅读约 9 分钟
> **主题**：Anthropic 9 月 2 日开源的 AI Native Agent ToB 电商项目（Commerce Agents）对 Agent 产品设计的借鉴
> **对象**：Agent 开发者 / 产品经理 / 架构设计者

---

## 一句话总结

> **设计 Agent，先确定"谁负责完整任务"，再决定需要多少个 Agent。** 模型负责判断，确定的规则与流程交给代码；Harness 把模型每一次判断都落到可靠的执行过程上。

---

## 核心背景

Anthropic 开源了一个 AI Native 的 ToB 电商项目（**Commerce Agents**）。它的设计把产品设计重点从「要拆几个 Agent」转向「**如何让一个 Agent 可靠地完成任务**」：

- **Harness** 管理上下文和工具调用，
- **后端**承接真实业务操作，
- **模型**只负责其中需要判断的部分。

下面是从该项目中提炼的**七条值得借鉴的设计**。

![[AI大模型/Agent/Anthropic-Agent产品设计新范式_assets/img_01.jpg|配图 · Commerce Agents 产品架构]]
> 官方实现简化的架构图：**模型**负责推理与选择工具；**Harness** 管理上下文·循环·工具调度；**Skills / Tools** 承载领域能力；购物 Agent / 经营 Agent 作为服务消费者。

---

## 七条值得借鉴的设计

### 一、尽量少用 SubAgent，先让主 Agent 拥有完整任务

需要共享**大量信息**的任务，优先交给同一个主 Agent。

- **例**：商家问「这批商品降价 15% 后，库存够不够支撑需求？」——同时涉及定价和库存。若拆给两个 Agent，各自答对一部分，却没人结合库存判断降价方案。
- 业务能力可以**分模块维护**，不必每模块都配一个 Agent。领域分工用 **Skill / 工具**保留（如定价团队维护定价工具和流程，主 Agent 按需使用，而不是让一个"定价 Agent"接管会话）。
- **何时才该用 SubAgent**：看是否需要**独立上下文**，或需要**完整移交任务**。
  - 深度研究 → 独立上下文：探索多，只向主 Agent 返回简洁结果，主 Agent 继续负责整体结果。
  - 专业服务 → 移交会话：已有独立专业 Agent 接手用户并完成任务。
- **判断准则**：仅仅多一项业务职能，**不足以**成为拆分理由。委派时由 Harness 明确子任务的**输入、工具权限和返回结果**。

![[AI大模型/Agent/Anthropic-Agent产品设计新范式_assets/img_02.jpg|配图 · 少用 SubAgent 决策树]]
> 任务归属三条件：**共享信息多** → 主 Agent + Skills/Tools；**需独立探索** → 委派子任务返回简洁结果；**专业服务完整接管** → 移交会话。反复交接会累积信息损失与等待成本。

---

### 二、经常用的工具，直接放进 System Prompt

**三分之一及以上请求**会用到的指令，优先放进 System Prompt（Skill 加载通常要多一轮模型交互，反复加载增加等待）。

- **例**：购物助手经常要搜索商品 → 搜索原则常驻；复杂选购研究、目标规划等低频流程 → Skill 按需加载。常驻的是**工具的使用说明**，参数定义和实现代码仍放工具层。
- 能从**用户入口**判断需要什么的，就由 Harness **提前准备**：用户从商品详情页打开助手，系统已知当前商品；从商家活动看板进入，系统已知当前活动——可在第一次模型调用前注入，免得模型先判断读什么、再发加载请求。
- **关键内容**（安全要求、品牌约束、过敏信息等）必须放 System Prompt，**不能只按频率取舍**。

**放哪里的判定**：
| 场景 | 放哪里 |
|---|---|
| 高频基础规则 | System Prompt |
| 低频但入口明确的流程 | Harness 提前加载 |
| 低频且无法预判的流程 | Skill 按需读取 |

三分之一是官方起点；常驻太多增加上下文负担，拆太碎增加加载轮次，最终按真实请求分布和评测调。

![[AI大模型/Agent/Anthropic-Agent产品设计新范式_assets/img_03.jpg|配图 · 指令放哪里]]
> 分配规则按「频率 + 可预测性」：高频使用说明常驻 System Prompt；入口可预测的低频流程由 Harness 提前加载；无法预判的才用 Skill 按需读取。常驻的是使用说明，参数与实现仍在工具层。

---

### 三、核心是 Harness 的设计，工具操作必须经过检查

- **模型负责提出调用，Harness 决定能不能执行。**
  - **例**：用户连续要求「再加两件」，Commerce Agents 会检查购物车增加后的**总量**，不能因为每次请求都没超限就放行；同一会话的购物车写操作**排队执行**，防多个请求各自通过检查、合起来却超限。
- 这些规则由**代码执行**，模型即使遗漏提示词**也不能绕过**。
- **执行检查要统一**，不能只在提示词里写"不要违规"，也不可分散在不同接入路径里漏掉检查。
  - **例**：用户粘贴商品 ID 要求加购 → 即使模型生成了调用请求，执行代码仍核对：这个 ID 是否来自当前会话中服务端返回的商品/订单/购物车记录？**无可信来源就阻止写入**。
- Commerce Agents 让不同运行方式**复用核心执行器**，换接入方式检查也不消失。
- 调用被阻止时返回 `blocked`，模型可解释原因、再查询商品信息——**放不放行由代码决定，怎么继续沟通由模型判断**。

**规则分层**：
- **Harness**：检查工具开放范围、操作对象来源、调用限额；
- **业务后端**：验证身份权限、库存资格等业务条件，完成真实数据修改；
- **模型**：理解需求、选择工具，根据执行结果继续判断。

> 商品 ID 来源可信 ≠ 当前用户有权修改它。Harness 检查来源后，后端仍要验证权限。**凡是不能接受模型偶尔跳过的约束，都应由代码保证。**

![[AI大模型/Agent/Anthropic-Agent产品设计新范式_assets/img_04.jpg|配图 · Harness 职责分工]]
> 从判断到执行三段分工：**模型**理解需求、选择工具、提出调用；**Harness** 统一检查（工具范围 / 对象来源 / 调用限额），不通过即返回原因；**业务后端**验证身份权限、完成真实数据修改。

---

### 四、工具明确动作边界，固定流程交给代码

顺序**已经确定**的业务流程，直接用代码执行。

- **例**：预订业务「先校验资格 → 锁定资源 → 创建记录」的顺序由后端保证。模型只决定是否发起预订，不替代码排每一步、处理步骤间依赖。
- **工具拆太细**会让模型承担不必要的流程管理——校验/锁定/创建各自暴露成工具，模型就要连续多次调用、判前一步是否成功、失败能否继续。**拆分提供灵活性，但对顺序固定的业务只会增加轮次和漏步机会。**
- 工具应封装**一个完整业务动作**：把真正要选的参数交给模型，把确定的内部流程留给代码。
  - **例**：搜索服务返回排序后的商品，模型根据预算/用途决定推荐哪些、展示多少——不要把整段选购封装成一个巨大工具。
- **返回结果要明确**：查不到就返回 `None` 并说明原因，不填 0；提案已暂存，也不等于修改已完成。
- **判断边界**（单点）：这一步是否需要理解用户意图？需权衡 → 交给模型；规则顺序已定 → 交给代码。

![[AI大模型/Agent/Anthropic-Agent产品设计新范式_assets/img_05.jpg|配图 · 工具动作边界]]
> 一个完整业务动作由代码保证顺序与失败处理（校验资格 → 锁定资源 → 创建记录）；太细会逼模型反复安排固定步骤，太大则吞掉仍需模型判断的任务。成功=真实完成、缺失=None+原因、暂存=尚未执行。

---

### 五、业务修改复用原有后端，别去重建企业系统

企业已经优化过的业务能力，直接通过工具**复用**。

- 促销计算、库存管理、审批已含大量业务规则，接入 Agent 后仍应由**原有系统**提供，不在 Agent 里重新实现。
  - **例**：商家要求调整促销 → 模型分析提方案，但优惠计算和活动限制仍调原有服务。
- **在工具里重写业务逻辑** = 多出一套要维护的规则：规则一变，原系统和 Agent 工具都要改，两个入口可能给出不同结果（例：配送资格查询）。
- 更合适：后端提供完整资格查询，工具调接口、整理返回信息，**业务规则继续由同一个系统维护**。
- **高权限修改走既有授权/审批/业务检查入口**：Commerce Agents 经营助手先生成**暂存提案**，执行时再检查有效批准和当前规则；购物助手没有实际扣款能力，结账交给宿主应用。
  - 模型提出降价方案 ≠ 获得直接修改价格的权限；真正执行仍经服务端检查。
- 已有成熟后端就优先复用；缺完整接口就先补齐服务能力。**接入 Agent 是增加一种交互方式，不应因此增加一条绕过业务约束的执行通道。**

![[AI大模型/Agent/Anthropic-Agent产品设计新范式_assets/img_06.jpg|配图 · 业务规则统一维护]]
> 原有应用的业务后端维护规则（库存 / 促销 / 身份权限 / 审批）并执行真实修改；Agent 工具只调接口、整理结果。受控写入链：先生成提案 → 走原有批准入口 → 执行时复查。

---

### 六、业务结果存系统里，异步任务按依赖安排

**业务结果独立保存**，上下文只放当前需要的信息。

- Commerce Agents 会在服务端记录已返回的商品等对象，后续操作核对来源；长期记忆也有独立存储结构。
  - 模型在对话里提到过商品 ≠ 能操作它，执行时仍核对可信记录。
- 聊天历史会被截断/压缩，**商品记录、任务状态和批准结果不能因此丢失**。
- **存文件还是数据库**：看谁要使用、怎样更新。
  - 小规模个人记忆 → 文件；涉及多人权限、并发更新、关联查询 → 数据库。
  - **例**：商家员工偏好按人保存、读取守权限，不能因共用一个商家账号就把不同员工的信息混在一起。
- 独立存储后，模型按需读取，其他页面/服务也能用同一份结果——**别把聊天记录当数据库**。

**异步与否的判定**：看当前回答是否依赖它的结果。
- 不影响当前回答的 → 后台处理（用户说出尺码后，记忆写入可另处理，不必让用户等保存完成）；
- 互不依赖 → 并行（销售 + 库存查询）；
- 有先后依赖 → 按顺序（报告需同时分析两份数据，必须等结果齐全）。

![[AI大模型/Agent/Anthropic-Agent产品设计新范式_assets/img_07.jpg|配图 · 状态与依赖]]
> 状态存储三合一（业务结果 / 任务状态 / 批准记录）独立保存、按需读取；长期记忆按人保存，多人权限/并发/关联查询优先数据库。依赖调度：不影响当前回答→后台，互不依赖→并行，齐全才续→串行。

---

### 七、上下文按变化频率管理，别把所有信息混在一起

> **固定规则放前面，会话信息放中间，实时数据放最后。**

- Anthropic 把请求内容分三层：全局的提示词/工具定义、当前用户的信息与对话历史、页面/时间等频繁变化的内容。
  - **例**：切商品页只需更新当前商品信息，共用的搜索规则和工具定义保持稳定→ 既给最新背景，又利于复用前面已缓存内容。
- **频繁变化的信息放太靠前会破坏缓存复用**：每次在 System Prompt 开头更新当前时间，即使后面规则完全相同，稳定前缀也会被打断。Harness 应分开组装：固定部分稳定、动态部分后置更新。
- **读取范围按任务控制**：用户搜鞋时，提前给尺码和品牌偏好即可，不必加载全部历史记忆。
- **何时做分层**：三类信息开始混用时，先明确每类放哪、何时更新，不必一上来就搭复杂系统。
  - 流量大、重复多 → 重点优化缓存；
  - 价格、库存、批准状态变化快 → 优先保证数据有效。
- **缓存复用的是稳定内容**，不能为提高命中率让模型继续用过期业务状态。

![[AI大模型/Agent/Anthropic-Agent产品设计新范式_assets/img_08.jpg|配图 · 上下文分层模型]]
> 一次请求的信息顺序：① 全局稳定（固定规则·工具定义）与 ② 会话信息在前 → 构成稳定前缀、利于缓存复用；③ 实时变化（当前页面·时间）放到末尾更新。Harness 分开组装；缓存不能代替实时业务检查。

## 落地清单（新增一个工具前先答清）

1. 这个工具能**操作什么**？
2. 执行前要**检查什么**？
3. 结果**存在哪里**？
4. 失败后**由谁处理**？

把这些问题答清楚，才知道一个功能是否具备**可靠运行**的条件。**Harness 值得投入的地方，就是让模型的判断有可靠的执行过程。**

> Commerce Agents 仍是**参考实现**，真实鉴权、业务规则和支付需要接入方补齐。但它给出的分工很清楚：**模型可以灵活选择方案，系统必须准确记录状态、执行规则，并承接每一次实际操作。**
