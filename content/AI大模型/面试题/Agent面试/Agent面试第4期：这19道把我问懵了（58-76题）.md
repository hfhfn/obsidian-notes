## 58｜多用户场景下，记忆系统应该如何做「隔离」？

> [!question] 题目
> 多用户场景下，记忆系统应该如何做「隔离」？不同用户的记忆不能混在一起。

> [!success] 一句话答案
> 每条记忆写入时绑定 `user_id`（多租户再加 `tenant_id`），检索时**先按用户过滤再召回**，公共知识与私人记忆分级共享；删除必须级联清理所有存储位置。

**展开**

1. **隔离粒度**：优先「共享库 + metadata 过滤」，成本低、易扩展；大客户或合规要求再上独立 collection / 独立库。对应 SaaS 的「逻辑隔离 vs 物理隔离」。
2. **检索必须 pre-filter**：在 ANN 检索前加 `user_id = current_user_id`，而不是先 top-k 再过滤——否则其他用户的记忆会占满候选集，召回率骤降。
3. **记忆分级**：公共知识（产品信息、FAQ）进共享池，需审核与来源标注；私人偏好、事实、历史进私有区，永不跨用户召回。
4. **写入治理**：`user_id` 由服务端会话注入，不能由模型生成；条目带来源、时间、置信度；敏感字段脱敏后入库。
5. **生命周期**：删除请求级联清理向量库、缓存、摘要、日志与备份（或加密擦除）；换设备/换账号通过导出导入或身份绑定迁移。

> [!note] 原题选择
> **D.** 每条记忆绑定用户 ID，检索时按用户过滤，公共知识共享、私人记忆隔离。

**追问准备**

- **概念层**：与 SaaS 租户隔离的类比——共享表 + `tenant_id` + 行级安全（RLS）是逻辑隔离；独立 schema/库是物理隔离；可按客户等级混用。
- **反例层**：记忆只存「用户说过 X」不存上下文，会把特定场景的偏好误当全局偏好；删除只删向量库不删日志缓存，属于「假删除」。
- **工程层**：记忆管理界面要展示「内容 + 来源上下文 + 时间 + 置信度」，支持编辑/删除/关闭某类记忆；删除需告知生效范围。
- **性能**：共享库按 tenant 分区/分片，向量库用 partition key（Milvus）或 payload index（Qdrant），让过滤走索引而不是全量扫描。

> [!tip] 采分点
> 用户 ID 绑定 / 检索过滤 / 权限控制 / 公共 vs 私人记忆；加分项：召回前过滤、共享级别、隐私底线。关键原则是「隔离做不好，比没有记忆更糟糕」。

## 60｜超长对话（100 轮以上）的记忆架构怎么设计？

> [!question] 题目
> 在长对话场景（如 100 轮以上）中，记忆系统面临什么挑战？如何设计一个能处理超长对话的记忆架构？

> [!success] 一句话答案
> 分层记忆 + 动态摘要 + 关键事件锚点，核心是「时间越远、记忆越抽象」，用 token 预算约束每一层的占比。

**展开**

1. **三类挑战**：上下文窗口爆炸；早期关键信息被挤出；寒暄/跑题噪音累积。轮数越多，成本与首 token 延迟也越高。
2. **分层记忆**：最近 N 轮保留原文（短期）；N~M 轮做滚动摘要（中期）；更早的内容抽成结构化事实/偏好/决策（长期），检索时按当前 query 召回，而不是全量注入。
3. **动态摘要**：摘要的摘要要设压缩比与保真校验，保留「谁、何时、约束、决定、未完成事项」，丢掉寒暄与重复。
4. **关键事件锚点**：用户明确约束、身份信息、关键决定、未完成 TODO 打 tag 永久保留，不参与压缩。
5. **预算分配**：例如系统提示 15% / 近期原文 45% / 检索记忆 25% / 摘要 15%；超限先裁低优先级。压缩异步执行，不阻塞主链路。
6. **指标**：远程召回率（长对话后还能答对早期问题）、摘要保真度、每轮 token、首 token 延迟。

**追问准备**

- **概念层**：与人类长期记忆类比——大事、情绪强、重复出现的信息进入长期记忆；日常细节留在短期。
- **反例层**：摘要的摘要压缩过度会失真，尤其是否定词与条件（「不要红色」被压成「喜欢红色」）；要用锚点、原文回查、摘要版本回滚兜底。
- **工程层**：压缩触发条件可以是轮数、token 阈值或话题切换；摘要要版本化，便于定位信息丢失点。

> [!note] 原题选择
> **B.** 分层记忆：近期原文、中期摘要、远期结构化，关键事件锚点永久保留。

> [!tip] 采分点
> 分层记忆 / 动态摘要 / 关键事件锚点 / 时间越远越抽象 / 远程召回率；加分项：摘要平滑过渡、锚点精炼、信息失真控制。

## 64｜编程 Agent 如何组装代码上下文？（题干还原）

> [!warning] 题干还原
> 原截图在此题处截断，题干按答案与追问还原：**编程 Agent（如 Claude Code / Cursor）面对一个大型代码仓库时，应该如何选择和组织上下文？** 答案依据原文补全。

> [!success] 一句话答案
> 不要把整个仓库塞进去，而是按任务动态组装：当前文件 + 语义/符号检索出的相关文件 + 调用链依赖 + 用户显式提及，并卡死 token 预算。

**展开**

1. **优先级**：当前打开/编辑文件 > 用户 @ 提及的文件 > 检索相关文件 > 调用链/import 依赖 > 仓库概览（README、目录树）。
2. **检索**：先用 grep / AST 精确找符号（函数名、类名、错误码），再用 embedding 找语义相关，最后 rerank；用便宜手段先缩小范围。
3. **调用链**：用 tree-sitter / LSP 解析 import 与调用关系，只拉 1~2 跳，避免把整个依赖图都塞进来。
4. **预算**：按 token 分配，超限时摘要化或裁剪低优先级内容；保留文件路径与行号，方便模型引用和生成 diff。
5. **动态性**：多轮任务每轮重新组装；优先让 Agent 主动搜索（agentic search），而不是一次性把上下文塞满。

**追问准备**

- **概念层**：为什么不是越多越好——lost in the middle、噪声稀释注意力、成本与延迟上升、关键文件反而被淹没。
- **反例层**：用户提到的函数在另一个仓库，可通过接口定义、包索引、按需拉取源码或只读镜像处理跨仓库依赖。
- **工程层**：排序可用「AST 命中 + embedding 相似度 + rerank + 最近编辑加权」；生成文件、vendor 目录默认降权。

> [!note] 原题选择
> **D.** 动态组装：当前文件 + embedding 检索相关文件 + 调用链依赖 + 用户提及文件，控制在窗口预算内。

> [!tip] 采分点
> 动态上下文组装策略；相关文件检索意识是加分点。反例：塞一堆无关文件，关键文件没进上下文，LLM 改错地方。

## 65｜Agent 的「幻觉」问题怎么缓解？

> [!question] 题目
> Agent 的「幻觉」问题怎么缓解？

> [!success] 一句话答案
> 把「闭卷生成」改成「开卷作业」：事实类问题强制先检索、答案逐条溯源、低置信度提示或拒答，再用 NLI 校验兜底。

**展开**

1. **意图分流**：事实类（政策、数字、人物）必须走工具；推理/创作类允许生成，但要标注假设与依据。
2. **工具优先**：检索不到就拒答，不允许「凭记忆」补全；工具返回结构化结果并带来源。
3. **答案溯源**：每个结论带 `doc_id` / URL / 工具名 / 时间戳，前端可点开原文；无来源的句子不允许进入最终答案。
4. **一致性校验**：用 NLI / LLM judge 判断「答案是否被检索文档支持」，矛盾则重写或拦截。RAG 只降低幻觉率，不能消灭幻觉。
5. **置信度**：综合检索分数、来源一致性、覆盖度打分，低分明确提示「可能不准确」。
6. **线上度量**：幻觉率、溯源覆盖率（目标 >80%）、拒答率（过高说明召回差）、人工抽检。

**追问准备**

- **概念层**：Agent 幻觉比 LLM 幻觉多一层工具错误——选错工具、参数传错、解析错，都会被模型当成事实继续推理，错误沿 loop 放大。
- **反例层**：检索到正确文档仍然幻觉，需要 NLI 一致性校验 + 引用约束 + 分段生成；光靠 RAG 不够，因为模型会误读文档。
- **工程层**：线上埋点保存 `query + 检索 docs + 模型输出 + 人工/用户反馈`，计算被标记错误的比例；同时监控溯源覆盖率与拒答率。

> [!note] 原题选择
> **C.** RAG 只能降低幻觉率而不能消灭，还需 NLI 校验答案是否被来源支持，并按意图区分事实类与推理类问题。

> [!tip] 采分点
> 讲清 Agent 幻觉的原理与关键细节。减分项：只说「用 RAG 减少幻觉」、说「让模型更诚实」——LLM 的目标函数决定它改不了，只能靠外部约束。

## 66｜对 Agent 安全性的理解

> [!question] 题目
> 谈谈你对 Agent 安全性的理解。

> [!success] 一句话答案
> 假设 Agent 一定会犯错，用最小权限、副作用分级、沙箱、审计和限流，把犯错的爆炸半径控制住。

**展开**

1. **权限最小化**：工具级、数据级、租户级三层授权；按任务发短期凭证，任务结束即回收。
2. **危险操作拦截**：工具注册时声明 `read` / `write` / `destructive`，destructive 级（`rm -rf`、`DROP TABLE`、改生产配置）必须人工 approve；不要用关键词匹配判断。
3. **沙箱隔离**：Docker / Firecracker microVM / gVisor；CPU 1~2 核、内存 1~4GB、网络白名单、只读挂载、执行超时。
4. **操作审计**：记录 who / what / when / 参数 / 结果 / `trace_id`，日志不可篡改，保留 90 天；敏感参数脱敏。
5. **限流与配额**：每 Agent 每分钟 ≤60 次外部调用；按任务设 token / 金额 / 调用次数预算，超限熔断。
6. **输入输出安全**：工具返回值一律当不可信数据；防 prompt injection；PII 脱敏；输出过审核。

**追问准备**

- **概念层**：安全的核心不是「让模型不犯错」，而是「犯错后损失可控」。
- **反例层**：只做 prompt 层约束（「不要删库」）挡不住注入；审计日志本身可能泄露敏感信息；沙箱共享宿主网络等于没隔离。
- **工程层**：HITL 不打断体验的做法——按风险分级、批量审批、操作可撤销；多租户场景让 `tenant_id` 贯穿到工具层。

> [!tip] 采分点
> 权限最小化 / 操作审计 / 危险操作拦截 / 沙箱 / 速率限制；加分项：副作用分级、爆炸半径、可追溯。原文深度版末尾被截断，以上已补全。

## 67｜多 Agent 对等协作如何稳定收敛？（题干还原）

> [!warning] 题干还原
> 原截图在此题处截断，题干按采分点与追问还原：**多 Agent 对等协作（Peer-to-Peer）模式有什么优缺点？如何设计才能稳定收敛？** 答案依据原文采分点补全。

> [!success] 一句话答案
> 对等协作灵活、易涌现、单点失败可补位，但容易无限协商、群体思维、责任分散；要用轻量协调者、最大轮次、决策规则和异议保护把它约束住。

**展开**

1. **适用场景**：开放式探索、方案头脑风暴、异质专家会诊；不适合强流程、强时效、强一致任务。
2. **收益**：多视角并行；容错（一个 Agent 挂了别人能补位）；可能产生超出单 Agent 的方案。
3. **风险**：收敛慢/无限协商、token 成本高、群体思维（LLM 倾向礼貌附和）、责任分散、输出不一致。
4. **协作结构**：轻量协调者负责议程、计时与收敛判定，但不垄断决策；共享黑板记录结构化发言，做去重与引用。
5. **决策机制**：最大协商轮次 + 决策规则（多数决/加权/弃权）+ 终止条件（共识阈值/边际收益下降/超时）。
6. **异议保护**：固定反方角色（devil's advocate）、匿名投票、少数派报告单独保留、决策日志可追溯。

**追问准备**

- **概念层**：与 Paxos/Raft 的相似性——共识、quorum、协调者、轮次/term、超时重试；区别是 Agent 的「投票」语义更模糊。
- **反例层**：10 个 Agent 讨论「今天天气」会过度协作、浪费 token——这类任务应先路由到单 Agent。
- **工程层**：异议保护可组合「反方角色 + 匿名投票 + 少数意见写入报告」；没有决策 owner 时，协调者要在轮次上限处强制收敛。

> [!tip] 采分点
> 容错 / 涌现 / 收敛慢 / 群体思维 / 责任分散；加分项：轻量级协调者、最大协商轮次、异议保护。

## 68｜多 Agent 系统如何做「错误隔离」？

> [!question] 题目
> 多 Agent 系统中，如何做「错误隔离」？即一个 Agent 出错后，如何防止错误传播到整个系统？

> [!success] 一句话答案
> 边界校验 + 熔断 + 沙箱 + 结果复核 + 降级路径，核心是「不让错误静默传播」。

**展开**

1. **边界契约**：每个 Agent 的输入输出都过 schema（Pydantic / JSON Schema）与语义合理性检查（空结果、越权、格式对但内容离谱）。
2. **隔离**：独立 state/context 命名空间，不共享可变全局状态；工具权限与配额隔离；代码执行进沙箱。
3. **熔断**：连续 3 次失败或错误率超阈值即熔断，跳过或降级；半开探测恢复；区分业务失败与系统失败，防误熔断。
4. **结果复核**：关键节点（最终输出前）加 reviewer / critic 做一致性校验；高风险场景加人工 gate。
5. **可追溯**：`trace_id` 贯穿全链路，每步记录输入、输出、工具调用；错误能定位到具体 Agent 与步骤。
6. **降级路径**：预定义 fallback（缓存、默认值、备用模型、人工、只读模式），返回部分结果时明确标注。

**追问准备**

- **概念层**：隔离不是「每个 Agent 一个数据库」，而是状态、权限、故障域三者分开。
- **反例层**：复核 Agent 自己也可能错——用独立模型 + 规则校验 + 人工抽检，避免同源盲区。
- **工程层**：共享黑板要版本化、只追加、控制写权限；熔断阈值用历史错误率而非拍脑袋。

> [!note] 原题选择
> **D.** 通过边界校验、熔断机制、沙箱执行和结果复核，防止单个 Agent 的错误扩散。

> [!tip] 采分点
> 边界校验 / 熔断 / 沙箱 / 结果复核 / 降级路径；加分项：可追溯性、隐性错误、误熔断防护。

## 69｜如何设计「生成—验证—精化」循环？（题干还原）

> [!warning] 题干还原
> 原截图在此题处截断，题干按追问与踩坑还原：**如何设计一个「生成—验证—精化」的迭代循环？怎样避免无效重试和过度精化？** 原文标准答案未截到，以下按主题补写。

> [!success] 一句话答案
> 生成 → 可执行的验证反馈 → 定向修正，构成有界循环；用 rubric、错误分类和守门 Agent 控制轮次与收益。

**展开**

1. **循环骨架**：Generator → Verifier/Critic → 结构化反馈（问题位置 + 原因 + 修改建议 + 严重度）→ Refiner；最多 N 轮。
2. **停止条件**：rubric 全部通过、达到分数阈值、轮次上限、边际收益低于阈值、超时或超预算。
3. **反馈质量**：验证信号必须可执行，避免「再改改」这种模糊反馈；验证器独立于生成器，规则 + 模型混合。
4. **重试策略**：先分类错误；临时错误退避重试；质量错误要换 prompt / 参数 / 检索 / 工具，不要原样重放。
5. **防过度精化**：守门 Agent 判断「已足够好」；保留 best-of 版本；冻结已通过段落；用 diff 防止改坏正确部分。
6. **成本控制**：小模型做 verifier、缓存中间结果、限制轮次与 token。

**追问准备**

- **概念层**：与人类改稿类比——初稿、审稿意见、定向修订；关键是审稿意见要具体。
- **反例层**：验证信号本身错了（验证 Agent 误判），会越改越差；用多验证器投票、规则兜底、人工抽检校准。
- **工程层**：区分可重试/不可重试错误，可用异常类型 + 错误码 + 分类器；重试时微调 prompt（如「上次失败了，请换个思路」）。

> [!tip] 采分点
> 迭代精化 / 验证反馈 / 最大轮次 / 守门 Agent / 错误分类；踩坑：同 prompt 同参数重试必得同错；过度精化会改坏正确细节。

## 70｜并行执行能带来什么收益和风险？如何调度？

> [!question] 题目
> 在 Agent 工作流中，并行执行（Parallel Execution）能带来什么收益？有什么风险？请设计一个并行执行的调度策略。

> [!success] 一句话答案
> 用 DAG 找无依赖节点并行，收益是延迟与吞吐，代价是 token、合并冲突和限流；用并发度控制、屏障同步、短路与降级兜底。

**展开**

1. **收益**：串行总耗时 Σt 降为 max(t)（理想情况）；同一时间处理更多请求，吞吐提升。
2. **风险**：token 成本上升；多个输出需要合并，可能信息冲突或风格割裂；并行调工具触发 API 限流；部分失败；调试与重放更复杂。
3. **调度**：依赖分析建 DAG → 拓扑分层 → 同层并行；并发度按下游配额设（如搜索最多 3 并发）；屏障同步后进入下一阶段；统一超时与取消。
4. **容错**：单节点失败可重试、降级或用其余节点结果凑合；只有关键节点失败才整体失败。
5. **优化**：短路（已有正确答案就取消其余节点）、hedged request（慢节点补发备份请求）、流式合并。
6. **指标**：加速比 = 串行时间 / 并行时间；P95 延迟、token 成本、失败率。

**追问准备**

- **概念层**：与 MapReduce 类比——map 并行、shuffle/合并、reduce 汇总；合并阶段往往才是瓶颈。
- **反例层**：5 个并行 Agent 中 4 个很快、1 个很慢，总等待由最慢决定——用超时降级、备份请求、拆分慢任务或缓存优化。
- **工程层**：并行还是串行的判断标准——是否存在依赖、是否时延敏感、成本预算、下游限流、结果一致性要求。

> [!note] 原题选择
> **C.** 并行可降低延迟但增加成本和合并复杂度，需依赖分析、并发度控制和屏障同步。

> [!tip] 采分点
> 延迟降低 / 依赖分析 / 并发度控制 / 屏障同步 / 加速比；加分项：短路优化、风格统一、资源竞争限流。

## 71｜如何设计 Agent 工作流的「错误恢复」机制？

> [!question] 题目
> 设计一个 Agent 工作流的「错误恢复」（Error Recovery）机制。当某个节点失败时，系统应该如何决策——重试、跳过、降级还是中止？

> [!success] 一句话答案
> 先分错误类型，再判节点是否关键，最后选重试/降级/跳过/中止；用错误预算和预定义兜底防止无限恢复。

**展开**

1. **错误分类**：瞬时（网络/限流/超时）→ 退避重试；永久（参数错/工具不存在/权限）→ 修正或中止；质量（格式/校验失败）→ 修正后重试；业务（无结果/不满足）→ 换路径或降级。
2. **关键性判断**：关键路径节点（输出是后续节点输入）不能跳过；增强路径（可选优化）可以跳过。
3. **恢复策略**：重试 ≤3 次 + 指数退避 + 抖动；降级（默认值/备用模型/缓存/人工）；跳过；中止并向用户报错。
4. **错误预算**：全局限制重试与降级次数，超限强制中止，防止恢复本身拖垮系统。
5. **预定义兜底**：每个节点声明 `on_failure` 策略与兜底值，不要把决策留到运行时。
6. **监控**：重试成功率、降级率、错误分布、恢复耗时。

**追问准备**

- **概念层**：与数据库回滚的异同——事务是原子性回滚；工作流多用 Saga 补偿，回滚本身有代价，且要求幂等。
- **反例层**：非关键节点降级用默认值，但默认值恰好是错的——要标注「已降级」、二次校验、必要时人工复核。
- **工程层**：错误分类器可用异常类型 + 错误码 + 规则 + 模型；关键节点的兜底行为必须在设计期写清楚。

> [!note] 原题选择
> **D.** 根据错误类型和节点关键性，选择重试/降级/跳过/中止，并设定错误预算上限。

> [!tip] 采分点
> 错误分类 / 关键性判断 / 重试 / 降级 / 中止 / 错误预算；加分项：预先定义兜底行为、重试成功率监控、次优降级。

## 72｜Agent 工作流如何做灰度发布？（题干还原）

> [!warning] 题干还原
> 原截图在此题处截断，题干按追问与踩坑还原：**Agent 工作流如何做灰度发布？流量切分和回滚要注意什么？** 答案依据原文补全。

> [!success] 一句话答案
> 按可归因、可粘性的维度切流，新旧版本并行；成功率之外必须监控输出质量；回滚要能处理长任务并保证状态兼容。

**展开**

1. **切流维度**：用户/租户（体验稳定、可对比）、地区（合规/延迟）、请求类型（低风险先灰度）、内部白名单；同一用户保持版本粘性。
2. **灰度节奏**：1% → 5% → 25% → 50% → 100%，每阶段设观察窗口与自动/手动 gate。
3. **监控**：除成功率、延迟、成本外，必须看质量——人工抽检、LLM judge、业务指标、拒答率、工具错误率，防「静默失败」。
4. **版本化**：prompt、模型、工具、代码、配置整体打版本，保证可复现；新旧版本的状态 schema 要向前兼容。
5. **回滚**：一键切回；长任务等待完成或中断 + 补偿；checkpoint 要能跨版本恢复。
6. **实验形态**：canary、A/B、shadow（影子流量只观察不返回）。

**追问准备**

- **概念层**：灰度与 A/B 的区别——灰度关注「新版本是否可用」，A/B 关注「哪个版本更好」。
- **反例层**：只监控成功率会漏掉静默失败（不报错但答案变啰嗦、漏关键信息）；要抽样人工评估。
- **工程层**：切分维度按「可归因、可粘性、样本量足够」选；长任务回滚用版本标记 + 幂等重放 + 断点续跑。

> [!tip] 采分点
> 流量切分 / 质量监控 / 静默失败 / 版本化 / 回滚与状态一致性。

## 73｜如何评估 Agent 的「幻觉率」？

> [!question] 题目
> 如何评估 Agent 的「幻觉率」（Hallucination Rate）？请设计一个幻觉检测的评估方案。

> [!success] 一句话答案
> 抽取可验证的原子事实，逐条用外部工具核查，按「错误陈述 / 总陈述」计算，并按严重程度分级统计。

**展开**

1. **定义**：Agent 输出中与事实不符的可验证陈述占比；事实类与推理类分开统计。
2. **流程**：事实抽取（LLM/规则）→ 判定是否可验证 → 工具核查（搜索/DB/知识库）→ 标注支持/矛盾/未知 → 统计。
3. **分级**：致命幻觉（编造政策、医疗金融建议）> 严重幻觉（错误数据、张冠李戴）> 轻微幻觉（日期偏差、表述不准）；可加权或分别报告。
4. **难点**：原子事实抽取本身有误差；内部数据无法外部验证；推理错误与事实错误要区分；时效性。
5. **工程**：LLM-as-Judge 初筛 + 工具精查 + 人工抽检校准；维护黄金集做回归测试。
6. **指标**：幻觉率、溯源覆盖率、拒答率、用户反馈错误率。

**追问准备**

- **概念层**：幻觉与「信息错误」不完全相同——幻觉是模型生成了无依据内容；信息错误可能是数据源错或过期。
- **反例层**：输出的是合理推理但结论错，属于事实错误，不算严格意义的幻觉；要看「是否有依据」。
- **工程层**：错误分析要按「数量 × 严重度」排序，不能只看数量最多的类型；分类控制在 5~8 个大类。

> [!note] 原题选择
> **B.** 提取输出中的事实陈述，用外部工具验证真伪，分级统计错误比例。

> [!tip] 采分点
> 事实抽取 / 事实核查 / 分级统计 / 外部验证 / 幻觉分级；加分项：张冠李戴、内部知识幻觉、不可验证陈述。

## 76｜Agent 工作流节点的「幂等性」为什么重要？

> [!question] 题目
> Agent 工作流节点的「幂等性」为什么重要？怎么设计一个可安全重试的节点？

> [!success] 一句话答案
> 任何有外部副作用的节点都要假设会被重试至少一次；用幂等键 + 先查后写 + 读写分离 + 下游去重，保证只生效一次。

**展开**

1. **为什么**：LLM 限流、工具超时、网络抖动让重试成为常态；不幂等会重复发邮件、重复扣款、重复建单。
2. **幂等键**：`request_id` + 业务唯一键（订单号 / 用户 + 操作 + 时间窗），由服务端生成并贯穿所有重试。
3. **先查后写**：执行前查幂等表/状态机；已处理直接返回上次结果；状态用 pending / success / failed。
4. **读写分离**：外部副作用带幂等键；State 更新走内存/checkpoint，天然可重放。
5. **下游不支持去重**：本地去重表、唯一约束、发送记录、延迟对账；支付用商户订单号，邮件用 `message_id` 或去重窗口。
6. **读操作天然幂等**；缓存与日志也要考虑重复写入。

**追问准备**

- **概念层**：幂等性与重试策略的关系——先判幂等，再决定是否重试；重试用指数退避与最大次数。
- **反例层**：邮件服务商不提供去重，可本地记录发送状态 + 延迟对账 + 人工复核；支付必须用商户订单号做唯一键。
- **工程层**：代码实现「先查后写」可用唯一索引、事务、Redis `SETNX`、状态机；幂等键不能由模型生成。

> [!note] 原题选择
> **B.** 重试是常态，写操作节点必须带幂等键 + 先查后写，避免重复副作用（重复邮件/重复扣款）。

> [!tip] 采分点
> 指出重试导致副作用累积的风险；加分项：幂等键 + 先查后写 + 读写分离设计。
