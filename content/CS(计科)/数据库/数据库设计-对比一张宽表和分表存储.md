直观地总结“一张大表”和“分表存储”在各个关键维度上的优劣。

### 数据库设计：一张大表 vs. 分表存储

| 维度           | ❌ 一张大表（反模式）                                 | ✅ 分表存储（关系型数据库范式）                      | 通俗解释                               |
| :----------- | :------------------------------------------ | :------------------------------------ | :--------------------------------- |
| **1. 数据冗余**  | **严重**。例如，每产生一个订单，就要把商品名称、价格、分类信息全部再写一遍。    | **极少**。数据只存一份。订单里只需要存一个`商品ID`。        | **不把相同的话说两遍。** 节省空间，避免出错。          |
| **2. 数据一致性** | **差（更新异常）**。修改商品价格，必须去更新所有历史订单，漏一个数据就前后矛盾了。 | **好**。修改商品表里的价格，所有关联查询自动就是新价格。        | **一处改动，处处生效。** 不会出现同一个商品有两个价格的情况。  |
| **3. 修改扩展性** | **灾难**。想给商品加个字段，得去修改几亿行的超级大表，极可能导致服务中断。     | **灵活**。只需要修改商品表，订单表和分类表纹丝不动。          | **想改衣柜，只动衣柜。** 不用为了改衣柜而去把整个家都拆了。   |
| **4. 安全权限**  | **混乱**。很难精细控制权限。给修改权限，可能就会看到或改掉不该碰的敏感信息。    | **清晰**。可以精确控制：仓管只能动商品表，客服只能看订单表。      | **会计管账本，库管管货架。** 各司其职，不乱不偷看。       |
| **5. 理解维护**  | **逻辑混乱**。订单数据和商品分类属性混在一起，时间久了，没人看得懂这张表是干嘛的。 | **逻辑清晰**。表名即功能：商品表管商品，订单表管交易。新同事一看就懂。 | **衣柜是衣柜，书柜是书柜。** 不需要在一个柜子里翻找所有的东西。 |
|              |                                             |                                       |                                    |
对比写入和查询

| 维度                | 一张大表          | 分表存储        | 本质    |
| ----------------- | ------------- | ----------- | ----- |
| **存储空间**          | ❌ 大（冗余）       | ✅ 小         | 分表省空间 |
| **写入性能**          | ❌ 慢（要写很多冗余字段） | ✅ 快         | 分表写入快 |
| **简单查询**（如查商品）    | ❌ 慢（表太大）      | ✅ 快         | 分表胜出  |
| **复杂关联查询**（如订单详情） | ✅ 快（一次读取）     | ❌ 稍慢（需JOIN） | 宽表胜出  |

**分表存储的本质**：

> 用“查询时的**计算成本**（多查几张表、多做JOIN）” 和 “**设计的复杂性**”，换取了“**存储空间的节省**”、“**数据的高质量**（一致性/易维护）”和“**特定查询的高性能**（如按分类查商品）”。
