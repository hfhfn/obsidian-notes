# DeepSeek-参数化查询防注入原理

> [!abstract] 一句话
> `cursor.execute(sql, params)` 能防注入，是因为 **SQL 结构（代码）与用户数据（数据）在协议层面彻底分离**，数据库从设计上就不会把参数当作 SQL 代码解析。

---

## 一、拼接 vs 参数化（本质区别）

**危险的字符串拼接：**
```python
name = "' OR '1'='1"
sql = "SELECT * FROM users WHERE name = '" + name + "'"
cursor.execute(sql)
# → SELECT * FROM users WHERE name = '' OR '1' = '1'
# 数据库把 OR '1'='1' 当成语法结构，条件永真，整个表被拖走
```

**安全的参数化：**
```python
sql = "SELECT * FROM users WHERE name = %s"
cursor.execute(sql, (name,))
# 数据库收到的是两样分开的东西：
#   SQL 模板：WHERE name = ?        （结构已固定）
#   参数值：  ' OR '1'='1           （只是一个普通字符串）
```

**底层发生了什么：**

1. **先编译、后传值**：数据库驱动先把带占位符的 SQL 发给数据库，数据库解析、编译出执行计划。此时 `?` 就是一个「值的位置」，语法结构已经固化。
2. **参数单独传输**：参数值走独立通道发送，只当一个**字面量值**填入该位置，**不做词法/语法分析**。
3. **不是文本替换**：占位符替换发生在数据库内部的执行层，而非 SQL 字符串层面。所以参数里无论有引号、分号、`--`、`OR`，都只是普通字符。

> [!note] 打个比方
> 拼接 = 把用户输入直接写进合同正文，用户能加条款；参数化 = 合同正文早已定稿，用户输入只是填在某个空白格里的名字，改不了合同结构。

---

## 二、参数化的边界：只保护「值的位置」

**表名、列名、`ORDER BY`、`ASC/DESC` 这类「标识符位置」不能参数化**，必须白名单校验：
```python
# ⚠️ 危险：表名/列名来自用户
sql = f"SELECT * FROM {table} ORDER BY {column}"

# ✅ 正确：让用户从预设合法值里选
allowed = {"name", "age", "email"}
if column not in allowed:
    raise ValueError
sql = f"SELECT * FROM users ORDER BY {column}"
```

---

## 三、小结

| 方式 | 用户输入的角色 | 是否可注入 |
|---|---|---|
| 字符串拼接 | 被当作 SQL 代码解析 | 是 |
| 参数化查询 | 仅被当作数据值 | 否 |

> [!tip] 防注入的本质
> 不是「转义了特殊字符」，而是**让数据和代码在协议层面彻底分离**——数据库从设计上就没有机会把参数误当成 SQL。
