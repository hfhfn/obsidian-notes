# 第一部分 · 核心认知（提示词工程 vs Agent）

> 一句话口径：**两者不是对立，而是不同抽象层级的工程手段。提示词是给单次 LLM 调用的"静态激励"，Agent 是围绕多次 LLM 调用的"多步控制流"。Agent 内部每一环仍然在用提示词——提示词是 Agent 的积木/零件，Agent 是提示词的应用形态。**（源自 Anthropic《Building effective agents》）

## 1. 提示词工程（Prompt Engineering）是什么

通过**设计输入给模型的指令文本**，引导 LLM 在**单次调用**中给出期望输出。不改变模型权重，不动外部世界。

| 手段 | 说明 |
|---|---|
| 指令 / 角色 | 明确任务目标、格式；用系统提示设定角色、风格、边界 |
| Few-shot（少样本示范） | 给输入-输出对示例，让模型模仿格式与推理 |
| CoT 思维链 | 引导显示中间推理（"Let's think step by step"），进阶有 Self-Consistency |
| 结构化输出 | 要求 JSON / 固定字段 / 用工具 schema 强制格式 |
| 模板 / 变量系统化 | 拆成可复用模板，保证一致与可维护 |
| 提示词管理 / 版本化 | 版本管理、AB 测试、eval 集回归 |

**能达到什么**：不调权重即可明显提升单次输出质量、格式稳定性、领域能力；成本低、见效快，是绝大多数应用的"第一层优化"。Anthropic 原文："多数应用，优化单次调用就够。"

**局限（答"为什么还要 Agent"）**：
1. 静态、一次有效——语境固定，不能随过程调整。
2. 无状态——默认不带跨步骤持久状态。
3. 无外部行动——只能输出文本，不能调 API / 读写文件 / 操作工具。
4. 无自我纠正——单次生成错了就是错了。

## 2. Agent 系统是什么

> **Agent = 让 LLM 动态地自主决定自己的流程与工具使用**，去达成一个任务。
> **Workflow（工作流）= 由预定义代码路径编排 LLM 与工具**。

**本质结构**：LLM（核心推理）+ 规划 Planning + 工具 Tool use + 记忆 Memory + 环境交互/反馈循环 + 控制流（多步+循环+分支）。

**关键组成**：
- **基础积木 = 增强型 LLM**（Augmented LLM）= 加检索 Retrieval + 工具 Tools + 记忆 Memory。
- **工具接入**：主流是 MCP。
- **编排层**：决定代码预设（Workflow）还是模型自主（Agent）。

**能力层级（低→高）**：单次调用（提示词）→ 增强型 LLM → Workflow → Agent → 多 Agent。

## 3. 系统性对比（重点，能背能展开）

| 维度 | 提示词工程 | Agent 系统 |
|---|---|---|
| 本质 | 静态文本激励（单次调用） | 多步控制流（多次调用+工具+状态） |
| 状态/记忆 | 无记忆、单次有效 | 有记忆、可持久状态 |
| 行动能力 | 只输出文本 | 可调工具/API，作用于外部世界 |
| 是否循环 | 否 | 是（反馈循环直至完成） |
| 自我纠正 | 无 | 可基于环境反馈重试/调整 |
| 复杂度 | 低、简单可预测 | 高、易发散，需编排/容错/兜底 |
| 确定性 | 高 | 低，需 guardrail |
| 成本/时间 | 低 | 高（多次调用×多轮循环） |
| 失败模式 | 格式偏离/幻觉/答非所问 | 死循环/越权/级联错误/成本失控 |

**协同关系（必答点）**：
- Agent 内部全是提示词——规划器、执行、生成、评审每一环都是"prompt + LLM 调用"。
- 工具即提示词的一种形态：工具定义要想给 Junior 写优秀 docstring 一样写示例、边界、输入格式。

**演进路线**：提示词 → Function Calling（工具调用）→ Agent → 多 Agent。**先"简单回调"再上"复杂 Agent"**，能用单次+检索就别上 Agent（Anthropic：以延迟和成本换表现）。

## 4. 面试分层答法

1. 先立关系：不同抽象层级，提示词是"微观工程"，Agent 是"宏观编排"。
2. 提示词讲"稳"：静态、无状态、低成本、确定性高。
3. Agent 讲"活"：有状态、能行动、能循环、能纠错，代价是复杂度/成本/不确定性。
4. 讲桥：基础积木=增强型 LLM（检索+工具+记忆）；工具（尤其 MCP）与提示词 schema 是承接点。
5. 讲选型：任务明确→提示词；需外部世界/多步/不确定→Agent；能用简单就别复杂。
6. 收口追问：
   - Agent 内部用不用提示词？→ 用，每个节点都是 prompt+调用。
   - 提示词和 function calling 关系？→ function calling 让模型声明要调的工具，其参数 schema 本身就是要精心设计的提示。
   - 什么时候 Agent 是过度设计？→ 单步、可枚举、确定性任务；成本/延迟敏感。

## 一、AI & 大模型

> 本主题是 AI 大模型开发岗面试主战场。题目跨分区编号，每条含"题面 + 追问 + 参考答案 + 一句话记忆"。

### Q1. LangGraph 如何实现常见的几种 Agent 模式？

**追问**：什么是 ReAct / Plan-and-Execute / 多智能体协作？核心概念（State/Node/Edge/checkpointing/interrupt）？相比"纯提示词+function-calling"解决什么问题？

**核心概念（先立骨架）**
- State：所有节点共享、带类型的任务状态，字段用 reducer 合并。
- Node：普通 Python 函数（输入 State → 输出对 State 的更新），单步动作。
- Edge：普通边与**条件边**（一个函数返回下一个节点名）。
- checkpointing 持久化：按 `thread_id` 存每条会话状态快照，支持暂停/恢复/回溯。
- interrupt / Command：人介入或把控制权交接给别的智能体。
- subgraph + Send API：子图封装复用、任务 fan-out 并行分发。

**常见模式在 LangGraph 的落地**
1. **ReAct**：`LLM_Node` → 条件边（有 tool_call → `Tools_Node` 执行并写回 State.messages；无 → END）→ 循环直到该作答。
2. **Plan-and-Execute**：`Planner_Node` 拆步骤存进 `State.plan` → 逐个 `Exec_Node` → 可选 `Replanner_Node` 重规划 → plan 清空 END。
3. **Router**：条件边先分类，按类别走不同 subgraph / 处理器（意图分派）。
4. **多智能体协作**：
   - Supervisor 主从：`Supervisor_Node` 决定交给哪个 worker，干完回 supervisor 成环。
   - Hierarchical 层级：supervisor 再套 supervisor（递归树）。
   - Handoff/Swarm：interrupt+Command 把控制权直接交给另一 agent。
   - Network 网状：agent 共享 State 自由读写（生产少用，上下文易爆）。
5. **Human-in-the-loop**：需批准处 `interrupt()` 暂停，人工输入后 `Command(resume=...)` 继续。

**面试加分点**：一针见血——"这些模式本质都是**同一套骨架**——State + Node + 条件边，区别只在图拓扑和 State 约定。" 相比纯 function-calling，LangGraph 把流程显式建模成图，可持久化、可中断、可并行、可复现。

**一句话记忆**：ReAct=想一步查一步；Plan-execute=先拆再做；Router=一入口多出口；多 agent 靠 supervisor/handoff——都能用 State+条件边拼出来。

### Q2. RAG 处理 PDF/Excel：文字/图片/表格分开提取后，要不要还原成原文上下文顺序？

**追问**：单独提取增强后有必要还原顺序吗？chunk 本来就会打乱顺序，还原还有意义吗？图文并茂怎么给用户？

**核心：先区分两个目标**
1. 要返回文件原文/提供定位 → 必须还原上下文顺序。
2. 只展示图文并茂结果 → 不必和原文逐字一致，让 **LLM 自行排版**或加图片/表格**引用展示**即可。

**核心手法 = "块化 + 顺序元数据 + 按需重组"**，不是"拼回一个连续文本"：
- 把 PDF/Excel 解析成异构块：文本块/图片/表格，每块带元数据 `(type, page, block_index)`。
- **chunk 会不会打乱顺序?——只有没记顺序索引时才会**。解析时永远保留文档相对顺序（`chunk_id/order`），检索/重排后按序追溯。
- **还原顺序在渲染/输出端按 order 排序重组**，而不是 chunk 阶段硬拼。

**落地细节**：
- 图文并茂：上下文给 LLM 图片/表格的**引用标记**（`[fig1]`、`[table3]`）而不是塞整图；LLM 输出引用，前端据标记渲染。
- 表格/图片增强（OCR、表格结构解析、视觉描述）写回为块元数据，可被检索复用。

**一句话记忆**：RAG 异构文档 = 块化解析，用"类型+页码+顺序索引"元数据保持可重组；是否还原顺序取决于**要不要给原文**，而 chunk 打不打乱只取决于**记没记顺序**。

### Q3. 怎么保证大模型输出是合法 JSON？（结构化输出 / JSON 约束）

**追问**：function calling 和 Pydantic 怎么配合？解析/校验失败怎么办？

**访谈官想听成套范式，不是单个点名——通用范式 = 四件套叠加**
1. **function calling**：走原生 tool-schema，模型按 schema 出结构化结果。
2. **Pydantic 模型约束**：用 Pydantic 定义输出模型，它内部能**自动生成 JSON Schema**（`model_json_schema()`）下发给模型做约束，并做反序列化校验。（面试官常以为 pydantic 不能自动转 JSON Schema，其实可以——顺势强调。）
3. **提示词约束**：prompt 写清输出格式、字段、示例（few-shot）。
4. **失败重试**：解析/校验失败带上错误信息重试（有限次），再不行降级处理。

**一句话记忆**：JSON 合法性 = function-call（pydantic 自动出 schema）+ 提示词约束 + 失败重试三件套叠加；pydantic 能自动转 JSON Schema。

### Q4. skill 是怎么接入 agent 的？（工具化接入）

**追问**：skill 怎么被"加载/发现"？硬编码还是按需？有没有工业成熟做法？

- **思路 1：封装成工具（tool）接入**——把 skill 写成一个工具节点注册进工具列表；agent 走 tool-calling 时被调用。加载流程：**先给模型一份"技能/工具列表+描述"放进提示词**，让它按需"搜索/命中"，命中后再调用对应工具（关键词搜索式暴露，而非一次性加载全部）。
- **思路 2（工业成熟）**：用专门的 skills 加载框架把 skill 以工具方式挂载到 LangGraph/LangChain。

**一句话记忆**：skill 接入 = 封装成工具进工具列表 + 提示词暴露描述按需命中再调用；复杂加载可用专门 skill 框架。

### Q5. 何时该微调（Fine-tune）？何时该 RAG / 提示词（Prompting）？

**追问**：一个任务什么时候调提示词就够，什么时候必须微调？微调 vs RAG 的代价和适用？

**核心 = 三种手段的取舍，先给判断主轴**：按"模型本身会不会 / 要不要锁死知识"分：**提示词**（零成本·不落地·适合"会但临时规定"）、**RAG**（注入外部/最新知识·不动模型·适合"知识会变/要引用出处"）、**微调**（重塑行为/风格/私有领域·最贵·适合"长持久、固定行为"）。

**三条决策线**
1. 知识类/会变的资料 → RAG：答案依赖文档、需随时更新、要附出处；RAG 不训练、可热更新、可审计。
2. 行为/风格固化 → 微调：输出格式统一、领域术语、去 prompt 负担、推理成本可更低；代价是训练数据/算力/每次更新重训。
3. 模型本就会、只是临时规定 → 提示词：一张 prompt/few-shot 就能稳，最便宜最快。

**关键判断点**：
- 知识变了 RAG 立刻生效、微调则要重训 → 高频变动知识绝不用微调。
- RAG 较贵场景：每次检索+塞上下文（token/成本/延迟）；微调可吞掉固定知识省 token。
- 两者常互补：RAG 管"问什么答什么"的检索，微调管"怎么答得像"的风格，不是二选一。
- 代价排序：提示词最省 < RAG < 微调。

**一句话记忆**：提示词=零成本临时规定；RAG=会变的外部知识（附出处/热更新）；微调=固化行为与领域（最贵）；知识看 RAG、行为看微调、临时看提示词——三者可叠加不互斥。

## 二、后端 & 开发

### Q1. 元组（tuple）和列表（list）的区别？

**追问**：最大区别是什么？不可变有什么好处？何时用哪个？

**第一句先讲最大区别**：**元组不可变，列表可变（可修改）。**

**展开**：
- 不可变：tuple 不能增删改；list 可 `append`/`pop`/改下标。
- 性能：tuple 更省内存、创建更快，读上略快。
- 可哈希：tuple 不可变可作 dict 的 key、可放 set；list 不可。
- 语义：tuple 适"定长不可变"结构（坐标、多返回值）；list 适"需增删改"的动态序列。

**一句话记忆**：元组不可变、list 可变（最大区别）；tuple 省内存可作 key、list 灵活可增删改——按"要不要可变+语义"选。

## 三、系统 & 网络

### Q1. 高并发下，协程怎么调度同步（阻塞）函数？

**追问**：协程里直接调阻塞/同步函数会怎样？`asyncio.to_thread` 和 `run_in_executor` 区别？IO 密集 vs CPU 密集？Go 的 goroutine 呢？

**核心结论**：协程（asyncio）是**单线程事件循环**。直接同步调用阻塞函数会把**整个事件循环卡死**，其他协程停摆，高并发归零。解法：把同步函数丢给**线程池/进程池**跑，协程 await 结果。

**分场景**：
1. **IO 密集同步函数**（读写文件/DB/网络/第三方 SDK）→ `await asyncio.to_thread(fn, ...)`：丢默认线程池，循环继续调度其他协程。底层 `loop.run_in_executor(ThreadPoolExecutor,...)`。注意默认线程数有限（`min(32, CPU+4)`），铺满无法撑上万连接；真正高并发优先原生 async 客户端（aiohttp/aiosqlite/async 驱动），只在边界用 to_thread 兜底。
2. **CPU 密集同步函数** → 线程池没用（受 **GIL** 限制）。用 `run_in_executor(ProcessPoolExecutor,...)` 跨进程并行，或依赖 numpy/C 扩展释放 GIL。一句话：**IO 用线程池、CPU 用进程池规避 GIL。**
3. 别在事件循环线程里跑长阻塞：症状是"请求超时/全部卡住"。

**Go 反差（谈资级）**：goroutine 运行时做 **M:N 调度**，网络/系统调用时把阻塞 goroutine 让出、OS 线程去跑别的，所以同步风格天然高并发。**Python 要躲 GIL+事件循环、显式 to_thread；Go 由运行时替你调度。**

**一句话记忆**：同步函数别在协程里裸调 → IO 丢线程池(to_thread)、CPU 丢进程池(躲 GIL)，循环才不堵；Go 则运行时 M:N 自动让出。

## 四、数据结构 & 算法

### Q1. 两个列表数据特别大，怎么解决内存不够？

**追问**：用 zip 是不是就够了？真正海量数据怎么办？

**分两档答**：
1. **常见场景（合并导致内存涨）**：用 `zip(a, b)` → 转 dict 或逐对处理。强调 **`zip` 返回生成器是惰性的**——不会一次性全拷贝，而是用的时候逐项产出，避免瞬时翻倍内存。面试官常问的就是这个"惰性"。
2. **真正海量（单列表就超内存）**，不能指望 zip，给"不上内存"手段：
   - 分块/分批：一次处理一个 chunk，处理完释放。
   - 流式处理：迭代器/生成器按需产出，不全驻留内存。
   - 外部存储：数据放 DB/Redis，按需查询。
   - 内存映射 mmap：把文件映射进地址空间按页惰性读入，几乎不占物理内存。
   - 必要时增量/离线聚合，源头收敛。

**一句话记忆**：两个列表用 `zip`（惰性生成器，别被"打包"骗，不一次性翻倍内存）；真海量用分块/流式/外部存储/mmap，别把全集一次进内存。

# 第三部分 · Agent 系统项目深挖

> 面试中被追问、且没讲清的项目细节。每个点拆成"该怎么讲 + 关键 reasoning + 面试官想看什么"。文中数字均为**通用参考值（估算）**，面试前替换成自己的真实值。

## 1. 意图识别（把"闲聊 vs 专业路由"讲透）

- **意图识别是 Agent 的入口分流**：回答"用户这句话想干什么"，据此决定走专业流程还是闲聊。
- **BERT 意图分类模型**：输入句 → BERT 句子向量 → 分类头（softmax 多分类）→ 映射到预定义意图集合。意图集合不只是 {闲聊, 专业}，专业侧还要细分（查知识库/调工具/多轮澄清/下单/运维…），每个意图对应一条路由。
- **闲聊处理**：作独立意图；或对专业类别给低置信度阈值兜底。命中闲聊→走闲聊生成，不进专业流程。
- **兜底设计（加分）**：置信度低于阈值→转澄清/拒答引导，避免误操作。
- **工程细节**：领域数据微调 BERT、类别不均衡处理、预测 top-k+阈值双判。

**一句话记忆**："用 BERT 分类头做多类意图识别：专业意图细分 + 闲聊兜底 + 低置信度走澄清。"

*量级参考（估算）*：意图类别 8~15（1 个闲聊+其余专业）；BERT 领域小样本微调（几百~几千条）；置信度阈值 0.6~0.7 以下走澄清。

## 2. 意图之后：调用工具 / MCP，怎么筛选工具

**讲成"分层筛选"，不含糊**：
- **第一层：意图 → 候选工具集合**。每个意图预绑定一组可能用到的工具（意图-工具映射表），先粗过滤。→ "做了，按意图粗筛"。
- **第二层：相似度精筛（可选）**。基于工具 description/功能向量，对 query 与工具描述算 embedding+余弦相似度，候选集内取 topK。
- **两层都不/不需要**：工具少（<50）可直接意图→映射，不必上 embedding；工具多才需第二层召回。
- **接 MCP**：MCP 提供标准工具接入和元数据（名称/描述/参数 schema）；路由层消费这些描述做筛选，把选中工具名+schema 交给 function-calling。

**必答参数（面试官盯着问）**：
| 问题 | 参考口径 | 参考值(估算) |
|---|---|---|
| 工具有多少 | 报总数 N | 30~100 个注册工具 |
| 分几类 | 业务查询/运维/知识/计算… | 5~8 类 |
| 意图粗筛命中集合 | S（远小于 N） | 单意图绑 5~15 个 |
| 相似度 topk | K≈3~5 可配置 | 3~5 |
| 还是写死路由 | **配置化不写死**，新工具免改码 | 映射表+动态 topk |

**关键 reasoning**：意图过滤比每次全量 embedding 更省、更可控、可解释；相似度用于工具多时精化候选；写死路由不可扩展、新工具要改代码 → 用配置/映射表+动态 topk。

**一句话记忆**："意图先粗筛候选工具，必要时再在候选内做相似度 topk 精筛；路由配置化不写死，MCP 提供工具 schema 供消费。"

## 3. 并发模型（含多租户隔离）

**立场**：Python 协程，单进程单线程事件循环（GIL 决定不靠多线程）。
- 单线程协程并发 **1w~10w QPS** 都 OK，toB 足够，不需要多线程。
- LLM 调用必须走 async 接口；遇同步函数：IO→线程池（to_thread）、CPU→进程池（ProcessPoolExecutor）。
- DB：连接池要满足并发（连接数≥峰值并发/复用，或用 async 驱动连接池）。

**多租户会话隔离（加分）**：用**自定义 ID＝租户ID+会话ID**作为状态存取、缓存、DB/Redis key 的统一前缀；每个请求协程凭自己 ID 读写彼此隔离的上下文，不串话、不覆盖。→ **身份隔离靠自定义 ID，不是靠多进程多线程。**

**一句话记忆**："单进程协程 1w~10w，LLM 走 async、同步按 IO/CPU 分流，DB 用足并发连接池；多租户靠'租户+会话'自定义 ID 隔离上下文。"

## 4. 状态管理：多 Agent 状态怎么统一管理

**讲成"运行时 + 持久化 + 隔离 三层"**：
1. **运行时（内存）**：多 Agent 共享同一个 State（LangGraph），各节点经 reducer 合并读写同一 State——**统一管理核心**。多 Agent 靠共享 State 或 parent/child 层级协同。
2. **持久化**：PG 做 **checkpoint 落库**（`BaseCheckpointSaver`），所有 Agent 状态快照按 `thread_id/session_id` 定点存储，支撑断点续跑/回溯/审计。
3. **隔离与生命周期**：多租户凭 session_id 定位各自 State；会话结束清理避免堆积。

**一句话记忆**："状态统一管理 = 运行期单 State(reducer 合并) + PG checkpointer 落库(按 thread_id 定点) + 会话/租户 ID 隔离 + 生命周期清理；多 Agent 靠共享 State/层级协同。"

## 5. 记忆与持久化

**记忆分层（两层都讲）**：
- **短期记忆（会话内）**：一次对话/任务内的消息与状态，放工作内存+checkpoint 落库，支撑断点续跑。
- **长期记忆（跨会话/跨用户）**：用户偏好、历史事实、领域知识。常见做法：**摘要**（把过去对话压缩成 summary 塞提示词）、**记忆压缩/提炼**、**向量库存长期记忆**按需检索。

**持久化选型（生产共识）**：checkpoint 用 **PostgresSaver / Postgres checkpointer**——状态快照按 thread_id 落 PG，断点续跑、回溯、可审计；比内存服务更可靠、能持久化到盘。长期记忆存结构化/汇总，或向量库+摘要。

**一句话记忆**：短期记忆=会话内状态 checkpointer 落 PG；长期记忆=摘要/压缩/向量检索；生产持久化选 **Postgres** 而非内存服务。

## 6. 模型型号 · 必背清单

> 干了很久却连自己用的模型型号都说不清，会立刻露怯。至少要能脱口而出项目用过的 3 个"厂商+型号"。

- **生成/对话**：OpenAI `GPT-4o`/`GPT-4.1`；Anthropic `Claude 4 Sonnet`/`Opus`/`3.7`；Google `Gemini 2.5 Pro`/`3 Pro`；国内 DeepSeek `V3`/`R1`、通义 `qwen-max`/`qwen3`、豆包 `doubao-pro`、智谱 `GLM-4`。
- **Embedding**：`bge-m3`（开源常用）、`text-embedding-3`。
- 说不准就报"厂商+系列+用途"，别报没把握的具体版本号。
- 价格/上下文以官网为准 → 见[专题 · 大模型 API 选型](#一大模型-api-选型与成本优化)。

**一句话记忆**：型号=厂商+系列+用途（生成/推理/embedding）；至少能报出项目里用的 3 个具体型号。

## 7. 多 Agent 的 State 怎么设计（Pydantic）

**设计原则**：
- **State 是多 Agent 共享的唯一"契约/黑板"**：所有节点读写同一 state，Pydantic 类型约束保证字段不跑偏。
- **按"层"切**：会话层（identities/messages）+ 任务层（当前步/计划/负责 agent）+ 业务层（领域实体）+ 共享层（进度/日志/审计/证据）。
- **reducer 合并（关键）**：同一 key 被多节点返回怎么并——追加用 `Annotated[list[X], operator.add]`，覆盖用普通字段，或自定义 reducer。
- **校验+持久化**：Pydantic 校验失败即报错可回退；state 可序列化→checkpoint 落 PG。

**示例 State（以"商家资质审核"多 Agent 为例，可报这些字段）**：```python
class QAState(BaseModel):
    # 会话/身份层
    session_id: str
    tenant_id: str
    messages: Annotated[list[Message], add]      # reducer 追加
    # 任务层
    intent: str                                    # 意图识别结果
    current_agent: str                             # 当前负责谁
    task_plan: list[str]                           # 计划/步骤
    done_steps: Annotated[list[str], add]
    # 业务层（领域实体）
    merchant: MerchantInfo                         # 资质信息
    review_status: Literal["pending", "pass", "reject"]
    evidence: list[SourceRef]                      # 引用定位
    # 共享/运维层
    tools: Annotated[list[str], add]               # 用过的工具
    error_log: Annotated[list[str], add]           # 容错记录
```

**面试讲法一句话**：State 分"会话/任务/业务/共享"四层，各 Node 写约定字段+reducer 合并不冲突，Pydantic 校验做边界；多 Agent 靠共享这一份 state 协同，再序列化落 PG 支撑持久化——能报出 `session_id/intent/task_plan/review_status/error_log` 这些字段就说明真做过。

# 第四部分 · 场景设计题（3 道带分案例）

> 3 道带计分的**工程排查/设计题**，是"一线 AI 工程师"能力考察的典型形态——给业务背景+症状，考排查顺序、根因定位、系统性防复发、让业务信任。每题按分数点答。

## 🏢 场景 1 · 企业知识库：文档更新后还在答旧内容（35 分）

> 背景：RAG 知识库问答已上线 6 周。本月 1 号更新退货政策（"7天无理由"→"7天无理由，已拆封商品除外"），当天上传新文档；但之后两周质检发现仍按旧政策答，拆封退货纠纷投诉上升。**代码、模型、prompt 均未改动。**

### 1) 定位顺序 + 最可能 3 个根因（15 分）

**排查顺序（先静态、后链路、再生成/记忆，成本低→高）**：
1. 文档是否真进库、旧版是否还在（数据源本身）——新文档有没有成功摄入？旧文档/旧 chunk 是否仍在检索范围？
2. 检索是否仍命中旧文档（索引/缓存）——embedding 索引有没有重建？检索结果有没有被缓存？
3. 生成/记忆层是否被旧口径污染——对话历史/长期记忆/prompt 里是否残留旧政策？

**3 个最可能根因**：
- **根因 A（最常见）：旧文档/旧 chunk 未失效**——新文档新增了，旧政策文档仍存在且被检索命中。
- **根因 B：向量索引未刷新 / 结果缓存没失效**——原文档更新但 embedding 库没重建，或命中与生成走了缓存，吃的是旧向量/旧结果。
- **根因 C：会话/长期记忆污染**——对话或长期记忆存了旧政策，模型拿着旧口径作答。

### 2) 每个根因的修复 + 验证（10 分）

| 根因 | 修复 | 证明修对的验证 |
|------|------|------|
| A 旧文档残留 | 文档带版本/生效时间戳，更新即失效旧版、删除或降权旧 chunk，检索按 `effective_date/version` 过滤 | 用"已拆封可以退吗"命中测试，应只返回新政策 chunk；黄金集回归断言答新 |
| B 索引/缓存未刷新 | 文档变更触发重索引，结果缓存 key 带 `doc_version`，更新即失效 | 检索看新 chunk 命中；清/换缓存 key 再问返回新口径 |
| C 记忆污染 | 事实类答案先查库再答、不依赖记忆；长期记忆加时间戳与"事实过期检测" | 无历史新会话 vs 带旧记忆会话对比均答新；控制变量 AB |

### 3) 自动化保障（10 分）
1. 黄金评测集+变更回归：每条文档更新自动跑"新旧互斥问题"集，断言答跟随最新版。
2. 文档变更追踪：摄入记录 `hash/version`，源变更自动重索引+失效旧缓存。
3. 一致性 Lint：检测库内互相矛盾声明，或用探测问题验证命中最新版本。
4. 元数据+引用：chunk 带 `effective_date/version`，答案强制带来源引用+时间戳；高敏事实强制检索、不依赖记忆。
5. 监控告警：跟踪"引用旧版本"比率+用户纠纷关键词（"已拆封"），异常自动告警。

## 🎧 场景 2 · 智能客服：转人工后客户要重新说一遍（35 分）

> 背景：电商客服转人工率 15%。用户投诉"转人工后还要重新说三遍"。质检发现转人工时只传了当前这句，历史对话与已收集信息全没带过去，人工处理时长上升 18%。

### 1) 转人工完整链路 + "上下文包"应含什么（10 分）
**链路**：机器人会话（全量状态持久化）→ 触发转人工 → **组装上下文包** → 传给人工工作台（工单/客服系统 API/webhook）→ 自动填充、可编辑。
**上下文包 ≠ 只有聊天记录**，应含：原始对话历史（多轮带时间戳）；已抽取结构化信息（订单号、问题描述、意图、槽位、脱敏后客户信息）；会话/服务元数据（session_id/customer_id/渠道/工单号）；已完成动作&未解决项（给过哪些方案、客户是否拒绝、待办）；敏感标记（已脱敏 / 需二次核验身份）。

### 2) 信息存哪、转人工怎么取/传（10 分）
- **存**：会话状态里以结构化 `dict`（`order_id/intent/slots`）持久化（会话 State/Redis/DB），**以 session_id 为主键**。
- **取&传**：转人工处理器在会话结束按当前 session_id 读取 → 组装进工作台模板/随工单调 API 带过去；**严格读当前会话，绝不跨会话取**。

### 3) 触发条件设计 + 误转 vs 漏转哪个代价大（8 分）
**触发（多信号融合）**：机器人置信度低 / 用户重复索求或明确要人工 / 多次问答失败 / 情绪不满 / 高危敏感场景（退款、金额投诉）自动转。
**漏转代价更大**：漏转=纠缠不解决→用户更愤怒、投诉升级、口碑受损、复杂 case 无人接；误转只是多占人工，可调阈值/分级路由优化。**宁可接受较高误转率，也别漏掉该转的**（尤其高危/情绪激烈）。用"先粗转后精路由"两类阈值平衡。

### 4) 会话隔离与脱敏（7 分）
- **隔离**：每会话独立 session_id 作为所有状态存取唯一主键，上下文包严格按 session_id 读，绝不给 B 塞 A 的状态。
- **脱敏**：传输与展示前打码（手机号/地址/卡号）；按角色最小权限只暴露必要字段；日志与工单同样脱敏；需明文走单独授权+二次核验。

## 📊 场景 3 · NL2SQL 问数：SQL 跑通、数字却不对（30 分）

> 背景：NL2SQL 系统 SQL 执行成功率 92%。财务问"上月销售额"→ 返回 1.2 亿；财务说该是 9800 万。系统生成 `SUM(amount) WHERE created_at>=上月1号`，而财务口径是 `SUM(amount) WHERE status!='refunded' AND type!='trial'`——**执行成功但语义错的静默失败**。

### 1) 为什么 EXPLAIN 发现不了？（8 分）
**EXPLAIN 只判断能否解析/执行/计划是否合理，不校验业务口径**。这句 SQL 合法能跑有计划，所以一路绿灯。**本质区别**：语法错/表不存在=**显式失败**（工具能捕获）；这类=**静默失败**在语义/口径层出错，工具仅凭 SQL 结构看不到"你算什么"，所以发现不了。一个错在语法/对象层，一个错在意图/口径层。

### 2) 除口径错外，这类静默失败还有哪些类型（7 分）
- join 错字段（`customer_id` vs `account_owner_id`/`billing_customer`）。
- 聚合语义错：`COUNT(*)` 当 `SUM` / 少 `DISTINCT` / 漏 status 过滤。
- 时间口径错：时区未归一、月初边界、`created_at`/`updated_at` 混用。
- 过滤漏/多/反向：漏 status、`NOT IN` 误写 `IN`、补多余过滤。
- null/空值处理错：未处理 NULL 使 SUM 偏小或行被吞。

### 3) 系统设计上怎么"系统性"防（10 分）
1. **口径沉淀为可复用定义**：业务指标固化成"度量库"（如销售额=SUM(amount) WHERE status≠refunded AND type≠trial），生成时优先映射已定义口径。
2. **约束生成+校验器**：schema 注入字段业务注释；金额/聚合类 SQL 强制校验必备过滤（如必须有 status），不过不放行。
3. **黄金校验集+回归**：每指标建"问题→正确 SQL/口径"断言集，上线/变更自动回归。
4. **结果一致性检查**：对返回数字与"同指标基准/上周"做异常值告警；白名单受约束生成比自由 SQL 更可控。
5. **全程留痕**：记录 query→SQL→数字→口径版本，可追溯纠偏。

### 4) 怎么让业务方信任这个数字（5 分）
- 给"口径=这个 SQL"：把生成条件和口径定义原样展示。
- 可下钻核对：数字可下钻到明细，业务自己验算。
- 透明与对标：显示口径定义/数据源/更新时间；与财务报表对账。
- 可信闭环：提供置信度/解释+"一键反馈纠错"，业务可纠正并记入黄金集——**透明+可验证+有纠错入口**比绝对值更能换信任。

## 一、大模型 API 选型与成本优化

> 速查：商用 API 选型思路、典型 RAG/Agent 请求吃多少 token、缓存降本（prompt caching 为核心）、面试怎么答有条理。**价格为 2026 量级快照，区分【已核实】/【未核实】，面试重点讲"机制与量级口径"，张口先说"以官网最新价为准"。**

### 1.1 选型核心思维
> **不是选一个"最好"的模型，而是按"任务复杂度×需求×预算"做分层路由。** 先看模型适配，再看价格量级，最后看上下文长度与后发能力（缓存/批量）。

### 1.2 国际三巨头（USD/百万tokens，2026-08 量级）

**OpenAI gpt-5.6 系列【已核实】**：sol（旗舰 $4/$20，缓存命中 $0.40）、terra（主流 $2/$12，$0.20）、luna（廉价 $0.20/$1.20，$0.02）。缓存命中价=输入价 0.1x。

**Anthropic Claude【已核实】**：Opus 5（$5/$25，缓存 $0.50）、Sonnet 5（$2/$10，$0.20）、Haiku 4.5（$1/$5，$0.10）、Mythos/Fable 5（限量旗舰 $10/$50）。Claude 4.6+/Sonnet 5 全 1M 上下文，按 standard 单价。Claude 4.7+ 新 tokenizer：**同样的英文文本 token 数约多 30%**。

**Google Gemini【已核实】**：Gemini 3.7/3.6 Flash 输入 $0.75/输出 $3.75（促销至 2026-12，2027 起 $1.5/$7.5）；Gemini 3.5 Flash $1.50/$9.00。**输出价含 thinking tokens**；Google 的 context caching 额外收**存储费**（$0.5~1/MTok·小时），别家无这笔。

### 1.3 中国厂商
**DeepSeek【已核实】**：deepseek-v4-pro 平峰输入 $1.32/输出 $3.96，**缓存命中输入仅 $0.044（约未命中的 3.3%，比国际 0.1x 更狠）**；v4-flash $0.44/$1.32。**有峰谷价**：高峰时段翻倍、其余减半 → 可错峰省钱。1M 上下文、支持 thinking/non-thinking。
**通义 / 豆包 / 智谱【未核实，以官网为准】**：qwen-max/plus/turbo、豆包 seed 系列（国产里偏便宜、中文性价比高）、GLM-4 系列 flash 档很便宜。三家价格页 JS 渲染，务必以官网为准确价。

### 1.4 选型对比思路（一张表）

| 维度 | 怎么看 |
|---|---|
| 模型分层 | 贵旗舰 vs 主流 vs 便宜 → 按任务难度路由 |
| 价格量级 | 输入通常为输出 1/3~1/5；中文比英文更耗 token |
| 上下文长度 | 自研 1M 已普及；长文档/长历史选 1M |
| 缓存友好度 | OpenAI/Anthropic/Google 0.1x，DeepSeek ~3% |
| 后发优惠 | Batch -50%、Fast +2x、off-peak、数据驻留+10% |
| 生态&合规 | 国内业务/数据不出境→国产；全球/合规→国际；成本敏感可错峰→DeepSeek |

> 一句话选型：**"先按任务复杂度把流量分档，便宜模型扛海量简单请求、贵模型只留难题；再叠加 prompt caching + batch + 分层路由控成本。价格变化快，具体一律以官网最新价为准。"**

### 1.5 成本构成 / Token 消耗量级

**Cost 从哪几块来**：
1. 输入+输出分开计费（基础大头）。
2. 缓存写/读：首次写按 1.25x~2x，后续命中 0.1x~0.03x（降本关键）。
3. 工具调用 overhead：每声明工具吃 token；启用工具会塞专用 system prompt（Claude Sonnet 5 约 354~474 token）。
4. 服务器工具：web search 约 $10/1k 搜索；Google 缓存额外收存储费。
5. 多 agent×多步：每一步回传上一步输出+越长历史 → 输入随步数线性膨胀，N×M 约成本翻 N×M 倍。

> 记忆：**1 token ≈ 4 英文字符 ≈ 0.75 英文单词**；**中文约 1 字 ≈ 1.5~2+ token，比英文更贵**。

**典型 RAG 单轮 token 量级**：系统提示几十~几百；工具定义每工具几十~几百+专用 prompt 300~600；**检索注入上下文（top-k 5~10 段）每段 500~1500 → 共 5k~15k，最肥一块**；对话历史每轮几百~几千；输出 500~1500/次。
→ 一次普通 RAG 请求 input 约 **5k~20k token**，用 Sonnet5（$2/$10）约 1~4 分钱；Opus5 约 3~10 分钱。**真正烧钱的是高并发×长上下文×多步多 agent，不是单次。**

**Agent 多步成本膨胀对策**：只传必要残差/增量、历史做阶段摘要(compaction)而非全量回灌、能 batch 的离线化。

### 1.6 缓存命中优化（面试最想听）

> 核心一句话：把不变的"系统提示/工具定义/共同前缀"放请求最前并打缓存标记，命中后以远低于输入单价复用 KV 缓存，省 prefill 计算和钱。

**原理**：推理输入要过 **prefill**（把整段 prompt 算一遍 KV cache）才进入生成。变长/动态内容每次都要重新 prefill；**不变静态块如果连续多次请求前缀完全相同，厂商可前缀匹配+复用已算好的 KV cache**，只对变化后缀做 prefill。**铁律：把不变的东西放最前且连成共同前缀，把会变的放最后；顺序 tools→system→messages，tools 变会连带失效其后整段缓存。**

**价格（【已核实】）**：缓存命中(读) 0.1x（DeepSeek ~3.3%）；Anthropic 写入 5min=1.25x、1h=2x；回本条件：5min 缓存写 1 次后第 1 次命中即回本；最低可缓存长度 Sonnet5≥1024、Haiku4.5≥4096、Opus5=512；Google 命中 0.1x+另收存储费。Anthropic 官方示范：Opus5 一次会话 50k 输入+15k 输出≈$0.705，其中 40k 走缓存命中≈$0.525（省 25%+）。命中判定看 `usage.cache_read_input_tokens > 0`。**并发注意：首个请求返回前缓存尚未建立，需等第一枪打完。**

**可落地降本清单（由浅入深）**：
1. 缓存静态前缀（system+工具定义+固定背景打共用前缀+cache_control）。
2. 把会变的放最后（检索文档/用户新消息/最新几轮）。
3. 分块缓存断点，让历史部分尺寸不变可命中。
4. 结果缓存：幂等/可容忍陈旧的 query 直接回放上次输出，推理成本→~0（处理时效与一致性、TTL/版本键）。
5. 语义/向量检索缓存：相似 query 先查缓存再决定要不要真检索。
6. 减少 token 本身：精简 system；RAG top-k 截断；长历史做阶段性摘要；工具懒加载（只注册本轮用到的）。
7. 模型分层路由：简单走便宜快模型，复杂才上旗舰。
8. Batch API：非实时离线任务 -50%。
9. 错峰：蹭 off-peak 半价。
10. 度量监控：埋点 cache hit rate、token 明细，定预算告警。

> ⚠️ KV cache 与 prompt caching：KV cache 是推理服务内部缓存每层 attention 的 Key/Value 的**底层机制**；厂商把它对用户包装成 **prompt caching** 并给 0.1x 命中价。**不要混为结果缓存**（结果缓存不调模型）。

### 1.7 面试四段式答题骨架

1. **先讲定价模型构成**：input/output 分开按百万 tokens 计费；+缓存写读+工具 overhead+服务器工具；多 agent 多步放大。具体以官网为准。
2. **再给典型请求量级**：普通 RAG input 约 5k~20k、输出几百~1.5k；system+工具定义几百，检索 top-k 最大头；多 agent 回灌历史近乘 N×M。
3. **落到降本三件套**：①模型分层路由，便宜扛量；②prompt caching——不变前缀放前打 cache_control，命中约 0.1x，命中即回本；③结果/语义缓存+精简上下文+batch(-50%)，埋点看 cache hit rate。
4. **点止损与工程**：会看 usage 字段、给历史做摘要、只传必要增量、预算告警。

**数字抓手**：`1 token≈4字符`；`prompt caching 命中≈输入价 0.1x（DeepSeek ~3%）`；`写一次第1次命中回本`；`batch -50%`；`中文比英文更耗 token`；`Opus5 50k/15k≈$0.705→缓存后 $0.525`。

## 二、MCP 与 Skill

> MCP（Model Context Protocol）是 **Anthropic 2024-11 提出的开放协议**，让 LLM 通过标准接口（JSON-RPC）调用外部工具/资源/数据源，把"模型该有的能力"从模型本身下沉到服务端，一次接入、多客户端复用。

### 2.1 先懂 MCP 三个面（面试必答）
- **Host**：Claude Desktop/Claude Code/Agent 框架，负责调度。
- **Client**：Host 与 Server 之间建立连接、发起调用的一端。
- **Server**：暴露能力的一方，实现工具/资源/提示词。
- **三种原语**：`tools`（可调用函数，带 schema）、`resources`（可读数据）、`prompts`（可复用提示模板）。
- **传输层**：本地 `stdio`（子进程）+ 远程 `Streamable HTTP`。
- **生态**：OpenAI、Google 已采纳，成为事实上的可互操作工具层标准。官方 SDK 覆盖主流语言。

### 2.2 高频 MCP 参考服务器（面试记忆点）
官方参考实现：Filesystem（受控文件读写）、Git、Fetch（抓网页转文本）、Memory（知识图谱记忆）、Time（时间时区）。已归档多因被社区专责接管（GitHub/Slack/PostgreSQL 等）。

**按场景盘点高频实用 MCP**：
| 场景 | 高频 Server/工具 |
|---|---|
| 文件/代码 | Filesystem、Git、GitHub、GitLab |
| 网页/内容 | Firecrawl、SearXNG、Fetch、Puppeteer/Playwright |
| 数据库 | PostgreSQL、SQLite、Redis、DuckDB（多数默认只读） |
| 办公协同 | Notion、Slack、Google Drive、Linear、Jira |
| 开发/部署 | Docker、Kubernetes、Playwright、各云厂商 |
| 记忆/知识 | Memory、Chroma/Deep Lake 向量库 |
| 搜索 | Brave Search、Perplexity、Google 系 |
| 内容创作 | 图片/视频/文档排版 AI 服务 |

> 📌 国内生态 `[存疑]`：阿里百炼、百度千帆、腾讯等据称有 MCP 布局，但具体清单/稳定性未逐一核实，被追问只定性答"在跟进"。

**找高频清单**：官方 Registry `registry.modelcontextprotocol.io`；社区 Smithery、mcp.so、PulseMCP。

### 2.3 skill + CLI 替代 MCP

**拆开三个词**：
- **Skill**：打包"指令+知识+校验脚本"让 agent 复用的能力包。本质把"怎么做某件事的 know-how"写进普通文件，agent 能读、能照着执行、能跑 script 自校验。
- **CLI**：命令行工具，各开发工具基本都有（gh、curl|jq|grep、npm…），天然可组合。
- **组合思路**：SKILL 注入怎么做（知识/提示），CLI 直接动手（执行），跳过 MCP 服务层——尤其单人/轻量/本地。

**skill vs agent（面试最直接一句）**：
- **Skill = 固定的 SOP 流程**：把"怎么做"写成确定步骤，追求稳定、可复用、可控可回归。
- **Agent = 会思考、会规划、自主决策的执行体**：基于环境/观察动态决策调不同工具与流程，会计划、会试错、会兜底。
- 一句话：Skill 是"怎么做的标准动作"（稳定复用），Agent 是"怎么做最合适的决策者"（思考/规划）；一个求确定性，一个求自主性。生产中常以 Agent 当大脑、把单步动作做成 Skill 供其调用。

**skill 内部机制（多想一步）**：
- Skill = 一个目录（能力包）：核心 `SKILL.md`（frontmatter 写 name/description，正文写步骤/规范/范例）+ `scripts/`（可执行校验脚本）+ `references/`（补充知识）。
- **被发现/加载**：agent 启动扫描技能目录，读每个 skill 的 description 建索引；**任务命中描述才把 SKILL.md 按需加载进上下文（不是全部常驻）**——description 写得好不好决定命中率。
- **执行**：skill 正文指导一步步做；校验时 scripts 跑一遍验证结果，agent 据此纠正。
- **和模型关系**：skill 本质是注入上下文的知识/指令，不微调模型、不依赖网络，纯本地文件可版本化。

### 2.4 优劣 & 判断框架

**Skill+CLI 优势**：轻量（零常驻服务）；无暴露面（不对外开 HTTP，无 MCP 引入的攻击面）；复用已装工具管道；可注入领域判断；非工程师易上手。
**Skill+CLI 短板**：无统一标准（CLI 鉴权/flag/报错不一）；不可被外部复用；依赖本地环境；跨工具生态弱，缺会话级细粒度权限。

**MCP 优势**：标准化协议，统一 `tools/list`/`tools/call`；写一次多客户端用；可服务化共享；OAuth+会话级 `allowedTools` 细粒度授权（后台无人值守 agent 刚需）。
**MCP 短板**：部署/配置重；网络/鉴权风险面；调试难；大文件传输别扭。

> 判断框架（可直接背）：**它们不是互相替代，是解决不同问题**——Skill = 团队/个人过程 know-how 与判断；CLI = 开发者构建/黑客模式；MCP = 已鉴权 SaaS 接入 / 企业 / 无人值守 background agent。一句话：**"CLI 和 MCP 给 agent 工具，Skill 给 agent 用好工具的上下文。"**

| 维度 | Skill | CLI | MCP |
|---|---|---|---|
| 本质 | 过程 know-how | 开发者工具链 | 已鉴权 SaaS 接入 |
| 最佳用户 | 所有人 | 开发者 | 企业/后台 agent |
| 鉴权模型 | 无 | 本地令牌 | 内置 OAuth |
| 访问控制 | N/A | 难会话级隔离 | allowedTools/网关 |
| 可组合性 | N/A | 原生管道 | 靠"结果落盘" |
| 凭据 UX | N/A | 终端命令 | 一键 UI |

**选型答案（面试常考"给你 Agent 接工具，选 MCP 还是写脚本？"）**：看场景——单机/本地/自用倾向 CLI+Skill；要共享、要权限、要后台无人值守、要给非工程师 → MCP。

### 2.5 补充：工具执行与沙箱（能说两句）

Agent 会让模型执行工具/生成代码（文件操作、跑脚本、访问网络），不加隔离可能改坏本地或泄数据。**沙箱形态（隔离强度低→高）**：
1. 权限/授权层：工具调用白名单、危险操作二次确认。
2. 进程/文件系统隔离：受限子进程/临时目录、限路径/网络。
3. 容器化沙箱（生产主选）：Docker/gVisor/Firecracker，窄文件系统+无/受限网络+无宿主权限。
4. 网络隔离+审计：沙箱内禁外连或走代理白名单，日志留痕可回放。

> 一句话记忆：Agent 执行工具/代码要落在沙箱：权限白名单+容器化隔离（Docker/gVisor）+网络受限+审计日志；单机 CLI/Skill 也要拍照回退，生产无人值守更必须沙箱兜底。

## 三、AI-Coding 工具对比

> 主流 AI-Coding 工具大致三类：**终端编码代理**（Claude Code、Codex CLI、Qwen Code、Aider）、**IDE 编辑器**（Cursor、Windsurf、GitHub Copilot）、以及更泛化的**应用/通用智能体**（OpenClaw、Hermes、DeepSeek-Harness 等）。面试讲清"它们是不是同一物种"比罗列功能更重要。本领域演进快，✅标已核实 / ⚠️标存疑，面试只把确认的当结论说。

### 3.1 终端编码代理（CLI Agent)

**Claude Code（Anthropic）**：终端里跑起来的 Agentic 编码代理，能读整个仓库、跑命令、改文件、提 PR。关键：agentic/长上下文/多文件；连 GitHub/GitLab 从 issue 到 PR；Dynamic workflows（拆 10~100 并行子代理）；Agent view；Routines；Computer use。优点：完成度高、上下文长、能 handle 大仓库。缺点：**贵、易自作主张需审查**。定价（✅2026）已并入 Pro($20/月)/Max($100起)——别说过时版本。一句话：**"终端里最能打的 agentic 编码代理，最强也最贵。"**

**Codex（OpenAI）**：**本地 CLI + 云端并行**两条形态。Codex CLI 本地跑；Codex Web/App 云端沙箱并行。优点：本地免费 CLI 低门槛、云并行批量。缺点：绑 OpenAI 账号计费、本地与云端有落差。差异化=**云端沙箱+并行、代码审查**。

**Qwen Code（阿里/通义）**：开源 agentic 编码 CLI + Qwen3-Coder 模型（480B MoE、35B active、256K 上下文可延 1M）。优点：**开源、可控、可私有化、中文好、性价比高**。适合合规/私有化/成本敏感团队。

**Aider**：老牌纯 CLI chat-with-repo，git diff 治理、可接多家/本地模型。最克制、git 友好。

### 3.2 IDE 编辑器

**Cursor**：AI 原生编辑器（VS Code 分支），补全+Agent 一体，开箱即用。**GitHub Copilot**：补全之王，深度绑 GitHub，Agent 是后补的课。**Windsurf**：AI IDE（原 Codeium），强调 Agent+流式补全，UI 口碑好、生态盘小。（⚠️功能点为印象级，仅当常识带过。）

### 3.3 应用智能体 / 通用 Agent（重点：说清"和编码代理不是一回事"）

> ⚠️ 面试关键：Claude Code/Codex 是**编码 agent**，但 OpenClaw、Hermes、DeepSeek-Harness 是**更宏观的应用/通用智能体或框架**，别混进"AI 编码工具"堆里，要能单拎出来各讲定位。

## 五、并发与限流 · 工程化

### 5.1 先定义"并发"（面试口径）
问"能处理多大并发"，**先说量化单位**：一般指 **QPS（每秒请求数）**或 **QPM（每分钟）**。再补一句支撑：单进程协程单线程事件循环能撑 **1w~10w QPS**（视请求耗时/IO 占比），toB 够用；要横向扩就加多实例+网关负载均衡。一句话：并发≠"同时做几件事"，说清 **QPS/QPM 量化口径+实际值**才显懂工程。

### 5.2 为什么要限流
- 保护自己：防突发流量把服务/DB/大模型 API 打爆。
- 保护下游：避免恶意/异常请求刷爆下游（尤其按量计费的大模型 API）。

### 5.3 常见限流算法（能背能讲）
| 算法 | 思路 | 特点 |
|---|---|---|
| 计数器（固定窗口） | 单位窗口内计数，超阈拒绝 | 简单；窗口边界易突发 |
| 滑动窗口 | 细粒度统计最近 N 秒 | 更平滑，开销略高 |
| 漏桶 | 请求入桶按固定速率流出 | **限制速率、能削峰**；处理突发不够快 |
| 令牌桶 | 固定速率加令牌，请求取令牌 | **允许一定突发（桶容量），工程最常用** |

### 5.4 落地形态（分层限流）
1. 网关层：Nginx `limit_req`/`limit_conn` 做 IP/接口级限流。
2. 应用层：Python 用 `asyncio.Semaphore` 控"同时在飞"协程数（限并发）、令牌桶/漏桶（限速率）。
3. 分布式限流：多实例用 Redis+Lua 原子操作共享计数器（令牌桶常落 Redis）。
4. 对接大模型 API：对方有配额/每分钟限制，客户端做**重试+退避(backoff)+并发控制**，防 429。

**一句话记忆**：并发先说 QPS/QPM 口径；限流令牌桶（允许突发）最常用，分网关/应用/分布式三层；Python 协程用 `asyncio.Semaphore` 控并发、令牌桶控速率；对接大模型 API 配退避重试防 429。

## 六、Nginx 代理与负载均衡

**Nginx 是什么（一句话）**：高性能 Web 服务器/反向代理服务器，也常做负载均衡和访问控制，生产里通常是流量入口那一层。

**三个核心作用**：
1. **反向代理**：隐藏后端真实服务，客户端统一打 Nginx、由它转发；可配合静态资源直接返回减小后端压力。
2. **负载均衡**：横向扩展与高可用。策略：轮询（round-robin）、权重（weight）、IP/会话 hash（粘性会话）、least_conn（发当前连接最少）。
3. **访问控制/限流**：`limit_req` 按速率限流、`limit_conn` 按连接数限流、`allow/deny` IP 黑白名单——正是"网关层限流"实现。

**面试口径**："高并发对外，前面挂 **Nginx 做反向代理+负载均衡+limit_req 限流**，把流量控住再进服务，实现横向扩容与非业务攻击兜底。" 若不负责细节可补："生产是 Nginx 统一入口，负责代理/负载/访问控制，具体配置运维维护，我清楚链路"——既懂又不越权。

**一句话记忆**：Nginx = 高性能反向代理+负载均衡（轮询/权重/ip_hash/least_conn）+访问控制（limit_req/limit_conn）；做流量入口、挡第一层限流，配合后端横向扩容。

## 七、模型部署 · vLLM

**vLLM 是什么（一句话）**：高吞吐、省显存的大模型推理/部署框架，业界部署开源 LLM 最主流方案之一。**会被问薪资的点：PagedAttention。**

**核心卖点（能讲 3-4 条）**：
1. **PagedAttention 显存优化**：把 KV Cache 按"页"分配，像操作系统虚拟内存分页，显著提高显存利用率、支持更大 batch。
2. **Continuous batching（连续批处理）**：来一个请求就动态插入当前 batch，把吞吐打满。
3. **兼容 OpenAI 接口**：服务暴露 `/v1/chat/completions` 这类 OpenAI 兼容 API，上层切换零改动。
4. **大模型扩展**：张量并行（Tensor Parallelism）拆超大到多卡；支持多种量化（AWQ/GPTQ/FP8）。

**部署形态**：典型 Docker+GPU，配模型权重与量化，一条命令/编排（K8s/docker compose）拉起；配 CUDA/FlashAttention。分工："我在应用/Agent 层通过 OpenAI 兼容接口调用，底层是 vLLM 服务化；显存/切卡/压测是运维负责，我清楚链路但不越权。"

**对比（一句话取舍）**：成熟稳定生态大→vLLM；极致推理延迟/绑 TensorRT→看业务；长上下文调度灵活→可提 SGLang。

**一句话记忆**：vLLM=主流开源 LLM 部署框架，**PagedAttention 省显存+Continuous batching 拉吞吐+OpenAI 兼容接口**；即使不是自己部署，也要能报出"生产用 vLLM 起的服务"。

### Q7. 你说 RAG 用 Milvus？
Milvus 是开源向量数据库，存 embedding+标量元数据，支持 dense/sparse/multivector 混合检索与混合重排，服务化、可横向扩。

### Q8. 知识库怎么搭？A 客户看不到 B 客户的权限怎么做？（关键：隔离必须在检索前，不能检索后过滤）
- **数据归属层**：每个文档/块带 `tenant_id` 作为 Milvus 标量字段；检索时用表达式 filter 强制 `tenant_id==当前租户`，向量检索只在授权子集内进行。
- **权限层（RBAC）**：用户→角色→权限；文档/块按密级与可见范围授权；检索前算好用户可访问集合当 filter 传入。
- **为什么不能事后过滤**：先全库检索再删非授权结果，可能泄漏且浪费（向量里非授权内容已被模型"看到"）。
- 补充：分级隔离（租户/项目/文档/块）、脱敏、审计。

### Q9. LLM-Wiki（Karpathy 观点）
> 核心：一个**个人知识库的构建模式**——不是即时检索式 RAG，而是让 LLM **增量地构建和维护一份常驻、互相链接的 wiki（markdown 文件）**，放在"你"和"原始资料"之间。知识**编译一次、持续更新（复利）**，而不是每次提问从零重建。

**一句话对比**：RAG = 每次提问从原文档现成检索、答完即散；**LLM-Wiki = 把读过的知识沉淀成持续变厚的结构化 wiki，交叉引用/矛盾/综合提前做好**，像复利。Manifest 金句："**Obsidian 是 IDE，LLM 是程序员，wiki 是代码库**"。

**三层架构**：①Raw sources 原始资料（只读不可变、真相源）；②Wiki 层（LLM 全权维护的 markdown 目录，建页/建链/保持一致，你只读它写）；③Schema 配置层（告诉 LLM"wiki 怎么组织/什么约定/流程"的文档如 CLAUDE.md——**这是让 LLM 当"有纪律的维护者"而非通用聊天**的关键）。

**三个操作**：Ingest 摄取（丢新源→LLM 读、写摘要页、更新 index 与关联页、记日志，一篇常动 10~15 页）；Query 查询（先查 index 再深读、带引用综合回答；好答案可回填成新页）；Lint 体检（周期查矛盾、旧结论被推翻、孤儿页、缺交叉引用）。中规模（~100 源）可不用向量检索；大规模再用本地 hybrid 搜索。

**Why 点睛**：累的不是读/想而是**记账**（更新交叉引用/摘要/标矛盾）——**LLM 不会烦、不会忘、一把改 15 个文件 → 维护成本≈0**。人类管选源/提问/思考意义，LLM 管其余。精神源头可溯 Bush 的 **Memex(1945)**。

**一句话记忆**：LLM-Wiki ≠ 每问必查的 RAG：让 LLM 把读过的东西**沉淀成常驻互链的 markdown wiki，编译一次持续更新**；Obsidian 是 IDE、LLM 是程序员、wiki 是代码库，维护成本≈0。

### Q10. 用过 Obsidian 吗？
本地 Markdown 知识库、纯文本可版本管理、双链+图谱、插件生态（Dataview/Canvas/模板），可当主动学习与复盘载体。顺带展示"有笔记习惯、输出习惯"。

### Q11. bge-M3 + RRF？召回率 60%→78% 怎么做到？78% 怎么算？
**bge-M3**：擅长多语言/多功能的 embedding 模型，同时输出 **dense（语义）+sparse（词法/BM25 式）+multi-vector（ColBERT）** 三种表示，适合做召回增强。
**RRF（倒数排名融合）原理**：把多路检索结果（dense+sparse+BM25）**按名次而非分数**融合；每篇文档得分=Σ `1/(k+rank_i)`，k 通常 60。**为什么用名次不用分数**：各路分数量纲/分布不同无法直接相加；名次是统一的、鲁棒——"无监督、不依赖分数归一化"。
**60%→78% 怎么来**：更好的分块 + 混合召回 dense+sparse + RRF 融合 + Rerank + 评估迭代。
**78% 怎么"算"（追问重点）**：需**带标注的评估集**（问题→正确文档/块）；**Recall@K**=正确答案的块是否出现在检索结果前 K 名=命中数/总数；模型输出≠原文时，**按原始文档块 ID/锚点对齐**标注，不是用改写后文本匹配——评估"检索有没有把正确原文块召回"，与模型措辞无关；自动脚本统计可回归对比方案。

### Q12. 高并发限流和高可用（没弄过怎么接）
**限流**：网关 limit_req/limit_conn+令牌桶+应用层 `asyncio.Semaphore`+Redis 分布式限流；对接大模型 API 做客户端退避重试。
**高可用核心**：多副本+Nginx 负载均衡+健康检查自动摘除；**无状态化**（session/状态外置 PG/Redis，Agent 任意实例接管）；兜底（熔断/重试带退避/超时/降级）；容量（压测定阈值、K8s HPA 自动扩缩容、热备容灾）；可观测（日志/指标/告警、SLO 联动）。
**应对"没弄过"**：别只说没弄过——**给设计思路**+一句"生产有一部分由运维兜底，但方案我清楚"。面试官要的是你有这层意识。

### Q13. subagent 是运行时临时生成的，怎么保证权限可控、又不影响体验？
**核心矛盾**：事前把每个 agent 权限定死 vs 产品里 subagent 动态生成、无法授权时分区。
**权限可控（deny-by-default+作用域继承）**：最小权限+默认拒绝（默认无权限，任务明确需要才放）；作用域（scope）继承（只继承父 Agent/任务受限作用域，一次性、只读优先）；敏感操作审批/沙箱；审计/可回放（记录用了哪些工具、读写什么；超时/异常自动回收）。
**不影响体验**：策略化自动放行（白名单/规则命中直接放，才需人点的是高风险资源）；异步审批（不阻塞主流程，先继续后台追认，失败给降级提示）；透明可见（前端展示正在做什么/进度/可中断）。
一句话：权限=默认拒绝+作用域继承+审批/沙箱+审计回收；体验=策略自动放行+异步审批+透明进度——**权限收紧不等于卡死用户，靠的是策略和异步化**。

### Q14. 知识蒸馏 200ms→10ms，怎么实现？能否用来给 API 提速？
**思路**：把大模型当 teacher，在标注/生成数据上训练小模型 student，输出/标签做 schema 对齐，配合量化或小模型蒸馏；核心是"**teacher 的软标签+对齐小模型**"，约降一个数量级延迟。
**迁移到业务 API**：把高频、简单、必须快的子任务（分类/信息抽取/意图）**蒸馏到小模型或专用小 LLM**；复杂任务仍走大模型——**"快的小模型承接简单短链、大的承接复杂长链"**，按延迟与质量分级路由。
**"怎么算 200→10ms"**：端到端延迟（模型调用到返回）在**同一硬件/同量级请求**下压测，取 **P50 或 P99**，AB 对比蒸馏前后；同一评估集验指标不掉。

### Q15. 你用的 Claude Code/ChatGPT 讲背后厂商/付费（容易被问穷的账）
- **分清厂商**：Claude Code→**Anthropic**；ChatGPT→**OpenAI**；两家不同模型、不通用。
- **付费两种**：**订阅（按月）** vs **按量 API（充值/token 计费）**。Claude 订阅 Pro($20/月)/Max($100 起)；OpenAI 也有订阅档。
- **成本口径**：订阅适合高频个人开发（含工具额度）；API 按量适合自动化/服务化，可控制上限。**讲自己怎么控制成本的**（预算上限/缓存/少写 token）比报"买几个账号"更稳。

### Q16. 通用个人/经历类答题要点
- 同学/团队分工类问题：客观、不贬低，突出**分工互补**而非"我比他强"（他负责 X、我负责 Y，强调配合与整体完整性）。
- 兴趣爱好：要真实、最好带一点和岗位相关但有烟火气（协作复盘、折腾工具、写笔记），别背模板。

## 二、项目叙事与简历表述

> 解决两个常卡的点：**①"项目中遇到什么困难"不知从哪说；②简历/口述全是概念词、不够真实。**给框架+可直接套用的清单与改写示例。

### 2.1 「遇到的困难」从哪入手——顺着整个业务流程脑暴
别凭空想"难不难"，**从业务闭环走一遍，能想到问题、想到方案，全都是"困难"**：
- 工具调用怎么排查解决；skill 怎么调用/加载；MCP 有没有遇到配置/鉴权/网络/超时。
- 输出不稳定（JSON）→ function call+pydantic+提示词约束+错误重试。
- 用的什么模型、**具体型号**要能报。
- 并发怎么样（协程/单进程/限流怎么撑）。
- 有没有小模型/蒸馏做快路径。
- 调用出错怎么兜底（超时/降级/缓存/重试退避）。
- 记忆上下文怎么持久化。
- 各个节点出错怎么回退/容错（失败重试、回退上一状态、checkpoint 断点续跑）。

> 心法（能直接说的立场）：**"问题+解决方案，就是遇到的困难。我不是没困难，而是每个节点都想好了怎么解——工具失败重试、JSON 四件套、并发协程+限流、记忆落 PG、节点回退容错。"**

### 2.2 单个困难怎么讲（STAR 变形）
**背景 → 卡点（具体、真实）→ 我的解（方案/取舍/为什么这么选）→ 结果（量化）**。别只喊难，讲"怎么想、怎么解、为什么换选型"，面试官要的是解决问题的过程。有取舍更好："我们最初 X，但遇到 Y，改用 Z（代价是…）"——体现权衡。

### 2.3 简历表述具体化：概念 → 业务（动词+数据+手段+结果）

改写法：`动词` + `数据规模` + `具体技术手段` + `元数据/引用维护方式` + `（结果量化）`。

| 概念表述（虚） | 业务表述（实） |
|---|---|
| "基于 Milvus 构建电商向量知识库" | 将 N 个文本 Chunk 的 embedding 写入 Milvus，按文档/页码维护元数据过滤与引用定位 |
| "做了 RAG / 检索优化" | 对 PDF/Excel 图文表分块、异构块带 `(type,page,索引)` 元数据；混合召回 dense+sparse+RRF+Rerank，Recall@K 由 60%→78% |
| "搭了 Agent" | 用 LangGraph 编排多步 Agent，意图识别→工具/MCP 路由→function-call 结构化输出，含 JSON 四件套与 Postgres checkpoint 记忆持久化 |
| "用协程做高并发" | 单进程协程支撑 1w~10w QPS，LLM 走异步、同步按 IO/CPU 分流，DB 连接池满足并发 |

**原则**：动词开头+数字+技术手段名+元数据/机制+可量化结果；**少形容词（强/高效），多数据与机制**。

### 2.4 项目介绍框架
- **需求 → 数据 → 方案 → 难点 → 结果**。
- 或标准四段：**项目背景 → 个人负责部分 → 项目流程 → 项目成果**。
- 两者等价；关键是用"具体化改写"往里填肉，别只剩框架空转。

## 三、AI 工具个人项目 & 低代码案例

> 面试两次被问"有没有用 AI 编码工具自己做小项目？""有没有做过 Coze/Dify 项目？"——都要卡住。这篇给成套剧本：**挑 2~3 个真能顺下来的讲，别编太远。**

### 3.1 vibe coding 个人小项目
原则：**别挑你不会的**，选能讲清"输入→处理→输出/技术栈/踩过什么坑"的，语气是"用 AI 帮我做生活/工作里一个具体小工具"。

**候选池（选 2~3 个）**：
1. 批量文档转 Markdown/抽表格（AI 写脚本统一转 md、分 chunk、抽表格）。
2. 个人知识库（Obsidian）自动化：抓取/剪藏去重、按模板归类、定时整理 ← 最真（Web Clipper+agent 维护 wiki，扣 LLM-Wiki）。
3. 一键 Markdown→PPT/海报（Marp）。
4. 本地 RAG 问答 bot（bge-m3+Milvus+检索，和简历 RAG 呼应）。
5. 数据清洗/报表脚本（pandas 洗 CSV、出图）。
6. 群/客服小机器人（接大模型 API+状态管理+限流重试）。
7. 网页/价格监控（curl+cron+LLM 总结推送）。

**怎么讲不虚**：哪怕很小，也按"需求→用了什么工具和模型→关键技术点（输入/处理/输出/踩了什么坑/怎么兜底）"交代清楚；**讲"踩过的一个坑你怎么解决"比讲功能更可信**。

### 3.2 低代码平台（Coze/Dify）案例
被问"做过 Coze 项目"时，挑一个能讲清"搭了什么流、解决什么问题"的：知识问答/客服机器人、日报/周报自动生成、文档问答/总结、数据查询助手、群运营机器人。
**加分句式**：'低代码平台我懂的是**背后的原理**（RAG/工作流/工具调用/JSON 约束），所以即使没在 Coze 上堆很多，也能讲清怎么搭、怎么调优——toB 自建就是用这些同样思路'。

### 3.3 60 秒口述剧本（可直接背，挑有交集的认领）
> ⚠️ 诚实第一：**没真做过的项目，投前拿工具跑一遍再认领**，被追问细节才站得住。

**A. Obsidian 知识库自动化（vibe coding，最稳）**：让 LLM 当"整理知识库的程序员"，新文章按统一模板生成摘要、自动归类、补双链、更新 index。技术要点：Markdown+LLM 抽信息/打标签/写页/更新 index；Web Clipper 收源。踩坑：一开始 LLM 乱建文件/双链乱 → 给一份 `CLAUDE.md` 约定"目录结构+命名规范+必须更新 index"。收尾：这就是"LLM-Wiki 模式"的个人实践。

**B. 批量 PDF/Excel → 结构化 Markdown**：AI 写解析脚本，文本直接提、图片/表格单独提取带位置信息，输出结构化文本（文本块/图片块/表格块带 type/page/索引元数据）。踩坑：全量转文本把表格版式打乱、检索定位不准 → 分块提取保留元数据。收尾：这是生产 RAG 前置解析的 mini 版。

**C. 本地 RAG 问答**：文档分 chunk+bge-m3 向量化+检索 topk+大模型生成带引用回答。踩坑：纯向量漏词法命中 → 加 dense+sparse 混合+RRF 融合。

**D. 客服知识问答 bot（Coze 低代码）**：传 FAQ/文档建知识库+大模型节点生成+带引用来源。重点能讲背后原理（分块/检索/引用定位），不只拖节点。

**E. 日报/周报自动生成工作流（Coze/Dify）**：多人/多源输入→模板变量→LLM 汇总成结构化周报→定时推送。结构化输出和触发是关键。

## 四、ToB / ToG 项目 · 甲方沟通要点

> ToB/ToG 项目里，开发或技术负责人免不了跟甲方沟通项目落地细节，事无巨细、沟通频繁。面试官借此考察项目落地与沟通协作，不只写码。

**沟通四大类**：
| 类别 | 要讲清的细节 |
|---|---|
| 数据 | 数据源/格式/脱敏/权限/样例数据谁提供、怎么拿、缺数据怎么办 |
| 实现方案 | 技术选型、对接方式（API/SDK/中间件/文件交换）、改动面、工期 |
| 对接平台 | 对方系统怎么打通：鉴权、协议、字段映射、联调环境、谁做联调 |
| 交付标准 | 验收指标、交付物、文档、培训、维保期、变更怎么控 |

**面试怎么讲（别只报"我做了 XX"）**：讲清一个完整闭环：**需求对齐 → 数据/平台前置条件确认 → 方案评审 → 联调 → 验收 → 移交文档/培训**。有货的加分点是**处理和甲方的冲突/变更**：需求变更怎么评估影响、怎么拒绝或分级、怎么书面留痕。一句话立场："我不仅能写代码，还能把项目从对接到交付的项目落地闭环说清楚。"

**一句话记忆**：ToB 落地 = 数据+实现方案+平台对接+交付标准 **四件事跟甲方对齐**；能把"对齐流程+变更处理"讲清楚，就证明有项目落地与沟通能力。

## 五、收尾反问与交流技巧

### 5.1 收尾阶段：别生硬"反问"，要像拉家常
最后"你有什么想问的"时，把它当打开话匣子的机会，而非一道标准答案题。可自然问：公司在发展上怎么样/近期重点？公司的愿景、方向、前景？你如何看待公司目前的方向前景（多聊两句，公司好不好大概能聊出一二）。

**聊到位的技巧（关键在"剥身份"）**：正式环节结束后脱离"面试官/应试者"身份，姿态放低、用"想向您请教"的口吻，话就开了。重点让对象愿意多聊。

### 5.2 为什么这阶段重要
聊好了说不定反而不看技术、觉得"你这个人有意思"就要你了——选人常常感性。也能借机评估公司值不值得去，不把决定权全押给"对方要不要我"。

### 5.3 所有回答：尽量多拓展、多深化（别惜字如金）
凡答了就尽量往深往宽多说几句：答完核心主动补一句"**之所以这样，是因为…/更细点说…**"；顺手展开相关场景或追问层（前提/边界/tradeoff）；把知识点串成一条主线讲（横向关联相近概念）；给自己设心法"**答到面试官开始点头、或主动接话为止**"。但要分清"多拓展"≠"跑题啰嗦"，围绕题目收得住。

**一句话记忆**：收尾别制度化反问，要拉家常了解公司"发展/愿景/前景"；正式环节后剥除身份、姿态放低更好聊；技术答完再多说两句 reasoning 和边界——惜字如金容易让人误以为"没真懂"。
