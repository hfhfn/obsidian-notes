# 🛡️ 业务降级与问题定位方法论

> [!abstract] 说明
> 面试被追问「业务降级是什么？PDF 格式乱怎么处理？出问题你怎么定位？」的**完整回答**。分两半：**降级**（可靠性兜底）+ **定位**（分层排查体系）。

---

## 1. 业务降级（Bedrock 兜底）

> 「夜幕降级」口误→应纠正为**业务降级**。核心：系统遇异常时，**主动放弃部分自动化能力，保障核心业务跑通**，而不是直接报错崩溃。

**触发时机**：PDF 解析失败 / 大模型调用超时 / JSON(Pydantic) 校验失败 / 自动化流程走不通。

**降级动作**（以商家资质审核为例）：
> "我们不直接返回报错，而是把这单资质文件**标记为需人工**，流转给人工审核人员处理，不再继续走自动审核链路。"

**一句话记忆**
> "业务降级 = 结构化校验/解析/LLM 都失败且重试无效时，自动把任务打标转人工，宁可人工兜底也不崩，保住核心流程可用。"

**实现要点**（面试展开）
- 分级重试（重试 N 次缩退）→ 再进降级。
- 降级标记写入 state（`review_status="manual"`），配合 §5 HITL 走人工断点。
- 记录降级原因到 `error_log` 供审计复盘。

---

## 2. PDF 文件格式不统一 / 杂乱怎么处理

> 资质 PDF 格式杂乱（扫描件/图片/版式不一）。三段式流程：

1. **OCR 提取**：有 PDF 和图片类 → OCR 识别文字内容。
2. **文本清洗**：解析后杂乱 → 剔除换行、乱码、多余空格等噪声。
3. **强制结构化 + 校验**：用 **Pydantic v2** 把解析出的信息强制结构化为统一字段，做类型/规则校验；校验不过则（重试后）触发降级转人工。

> **藏在"强制结构化"里的术语**
> 发言里「百单体壳」= **Pydantic**；「Jason 解析」= **JSON 解析**。回答时用规范词：**Pydantic Schema 结构化 + JSON 校验**。
```python
# Pydantic v2 强制结构化样本（抽取营业执照字段）
from pydantic import BaseModel, Field, field_validator

class LicenseInfo(BaseModel):
    company_name: str
    unified_code: str = Field(min_length=18, max_length=18)
    legal_person: str

    @field_validator("unified_code")
    @classmethod
    def alnum(cls, v: str) -> str:
        if not v.isalnum():
            raise ValueError(f"统一信用代码非法：{v}")
        return v

# 解析出的原始 dict → 强制结构化（失败抛 ValidationError → 触发降级）
try:
    lic = LicenseInfo.model_validate(raw_fields)
except Exception:
    # 重试 N 次仍失败 → 业务降级 → status=manual
    state["review_status"] = "manual"
```

> 补充：OCR 也可能把「某公司」误识成「某公同」（相似字），可用 **State Diff 对比 + 原始日志回溯**在定位阶段发现这类校验失败根因。

## 3. 问题定位方法论（分层金字塔）

> 被问「路径长、操作多、出问题怎么定位？」——别只答「打日志 + 看快照」，要**分层**。

**定位金字塔（自下而上）**：```
Layer 4: 业务指标监控（What）   ← 用户报障、业务大盘
Layer 3: 链路追踪（Where）      ← 哪个节点/环节慢了/挂了
Layer 2: 状态快照（Why）        ← State 在哪个节点被改坏了
Layer 1: 明细日志（How）        ← 具体入参、出参、报错
```

- **Layer 1 明细日志**：每个 LangGraph 节点打**入参/出参**日志，记录 task_id、会话 ID、输入数据、模型原始返回、异常全落日志；用 task_id 能打包整条任务所有节点日志。
- **Layer 2 状态快照**：LangGraph 自带 checkpoint，每跑一个节点全局 State 做快照保存 → 出故障后回看每个节点执行后的 State，看是哪个环节把数据改坏（定位是解析问题 / RAG 召回不对 / 还是大模型出错）。
- **Layer 3 链路追踪**：哪个节点慢 / 挂了，落在调用链。
- **Layer 4 业务监控**：从报障/大盘定位到是哪一类单被影响。

**关键术语纠正**（音频转文字易错，正式说规范词）：
- 「节点入餐出餐」→ **节点入参(Input)/出参(Output)**
- 「rog 召回」→ **RAG 召回**
- 「chat point china point」→ **Checkpoint 快照**

**一句话记忆**
> "定位靠四层：明细日志(入参出参+task_id可打包)→状态快照(checkpoint 回看是哪步改坏)→链路追踪(哪节点慢/挂)→业务监控(影响面)；其中 checkpoint 快照能直接看出解析、RAG、还是大模型的问题。"

## 4. 分层日志示例（Layer 1 落地）
```python
import logging
from functools import wraps

logger = logging.getLogger("agent")

def log_node(fn):
    @wraps(fn)
    def wrapper(state, config):
        task_id = config["configurable"]["thread_id"]
        logger.info("[%s] IN  %s", fn.__name__, state)
        try:
            out = fn(state, config)
            logger.info("[%s] OUT %s", fn.__name__, out)
            return out
        except Exception as e:
            logger.error("[%s] ERR %s", fn.__name__, e, exc_info=True)
            raise
    return wrapper
