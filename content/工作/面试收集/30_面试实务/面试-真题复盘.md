## 二、架构与技术类

### Q5. 主要工作内容？是不是拿 LangChain 搭 AI 流程？
**答法**：是的，以 LangChain/LangGraph 为核心，串 RAG、Agent、工具调用；具体工作含：文档解析+分块+向量化（Milvus）、检索优化（混合召回+Rerank/BBF）、Agent 编排与工具/MCP 接入、结构化输出、评估与上线、Docker 部署。
> 顺势把上面 Q11/12/16 的能力透出来，别只报一句。

### Q6. 业务也不复杂，为什么不用 Coze / Dify？【你卡住，必补】
**为什么要自建（toB 决定性理由，挑 3 条）**
1. **多租户权限/数据隔离**：要"A 客户看不到 B 客户"，低代码平台难做细粒度 RAG 权限。
2. **私有化部署/数据不出域**：toB/toG 合规要求，平台常是 SaaS 或难私有化。
3. **深度定制**：自定义召回/Rerank/微调、专属模型与工具、复杂 Agent 多步状态，低代码撑不起。
4. **成本/性能/锁死**可控。
**为什么 Coze/Dify 好**：快速 Demo、非工程师也能搭、内置模板与工具；适合 POC。
**一句话收**：Coze/Dify 适合"快速验证、轻业务"；我们做 toB 定制+权限+私有化，自建 LangChain/LangGraph 更可控。

### Q7. 你说 RAG 用 Milvus？
**答法**：Milvus 是开源向量数据库，存 embedding + **标量元数据**，支持 dense/sparse/multivector 混合检索与混合重排（很利于我们做混合召回+BBF），服务化、可横向扩。
> 关联 [[工作/面试收集/00_题库/05-AI&大模型|05-AI&大模型]]·Q2 多模态文档解析。

### Q8. 知识库怎么搭？A 客户看不到 B 客户的权限怎么做？【硬题，讲清两层】
**答法（关键：隔离必须在检索前，不能检索后过滤）**
- **数据归属层**：每个文档/块带 `tenant_id`（+ 文档ID）作为 **Milvus 标量字段**；检索时用**表达式 filter 强制 `tenant_id == 当前租户`**，向量检索只在授权子集内进行。
- **权限层（RBAC）**：用户→角色→权限；文档/块按密级与可见范围授权；检索前把用户可访问集合算好当 filter 传入。
- **为什么不能事后过滤**：先全库检索再删非授权结果，可能泄漏且浪费（向量里非授权内容已被模型"看到"）。
- **补充**：分级隔离（租户/项目/文档/块）、脱敏、审计。

### Q9. LLM-Wiki（Karpathy，2026 提出）——已核实，可正面答【原待核实，已补齐】
> **核心**：一个**个人知识库的构建模式**——不是即时检索式的 RAG，而是让 LLM **增量地构建和维护一份常驻、互相链接的 wiki（markdown 文件）**，放在"你"和"原始资料"之间。知识**编译一次、持续更新（复利）**，而不是每次提问从零重建。

**一句话对比（面试先抛，别定义先）**
> RAG = 每次提问时从原文档现成检索、答完即散（无积累）；**LLM-Wiki = 把读过的知识沉淀成持续变厚的结构化 wiki，交叉引用/矛盾/综合都提前做好**，像复利。Manifest：原文就写"**Obsidian 是 IDE，LLM 是程序员，wiki 是代码库**"。

**三层架构（能背）**
1. **Raw sources 原始资料**：你收集的文档/文章/PDF，**只读、不可变**，是真相源。
2. **Wiki 层**：LLM 全权维护的 markdown 目录（实体页/概念页/对比/概述/综合），LLM 负责建页、建链、保持一致，**你只读、它写**。
3. **Schema 配置层**：一份告诉 LLM"wiki 怎么组织/什么约定/什么流程"的文档（如 CLAUDE.md / AGENTS.md）。**这是让 LLM 当"有纪律的维护者"而非"通用聊天"的关键**，你与 LLM 共同演进它。

**三个操作（Ingest / Query / Lint）**
- **Ingest 摄取**：丢新源 → LLM 读、与你讨论、写摘要页、更新 index 与关联页、记日志（一篇常动 10~15 页）。
- **Query 查询**：LLM 先查 index 找相关页，再深读、**带引用综合回答**；好的回答可**回填成新页**，让探索也复利。
- **Lint 体检**：周期性查矛盾、被新源推翻的旧结论、孤儿页、缺交叉引用；LLM 还建议新问题/新来源。

**索引/工具**：`index.md`(内容目录) + `log.md`(时间线，可用 unix 工具 grep 解析)；**中规模(~100 源)可不用向量检索**；规模大再用本地 hybrid 搜索（如 `qmd`：BM25+向量+rerank、on-device、带 MCP server）。

**Why（点睛）**：累的不是"读/想"而是"**记账**"（更新交叉引用/摘要/标矛盾/跨页一致）。**LLM 不会烦、不会忘、一把改 15 个文件 → 维护成本≈0**。人类管"选源、提问、思考意义"，LLM 管"其余"。精神源头可追溯到 Bush 的 **Memex(1945)**。

**Obsidian 联系（面试顺势说，接你真实场景）**：Karpathy 原文以 Obsidian 为例（"Obsidian 是 IDE，LLM 是程序员，wiki 是代码库"），官方据此做了实现；而**你自己就在用 Obsidian + agent 维护知识库**——比空谈更有说服力，也是"我用过"的直接例证。

**一句话记忆**
> LLM-Wiki ≠ 每问必查的 RAG：让 LLM 把读过的东西**沉淀成常驻互链的 markdown wiki，编译一次持续更新**；Obsidian 是 IDE、LLM 是程序员、wiki 是代码库，维护成本≈0。

### Q11. bge-M3 + RRF？召回率 60%→78% 怎么做到的？78% 怎么算的？【硬题】
**bge-M3**：擅长多语言/多功能的 embedding 模型，同时输出 **dense(语义) + sparse(词法/BM25式) + multi-vector(ColBERT)** 三种表示，因此适合做召回增强。
**RRF（Reciprocal Rank Fusion，倒数排名融合）核心原理**：
- 把多路检索结果（如 dense + sparse + BM25）的排名**按名次而非分数**融合；每篇文档得分 = Σ `1/(k + rank_i)`，k 通常取 60。
- **为什么用名次不用分数**：各路检索的分数量纲/分布不同，**无法直接相加**；而"名次"是统一的，鲁棒——真正差一点的 doc 名次高就被保留，是"无监督、不依赖分数归一化"的融合法。
**60%→78% 怎么来**（组合拳：更好的分块 + 混合召回 dense+sparse + RRF 融合 + Rerank + 评估迭代）。
**78% 怎么"算"的（回答追问重点）**：
- 需要有**带标注的评估集**：一批「问题 → 正确答案对应的文档/块」。
- **Recall@K** = 正确答案的块是否出现在检索结果前 K 名；= 命中问题数 / 总问题数。
- **"模型输出不完全等于原文"怎么办**：标注时**按原始文档块 ID / 锚点对齐**，而不是用模型改写后的文本去匹配——评估的是"检索有没有把正确原文块召回"，与模型措辞无关；用自动化脚本跑评估集统计，可回归对比不同方案。

### Q12. Agent 平台上生产、突发流量，怎么做限流和高可用？【你开头说没弄过，就被换题，必补】
**限流**（见 [[工作/面试收集/20_专题研究/并发限流-工程化|并发限流-工程化]]）：网关 limit_req/limit_conn + 令牌桶 + 应用层 `asyncio.Semaphore` 控并发 + Redis 分布式限流；对接大模型 API 做客户端退避重试。
**高可用（H.A.）几个核心**
- 多副本 + Nginx/网关负载均衡 + **健康检查自动摘除**故障实例。
- **无状态化**：session/状态外置到 PG/Redis；Agent 可任意实例接管。
- **兜底**：熔断（上游挂了降级）、重试带退避、超时、降级（缓存/兜底回答）。
- **容量**：压力测试定阈值；**自动扩缩容**（K8s HPA）；热备与容灾。
- **可观测**：日志/指标/告警（Prometheus/Sentry），SLO 与告警联动。
**应对"没弄过"**：别只说没弄过——**给出设计思路**（上段）+ 一句"生产上有一部分由 SRE 抖底，但方案我清楚"。面试官要的是你有这层意识。

### Q14/Q15. subagent 是**运行时临时生成**的，怎么保证它的权限可控、又不影响用户体检？【你没答好，必补】
**核心矛盾**：事前把每个 agent 权限定死（整里） vs 产品里 subagent 是**动态生成**的，无法授权时分区。
**权限可控（deny-by-default + 作用域继承）**
- **最小权限 + 默认拒绝**：subagent 默认无权限，只有任务明确需要才放。
- **作用域（scope）继承**：subagent 只继承父 Agent/当前任务的**受限作用域**令牌与资源范围，且**一次性地、只读优先**。
- **敏感操作审批/沙箱**：关键动作需授权或丢沙箱（见 [[工作/面试收集/20_专题研究/MCP与skill-对比|MCP与skill-对比]] 沙箱节）。
- **审计/可回放**：记录 subagent 用了哪些工具、读写了什么；超时/异常自动回收。
**不影响体验**
- **策略化自动放行**：白名单/规则命中直接放，才需要人点的是"高风险资源"。
- **异步审批**：审批不阻塞主流程，先继续、后台追认；失败给明确降级提示。
- **透明可见**：前端展示 subagent 正在做什么、进度与可中断。
- **一句话**：权限=默认拒绝+作用域继承+审批/沙箱+审计回收；体验=策略自动放行+异步审批+透明进度——**权限收紧不等于把用户卡死，靠的是策略和异步化**。

### Q16. 评论分类：知识蒸馏 200ms→10ms，怎么实现的？能否用在你的 API 响应？【硬题】
**对齐你的数据**：把大模型当 teacher，在标注/生成数据上训练一个小模型 student，输出/标签做 schema 对齐，配合量化或小模型蒸馏；核心是"**teacher 的软标签 + 对齐小模型**"，让 20 倍左右降延迟。
**思路可迁移到业务 API 响应**：把高频、简单、必须快的子任务（如分类/信息抽取/意图）**蒸馏到小模型/或走专用小 LLM**；复杂任务仍走大模型——**"快的小模型承接简单短链、大的承接复杂长链"**，按延迟与质量分级路由。
**"怎么算 200→10ms"**：端到端延迟（模型调用到返回）在**同一硬件/同量级请求**下压测，取 **P50 或 P99**，AB 对比蒸馏前后；可再用同一评估集验指标不掉。

### Q17/18/19. 你用的 Claude Code/ChatGPT 背后是哪家？怎么付的钱？【容易被问穷的账，讲清口径】
- **分清厂商**：Claude Code→**Anthropic**；ChatGPT→**OpenAI**；两家不同模型、不通用。
- **付费方式两种**：**订阅（按月）** vs **按量 API（充值/token 计费）**。
  - Claude 订阅：Pro($20/月) / Max($100/月)（按量 Developer 计费另有）。ChatGPT 也有订阅档。
  - 闲聊账号 vs API 是按量 key。
- **成本口径**：订阅适合**高频个人开发**（含工具额度）；API 按量适合**自动化/服务化**，可控制上限。
- 📌 填：你实际怎么买的、大概档次，讲**自己怎么控制成本的**（预算上限/缓存/少写 token）比报"买了几个账号"更稳。
